# MAUI 실제 수신 코드 확정 검증 계획

## 23시 후속 — 단일 업무 수신 확인 및 원상 모드 복원

[단일 실제 수신](단일경매_버튼별_MAUI실수신.md)과 [증거표](단일경매_MAUI실수신_증거표.md)를 추가했다. 단일모드 대량 SV에서 디코더 추적이 실행을 지연시켜 업무 처리 진입 경계로 옮겼다. 기존 야간 정책에 의한 정상 종료 후 같은 바이너리를 재실행했으며, 아래 진단 소스 추가·교체 빌드안은 실행하지 않았다. 검사 후 원래 일괄 모드/구간 복원, 추적점 제거·Detach, users.XML 해시 일치를 확인했다. 아래 '계속 실행 중'은 22:41 당시 상태이며 이후 야간 종료까지 포함한 최종 상태가 아니다.

## 22:41 후속 결과 — 재시작 없이 일괄 실수신 확인

아래는 21시대에 세웠던 계획이다. 이후 기존 Visual Studio의 디버거를 실행 중인 MAUI 프로세스에 연결하고 `AuctionClientInboundDecoder.Decode` 함수 추적점을 사용해 수신 코드·허용 상태만 관찰했다. **제품 소스에 진단을 추가하거나 앱을 재시작할 필요 없이 일괄모드 수신 검증을 수행했다.** 추적점은 삭제하고 Detach했으며 기존 앱은 계속 실행 중이다. 사용자에게 재시작 예외 승인을 다시 요구하지 않는다.

확정한 내용은 [일괄 버튼별 실제 수신](일괄경매_버튼별_MAUI실수신.md)과 [증거표](일괄경매_MAUI실수신_증거표.md)를 참조한다. 단일모드의 전수 실수신 관찰은 이번 일괄 결과로 대체하지 않는다. 아래 소스 진단·재시작안은 실행되지 않은 대안 기록으로 남긴다.

## 당시 계획

버튼 실측과 코드 대조는 작성했지만 실행 중인 MAUI에 패킷별 수신 진단이 없어 컨트롤러의 CA/CF/CI가 서버에서 어떤 코드로 바뀌어 도착하는지까지는 입증하지 못했다. 정확한 버튼→MAUI 수신 순서를 확정하려면 아래 작업이 필요하다. **현재는 계획이며 소스 변경·재시작은 실행하지 않았다.**

## 구체적 변경 범위

- 수신 진단 도우미: 프로토콜 코드는 고정 허용 목록만 출력하고 AS 상태(8001~8007), AF 결과(22~24), AT 방식(10/20), SD 모드(C/F)·카운트처럼 검증에 필요한 고정 범위 필드만 출력한다.
- `AuctionClientInboundDecoder.Decode`: 디코더가 SV/SS를 소비하기 전 수신을 관찰한다. 원문·개체번호·사업장·참가자·가격·인증값은 기록하지 않는다.
- 프로세스 한정 환경 변수로 검증 때만 활성화한다. XML·host.json·영구 시스템 환경 변수는 변경하지 않는다.
- 잘못된 입력·알 수 없는 코드·민감 필드가 출력되지 않는 검사, 비활성 상태에서 추가 로그가 없는 검사.
- 기본 통신과 상태 처리 순서는 바꾸지 않는다. 진단 출력 자체의 실패가 패킷 처리를 막지 않도록 구현한다.

## 실행과 확인

1. 현재 창·프로세스·users.XML 해시·기존 변경 상태를 보존 기록한다.
2. 별도 출력에 빌드·검사를 마친다.
3. 경매 대기 상태에서 **MAUI 전광판만** 정상 종료 후 진단 빌드로 다시 연다. Chrome·컨트롤러는 유지한다. 이는 기존 '프로그램을 끄지 말 것' 조건의 예외 승인이 필요하다.
4. 기존과 같은 버튼 동작을 다시 검증하고 컨트롤러 로그 시각과 MAUI 수신 진단 시각을 대조한다. 불필요한 결과/설정 변경은 반복하지 않는다.
5. Docs/경매프로그램의 추정·미확인을 실측으로 교체한다. 여전히 검증되지 않은 항목은 그대로 남긴다.
6. XML 해시와 기존 Chrome·컨트롤러 유지 여부를 확인한다. 진단 비활성 기본 실행은 기존 동작을 유지한다.

프로그램종료 버튼, 설정 저장·서버 초기화는 별도 보존 조건 때문에 이 검증에서도 실행하지 않는다. 활성 수동 Enter 경매는 음성경매 설정 변경 없이 검증할 수 없는 조건으로 명시한다.
