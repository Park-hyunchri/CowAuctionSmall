# 경매 진행 중 신규/수정 정보 동기화 개선 방향

## 1) 배경
- 현재 `ServerGetData.ProcessMessageAsync()`는 `_runRunSipNumber != -1`이면 비교 루프를 바로 종료한다.
- 그래서 경매가 진행 중일 때는 "진행 중인 개체"뿐 아니라 "다른 개체의 신규 등록/정보 수정"도 함께 지연된다.
- `ModifiedData()`에서도 `_runRunSipNumber != -1`이면 수정 반영을 크게 제한하고 있어, 실시간성보다 안전성에 치우쳐 있다.

관련 코드:
- `Services/ServerGetData.cs:272`
- `Services/ServerGetData.cs:449`

## 2) 목표
- 경매 진행 중에도 **진행 중 개체를 제외한** 신규/수정/삭제는 즉시 반영한다.
- 진행 중 개체는 **변경 반영 금지 대상**으로 간주하고, 해당 변경은 종료 후에도 적용하지 않고 폐기한다.
- 경매 진행 중 데이터 변경 이벤트가 발생해도 진행 화면의 페이지(특히 유전능력 페이지) 회전은 절대 발생하지 않게 한다.
- 로직을 "전역 중단"에서 "개체 단위 제어"로 바꾼다.

## 3) 권장 설계 방향
## A. 전역 중단 제거
- `ProcessMessageAsync()` 초반의 `if (_runRunSipNumber != -1) return;` 제거.
- 서버 폴링/파싱/비교는 계속 수행하고, 반영 단계에서만 필터링한다.

핵심 원칙:
- 수집과 비교는 계속
- 적용만 선별

## B. 변경 이벤트를 3가지로 분리
- `Insert`(신규 개체)
- `Update`(같은 개체 정보 변경)
- `Move`(같은 개체의 `SpaceIndex` 변경)

현재처럼 카운트 기반 분기(증가/감소/동일)만 사용하면 일부 케이스를 놓칠 수 있으므로, 권장 키(`EntityNumber`) 기준으로 집합 비교를 통일한다.

권장 비교 방식:
1. `oldMap = oldList.ToDictionary(EntityNumber)`
2. `newMap = newList.ToDictionary(EntityNumber)`
3. `Insert = newMap.Keys - oldMap.Keys`
4. `Delete = oldMap.Keys - newMap.Keys`
5. `Common = 교집합`에서 `Equals` 비교로 `Update/Move` 판정

## C. 진행 중 개체는 "하드 블록(반영 금지)"
- `_runRunSipNumber`에 해당하는 개체의 `Insert/Update/Move/Delete`는 모두 화면 반영 대상에서 제외한다.
- 제외된 변경은 `pending`에 저장하지 않는다. 즉, **보류가 아니라 폐기(discard)** 한다.
- 로그로만 남기고(`blocked-running-entity-change`) 처리 종료한다.

적용 규칙:
- 진행 중 개체 식별 기준은 `SipNumber == _runRunSipNumber.ToString()` 우선.
- 동일 `SpaceIndex` 충돌로 진행 화면 안정성을 해칠 가능성이 있으면 동일하게 차단.
- `AS 8006`, `AF/SD` 이후에도 차단했던 변경은 재적용하지 않는다.

## D. 즉시 반영 허용 범위 정의
- 즉시 반영:
  - 진행 중 경매번호와 무관한 개체의 신규/수정/삭제
  - 다른 `SpaceIndex` 패널 변경
- 반영 금지:
  - 진행 중 `SipNumber`와 직접 충돌하는 모든 정보 변경
  - 진행 패널 UI 안정성을 깨는 위치 이동/상태 급변

## E. 경매 중 페이지 회전 금지(유전능력 페이지 포함)
- 경매 진행 상태(`_runRunSipNumber != -1`)에서는 변경 이벤트로 인해 진행 패널의 페이지 인덱스가 변경되면 안 된다.
- `DisplayRunning()` 재호출 시에도 기존 페이지 상태를 유지하고, 타이머 재시작/리셋을 금지한다.
- 특히 유전능력 페이지 회전 타이머는 경매 진행 중에는 동결해야 한다.

권장 구현 포인트:
- `PanelDisplayState`에 `IsAuctionLocked` 또는 동등 플래그를 두고 진행 중에는 페이지 관련 업데이트를 스킵.
- `UpdateSignature` 변경이 들어와도 진행 중이면 "페이지 회전 관련 필드"는 갱신하지 않는다.

## F. 화면 반영 단위 개선(선택)
- 현재 `OnDataChanged()`는 메시지마다 `_currentCowList.Clear()` 후 재구성한다.
- 변경 건만 부분 반영하는 방식으로 바꾸면 깜빡임/부하를 줄일 수 있다.

관련 코드:
- `ViewModels/MainWindowViewModel.cs:285`

## 4) 단계별 구현 제안
1. 1단계(필수): 전역 `return` 제거 + 진행중 개체 필터 도입
2. 2단계(필수): 진행중 개체 변경 `discard` 처리 및 차단 로그 추가
3. 3단계(필수): 경매중 페이지 회전/타이머 리셋 금지 처리
4. 4단계(권장): 비교 로직을 키 기반 diff로 통합
5. 5단계(권장): UI를 부분 갱신 방식으로 전환

## 5) 최소 수정 포인트
- `Services/ServerGetData.cs`
  - `ProcessMessageAsync()`의 전역 중단 제거
  - `ModifiedData()`의 전역 중단 제거, 개체 단위 필터 적용
  - 진행중 개체 변경 `discard` 분기 추가(보류 큐 없음)
  - `OnStringArrMsg()`/`OnStringArrAF_SD()`는 진행 상태 전환만 담당(차단 데이터 재적용 없음)
- `Services/DisplaySelect.cs`
  - 경매 진행 중 `DisplayRunning()` 재호출 시 페이지 인덱스/회전 타이머 고정
  - 변경 이벤트 수신 시 유전능력 페이지 로테이션 트리거 차단
- `ViewModels/MainWindowViewModel.cs`
  - 가능하면 변경 리스트 기준 부분 반영(선택)

## 6) 테스트 시나리오(필수)
1. 단일경매 진행 중, 다른 개체 신규 등록 발생 -> 즉시 해당 패널 표시
2. 단일경매 진행 중, 다른 개체 정보수정(비고/어미/산차) -> 즉시 갱신
3. 단일경매 진행 중, 진행 개체 자체 정보수정 -> 즉시 차단(discard), 종료 후에도 반영되지 않음
4. 진행 중, 다른 개체 `SpaceIndex` 이동 -> 기존 패널 로고 처리 + 새 패널 표시
5. 단일경매 진행 중, 다른 개체 변경 이벤트 연속 수신 -> 진행 패널이 유전능력 페이지로 회전하지 않음
6. 진행 중 타이머 tick 발생 시에도 진행 패널 페이지 인덱스 고정 유지
7. 종료(`8006`) 직후 차단했던 진행 개체 변경이 재적용되지 않음

## 7) 운영 안정성 체크포인트
- 중복 메시지 대응: 진행중 개체 변경은 동일 정책으로 즉시 폐기
- 순서 역전 대응: `UpdateDtm` 또는 수신 시각 기반 최신값 우선
- 스레드 안정성: `_lockObj` 또는 별도 lock으로 차단/적용 분기 일관성 유지
- 로그: 즉시 반영/차단(discard)/페이지회전차단 경로를 분리 로깅

## 8) 결론
- 핵심은 "경매 중이라서 전체 동기화를 멈추는 방식"을 없애고,
- "진행 중 개체는 변경 반영을 금지하고, 나머지는 계속 반영"하는 구조로 전환하는 것이다.
- 동시에 경매 진행 중에는 유전능력 페이지를 포함한 페이지 회전이 변경 이벤트로 트리거되지 않도록 고정해야 한다.
- 이 방식이면 화면 안정성과 실시간성을 동시에 확보할 수 있다.
