## 목적과 현재 문제

API는 개체 이력번호별로 조회하되 화면의 이력 문구는 현재 표시 대상 묶음의 처리가 끝났을 때 한 번에 반영한다. 경매 진행·가격·낙찰·일반 비고는 기존처럼 즉시 갱신한다.

현재 MainWindowViewModel.QueueHistoryAsync는 개체별 조회 완료마다 UpdatePanels를 호출한다. UpdatePanels도 서비스의 중간 메모리 캐시를 직접 읽으므로, 완료 콜백만 묶어도 다른 경매 메시지가 들어올 때 일부 이력이 먼저 노출될 수 있다. 화면에 반영을 확정한 이력과 조회 중인 결과를 분리해야 한다.

## 동작 기준

1. 묶음은 현재 보드에 표시되는 소 개체(구분 1·2·3)의 유효한 15자리 이력번호 집합이다. 같은 개체의 중복 슬롯은 한 번 조회한다. Board 밖 개체·염소·말·무효 번호는 제외한다.
2. 기존 API의 개별 순차 호출, 최소 1초 간격, 재시도·인증 중단·캐시 정책을 유지한다. 병렬 HTTP 호출이나 전체 출품 목록 선조회는 추가하지 않는다.
3. 묶음의 결과는 임시 보관한다. 캐시 적중도 같은 반영 경계를 통과한다. 정상 빈 결과와 조회 실패를 구분하여, 정상 빈 결과는 이전 이력을 지우고 실패는 기존 정상 표시를 유지한다.
4. 모든 대상이 성공·실패·기존 서비스의 조회 중단 중 하나로 정리되면 UI Dispatcher 작업 한 번에서 확정 결과를 적용한다. 중간 조회 결과는 경매 메시지의 일반 화면 갱신에서도 노출하지 않는다.
5. 조회 중 경매 데이터가 갱신되어도 이력번호 집합이 같으면 묶음을 다시 시작하지 않는다. 대상이 바뀌면 이전 묶음의 화면 반영을 무효화하고 최신 대상 묶음으로 전환한다. 이전 요청이 끝나기 전 무제한 추가 작업을 만들지 않는다.
6. 캐시 기준일 변경 시 기존 이력 표시와 묶음을 초기화한다. UI 반영 직전에도 기준일·묶음 세대·종료 상태를 검사한다. 이력 API와 당일 캐시의 기존 날짜 정책은 변경하지 않는다.
7. 수동 이력 새로고침도 동일한 묶음 반영을 사용한다. 진행 중인 동일 수동 요청은 병합한다. 실패 후 동일 입력의 반복 polling이 무한 재조회를 유발하지 않게 한다. 대상 변경·수동 새로고침·기준일 변경은 새 묶음의 시작 사유다.
8. 조회 결과를 과거 gValues 전체에 덮어쓰지 않는다. 적용 시 현재 표시 개체에 이력 문구만 반영하여 최신 가격·상태·출하 정보와 슬롯 변경을 보존한다.

## 실행 순서와 검증

1. 시작 Git 상태와 대상 파일의 현재 내용을 보관한다. 기존 구조 개편 및 사용자 변경을 보존한다.
2. UI와 독립적으로 검사할 수 있는 묶음 조정자를 구현한다. 지연되는 가짜 개별 조회를 사용해 첫 결과가 화면으로 노출되지 않는지 확인한다.
3. ViewModel의 모든 이력 표시 경로를 조정자에 연결한다. 개별 조회 완료 후 전체 화면 갱신 및 서비스 캐시 직접 읽기를 제거한다.
4. 캐시/신규 혼합, 중복 번호, 성공 빈 결과/실패, 실시간 갱신 중 부분 노출 차단, 대상 교체, 오래된 UI 콜백, 기준일 변경, 수동 중복 새로고침, 종료 후 반영 차단을 검사한다.
5. Debug·Release 빌드와 기존 경매·표시 전체 검사 및 이력·SQLite 오프라인 검사를 실행한다. 실패는 같은 범위에서 해결하고 결과를 기록한다.

```powershell
dotnet build CowAuctionSmall.csproj -c Debug --no-restore
dotnet build CowAuctionSmall.csproj -c Release --no-restore
dotnet run --project Validation/ReferenceAdoptionChecks/ReferenceAdoptionChecks.csproj --no-restore -- all
dotnet run --project Validation/OwnerHistoryChecks/OwnerHistoryChecks.csproj --no-restore -- --offline
```

제품 App 및 운영 API를 실행하지 않는다. 실제 화면의 동시 표시 체감·전광판·운영 서버 지연은 현장 확인 항목으로 구분한다.

## 한계와 범위 제외

- 한 묶음의 신규 대상이 많거나 응답이 느리면 이력 표시까지 기다림이 길어진다. 이번에는 임의 제한시간으로 일부 결과를 먼저 공개하지 않는다. 경매 정보 표시는 기다리지 않는다.
- 이미 시작한 개별 HTTP 요청의 취소 정책은 그대로 유지한다. 대상 교체 후 오래된 결과의 화면 반영을 막고 불필요한 후속 조회를 줄인다.
- 인증키·설정 값·패키지·API 주소/파라미터·호출 간격·DB 스키마/보존 기간·텍스트 스크롤·GIF 미지원 정책은 변경하지 않는다.
- 운영 배포·commit·push는 수행하지 않는다.

## 구현 및 검증 결과

- AnimalHistoryBatchCoordinator가 한 개의 조회 작업 흐름에서 최신 대상 묶음을 처리한다. 확정된 이력 사전과 임시 결과를 분리하여 동기 캐시 적중이나 다른 경매 메시지도 중간 결과를 표시하지 못하게 했다.
- MainWindowViewModel의 개체별 완료 갱신을 제거하고 자동·수동·기준일 변경·종료 경로를 묶음 처리에 연결했다. 묶음 반영은 현재 개체 데이터의 복사본을 사용하므로 조회 시작 당시 가격·상태로 되돌리지 않는다.
- AnimalHistoryService에 Epoch와 GetAnimalHistoryNoteAsync를 추가했다. 현재 기준일의 유효 결과 여부와 문구를 함께 반환해 실패와 정상 빈 결과를 구분한다. 기존 API·캐시·재시도 코드는 유지했다.
- 신규 `Validation/ReferenceAdoptionChecks/HistoryBatchChecks.cs`는 부분 완료, 캐시/신규 혼합, 중복 번호, 같은 집합 반복 입력, 실패/빈 결과, 수동 연타, 자동→수동 전환, A→B→A 대상 교체, 지연 UI 콜백, 기준일·Reset·Dispose를 검사한다. 서비스 경계도 fake 클라이언트와 메모리 저장소로 확인했다.
- `dotnet run --project Validation/ReferenceAdoptionChecks/ReferenceAdoptionChecks.csproj --no-restore -- history`: 신규 28개 통과.
- 같은 프로젝트 `-- all`: 전체 926개 통과.
- `dotnet run --project Validation/OwnerHistoryChecks/OwnerHistoryChecks.csproj --no-restore -- --offline`: 77개 통과.
- `dotnet build CowAuctionSmall.csproj -c Debug --no-restore -v:q` 및 Release: 각각 경고 88개·오류 0개. 새 패키지 설치·복원·설정 변경 없음.

총 3명이 구현·독립 검토·검증을 분담했다. 제품 App·운영 API·전광판은 실행하지 않았다. 실제 ViewModel 전체 연결과 전광판의 동시 표시 체감은 수동 확인 항목이다. 신규 대상이 많을 때 이력 표시까지 기다림이 길어질 수 있다는 기존 계획의 한계는 유지한다. 변경 기록은 [WORKLOG](../../../WORKLOG.md)를 참고한다.
