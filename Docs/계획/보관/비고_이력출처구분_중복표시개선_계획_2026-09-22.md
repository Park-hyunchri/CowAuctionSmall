# 비고·이력 출처 구분과 중복 표시 개선 계획

> 문서 상태: **철회·원상복구** · 정리일: 2026-10-01
> 사용자 요청으로 중복 생략 변경을 원상복구했다. 현재 Note 원문을 임의로 생략하는 기능의 구현 지침이 아니다.
> 현재 동작: [기능 문서](../../기능/README.md) · [전체 목차](../../README.md) · [작업 기록](../../../WORKLOG.md)

작성일: 2026-09-22

상태: **철회·원상복구 완료(2026-09-22)**. 사용자가 서버 `Note` 원문에 이미 이력이 포함되어 있었음을 확인하고 중복 생략 변경의 원상복구를 요청했다. 구현 과정의 소스·검증·설명 변경을 작업 전 상태로 복구했다. 아래 내용은 철회된 계획의 기록이며 현재 적용된 동작이 아니다.

## 1. 목적과 확인한 현상

사용자가 확인한 화면 위치 2·3·4번을 별도 실행본으로 조사했다. 서버 비고에 소유주 이름과 날짜의 연결 이력이 이미 포함되어 있었으며, 이력제 조회 결과가 뒤에 추가되어 같은 소유주 내용이 빨간색과 흰색으로 반복 표시됐다.

해당 실행에서 경매 API 새로고침을 두 차례 요청한 뒤에도 이력제 문구의 흰색은 유지됐다. 이 결과는 그 실행에서 확인한 범위이며, 모든 갱신 상황의 색상 문제를 배제한 것으로 해석하지 않는다. 이번 개선은 확인된 중복 표시와 데이터 출처 구분을 대상으로 한다.

사용자의 최종 기준은 **서버 원본 `Note`와 이력제로 추가한 부분이 확실히 구분되어야 한다**는 것이다. 기존 `Note` 속의 이름·날짜를 흰색으로 바꾸는 이전 제안은 적용하지 않는다.

## 2. 유지해야 할 규칙

| 항목 | 데이터 보존 | 표시 규칙 |
| --- | --- | --- |
| `Note` | 현재 수신·파싱 경로가 제공한 원문 유지 | 일반 비고 전체를 빨간색으로 표시 |
| `NoteChangeOwner` | 조회 결과 원문 유지 | 추가 표시가 필요한 경우 흰색으로 표시 |
| 중복된 추가 이력 | 원본 두 필드를 수정하거나 비우지 않음 | 추가 이력의 화면 표시만 생략 |
| 구분자 ` / ` | 표시 과정에서만 생성 | 두 부분이 모두 표시될 때만 빨간색으로 표시 |
| 빈 비고·기존 `-` 표식 | 원본 필드 유지 | 기존처럼 화면에서 생략 |

- `Note`에 들어 있는 소유주 이력도 서버 비고이므로 빨간색을 유지한다.
- 이미 적용된 사업장별 비고 파싱 규칙은 변경하지 않는다. 이번 작업의 원문 보존은 그 파싱 이후 전달된 `Note`를 중복 처리 때문에 다시 수정하지 않는다는 뜻이다.
- 이름만 같다는 이유로 문구를 삭제하지 않는다.
- 기존 비고가 더 긴 이력을 포함하면 전체 연결을 보존한다.
- 출처와 관계없이 비고 전체에 흰색 또는 빨간색을 일괄 적용하지 않는다.
- 이력 조회·당일 캐시·재시도·호출 예산·통신 프로토콜은 이번 변경 대상이 아니다.

## 3. 표시 결과 예시

아래 이름과 날짜는 설명용 합성 데이터다.

| 서버 `Note` | 추가 `NoteChangeOwner` | 최종 표시 |
| --- | --- | --- |
| `어미확인` | `TEST_A → TEST_B(양수 2026-02-01)` | 빨간 비고 + 빨간 구분자 + 흰 추가 이력 |
| `어미확인, TEST_A(26.01.01)→TEST_B(26.02.01)` | `TEST_A → TEST_B(양수 2026-02-01)` | 원래 비고 전체를 빨간색으로 한 번 표시 |
| `TEST_A(26.01.01)→TEST_B(26.02.01)→TEST_C(26.03.01)` | `TEST_B → TEST_C(양수 2026-03-01)` | 더 긴 원래 비고를 빨간색으로 유지하고 추가 이력 생략 |
| `TEST_A(26.01.01)→TEST_B(26.02.02)` | `TEST_A → TEST_B(양수 2026-02-01)` | 날짜가 다르므로 기존 방식으로 두 부분 표시 |
| 빈 값 또는 `-` | 유효한 조회 문구 | 조회 문구만 흰색으로 표시 |
| 일반 비고 | 빈 조회 문구 | 비고만 빨간색으로 표시 |

## 4. 중복 판정 기준

화면에 추가하려는 이력이 기존 비고에 **동일한 소유주 변경 사건으로 포함되어 있음**을 확인할 때만 생략한다.

1. 조회 문구에서 이전 소유주·현재 소유주·양수 날짜를 확인한다. 현재 생성 형식인 `이전 → 현재(양수 yyyy-MM-dd)`를 우선 지원한다.
2. 서버 비고에서는 `이름(날짜)→이름(날짜)` 형태의 인접한 연결을 찾는다. 긴 연결은 각 인접 구간을 비교한다.
3. 이전 소유주와 현재 소유주가 각각 일치하고, 현재 소유주의 양수 날짜까지 일치해야 중복으로 판정한다. 현재 조회 문구에는 이전 소유주의 시작 날짜가 없으므로 그 날짜를 임의로 추정하지 않는다.
4. `→`와 `->`, 구분 기호 주변 공백, 확인된 날짜 표기 차이만 비교용으로 정규화한다. 원본 문자열은 그대로 둔다.
5. 두 자리 연도는 조회 결과의 명확한 네 자리 날짜와 비교한다. 운영체제의 두 자리 연도 해석 기준으로 임의의 세기를 부여하지 않는다. 해석이 모호한 경우 생략하지 않는다.
6. 이름은 토큰 전체로 비교한다. 다른 이름의 부분 문자열, 일반 문장에 포함된 이름, 화살표 없는 이름 나열은 중복 근거로 사용하지 않는다.
7. 날짜 누락·유효하지 않은 날짜·동명이인으로 의심되는 불명확한 연결·지원하지 않는 형식은 판정 불가로 처리해 추가 표시를 유지한다. 표시상 일치 판정은 실제 사람의 신원 동일성을 증명하는 기능이 아니다.

판정이 불확실하면 중복이 남더라도 정보를 숨기지 않는 쪽을 선택한다. 임의의 이름 검색·문자열 전체 치환으로 원본 비고를 삭제하지 않는다.

## 5. 구현 구조와 영향 파일

### 5.1 공통 조합 규칙

`Domain/Auction/AuctionNoteComposer.cs`를 신규 후보로 둔다. WPF·네트워크·파일 접근이 없는 순수 계산 코드로 작성한다.

- 입력: `Note`, `NoteChangeOwner`.
- 결과: 표시할 일반 비고, 표시할 추가 이력, 중복 생략 여부, 최종 합성 문자열.
- 중복 판정과 문자열 조합은 한 곳에서 수행한다.
- 계산 결과 때문에 원본 `gValues`를 변경하지 않는다.
- 전역 캐시·새 작업 스레드·타이머는 도입하지 않는다. 일반적인 짧은 비고를 대상으로 제한된 형식만 판정하며, 정규식을 사용한다면 과도한 역추적을 피하도록 제한한다.

## 6. 진행 순서

1. **입출력 규칙과 판정 검사 작성**: 합성 사례로 중복·비중복·판정 불가와 원본 보존을 확정한다.
2. **공통 조합 구현**: 조회 문구와 비고의 소유주 연결을 비교하고 표시 결과만 계산한다.
3. **모델·화면 연결**: `DisplayNote`와 `NoteText`에 동일한 결과를 적용한다.
4. **오프라인 회귀 검증**: 색상·바인딩·스크롤을 진행/낙찰/유찰과 해상도별로 확인한다.
5. **실제 화면 확인**: 사용자가 확인한 위치 2·3·4번에서 기존 빨간 비고의 보존과 추가 중복 문구 생략을 비교한다. 현재 세 칸은 모두 중복 사례이므로 별도 비중복 합성 사례로 흰색 추가 표시도 검증한다.
6. **문서·완료 기록**: 실제 변경 파일과 검증 결과, 확인하지 못한 범위를 기록한다.

## 7. 검증 항목

### 조합과 원본 보존

- 두 사람의 연결, 세 사람 이상의 긴 연결에서 추가 이력이 중복되는 경우.
- 이름만 같고 날짜가 다른 경우, 현재 소유주만 같은 경우, 이전 소유주가 다른 경우.
- 비고 내용 안의 부분 이름, 임의의 괄호·날짜, 화살표 없는 문장에 대한 오탐 방지.
- `→` / `->`, 구분 기호 주변 공백, 확인된 날짜 형식, 잘못된 날짜와 모호한 두 자리 연도.
- `Note`·`NoteChangeOwner`의 null/빈 값/공백과 비고 `-` 표식.
- 중복 생략 뒤에도 두 원본 속성·복제본·기존 이력 캐시가 유지됨.
- `gValues.DisplayNote`와 실제 Run을 합친 텍스트가 일치함.

### 색상과 갱신

- 일반 비고에 소유주 이름·날짜가 포함돼도 빨간색 유지.
- 비중복 추가 이력은 흰색, 구분자는 빨간색.
- 중복일 때 흰 Run과 구분자가 없어지고 원본 빨간 문구가 유지됨.
- 비중복 → 중복 → 비중복 전환 때 숨겨진 이력이 원본 손실 없이 다시 표시됨.
- 이력 조회 전후·조회 결과 없음·기존 서비스의 실패 시 이전 정상 결과 유지 흐름.
- 동일 데이터 반복 갱신·가격만 변경·원본 비고만 변경·추가 이력만 변경.
- 새로고침·순환 페이지 전환·진행→낙찰→유찰·재진입 후 색상 유지.
- 표시 문자열이 동일하지만 일반/추가 출처가 바뀌는 경우 색상이 갱신됨.
- 표시 길이가 바뀌는 경우 스크롤 위치를 적절히 초기화하고, 실제 표시가 같으면 불필요한 재시작을 피함.

### 실행 방법

- 별도 TEMP 출력의 Debug 빌드 후 조합·색상 전용 검사, ReferenceAdoptionChecks `binding`, OwnerHistoryChecks `--scroll-offline` 실행.
- 새 순수 판정 검사와 기존 관련 오프라인 검사를 실행하고 실패 시 같은 목적의 오류를 해결한다.
- 개인정보·실제 소유주 이름·개체번호·인증 정보는 테스트나 작업 기록에 새로 넣지 않는다. 실제 사례는 합성 이름과 날짜로 대체한다.
- 실제 확인은 승인된 기존 실행 범위 안에서 2·3·4번 표시와 새로고침을 확인하며 경매 시작·응찰·낙찰 제어 신호를 보내지 않는다.
- 이번 계획 작성 시 빌드·테스트·앱 실행은 미수행이다. 구현 전 계획이며 통과 결과를 미리 기재하지 않는다.

## 8. 완료 기준

- `Note`의 표시 내용과 빨간색이 보존된다.
- 추가 이력의 출처가 원본 필드와 흰색 표시로 구분된다.
- 확인된 중복 추가 문구만 생략되고, 불확실한 문구는 숨기지 않는다.
- 더 긴 기존 이력과 비고의 일반 설명이 손실되지 않는다.
- 모델·ViewModel·실제 화면의 표시 문자열이 일치하고 색상·스크롤 회귀 검사가 통과한다.
- 신규 패키지·통신 규격·캐시 형식·사업장 설정 변경 없이 목적을 달성한다.

## 9. 계획 작성 검증

- 작성 시작 시 Git 상태 194개 항목. 기존 미커밋·미추적 작업을 보존하고 이 계획 문서만 추가한다.
- 문서 내용·파일 링크·신규 diff를 확인한다.
- 소스 구현·WORKLOG 갱신·commit·push·운영 배포는 이번 계획 작성에서 수행하지 않는다.
