## 1. 현재 동작과 개선 이유

현재도 HTTP 조회는 비동기다. 별도 스레드를 하나 만드는 것만으로 빨라지는 구조는 아니다.

| 현재 구현 | 영향 | 개선 방향 |
| --- | --- | --- |
| 조정자가 이력번호 순으로 한 건씩 완료를 기다림 | 앞 요청이 느리면 뒤 요청과 캐시 확인도 기다림 | 캐시 확인과 HTTP 대기열을 분리하고 제한된 동시 조회 지원 |
| 서비스가 세마포어 1개로 요청·응답·재시도 대기 전체를 직렬화 | 느린 응답과 재시도 대기가 다른 개체를 막음 | 동시 요청 수, 요청 시작 간격, 재시도 예약을 분리 |
| 요청 시작 간격 최소 1초 | 신규 개체가 많으면 전체 수집에 시간이 필요 | 제공기관의 허용량을 확인한 뒤 간격·동시 요청 수 결정 |
| 메모리·당일 SQLite 캐시를 이미 사용 | 캐시가 있어도 조정자의 앞선 신규 조회에 막힐 수 있음 | 대상 전체의 유효 캐시를 먼저 확인해 임시 결과로 준비 |
| 묶음 전체가 끝나야 확정 결과를 화면에 반영 | 일부 조회가 성공해도 추가 문구가 아직 안 보임 | 일괄 표시는 유지하고 진행률·완료·중단 상태 안내 |
| 대상은 이미 현재 보드에 배치된 소 개체로 제한됨 | 전체 출품 목록을 무조건 조회하는 구조는 아님 | 이 범위를 유지하고 대상 교체 때 최신 표시 개체를 우선 처리 |

진단 당시 Debug 실행본의 최신 경매 스냅샷은 143건이고 그중 이력 캐시가 있는 대상은 25건이었다. 그 25건 중 기존 문구 생성 조건을 만족하는 대상은 6건이었다. 이는 저장 기록의 특정 시점 집계이며 현재 실행 중인 작업 수나 모든 API 요청의 성공 여부를 증명하는 수치는 아니다.

`IsAnimalProductsTraceability=Y`와 서비스 키가 있어도 모든 개체에 문구를 추가하지는 않는다. 기존 문구 생성기는 양수 이력과 직전 소유주를 구분할 수 있는 경우에만 문구를 만든다. 이번 작업에서는 이 조건을 변경하지 않는다.

## 2. 보존할 동작과 변경 범위

1. 경매 가격·진행·낙찰·유찰·일반 비고 갱신은 이력 조회를 기다리지 않는다.
2. 이력은 현재 보드에 배치된 소 구분 1·2·3, 유효한 15자리 이력번호만 대상으로 한다. 중복 슬롯의 같은 개체는 한 번만 조회한다. 전체 출품 목록 선조회는 추가하지 않는다.
3. 캐시 결과와 신규 조회 결과 모두 임시 보관한다. 묶음 전체 처리가 끝난 뒤 현재 개체에 이력 문구만 일괄 적용한다. 조회 시작 당시 가격·상태를 덮어쓰지 않는다.
4. 정상 빈 결과는 이전 문구를 지우고, 실패·중단은 기존에 확정한 정상 결과를 유지한다. 처음부터 결과가 없는 대상은 빈 표시를 유지한다.
5. 같은 대상 집합의 반복 수신은 작업을 다시 시작하지 않는다. 수동 이력 새로고침은 기존처럼 재조회 의도를 보존하고, 진행 중 동일 요청은 병합한다.
6. 날짜·대상 세대·종료 상태를 조회 결과 처리와 UI 반영 직전에 확인한다. 오래된 결과·진행률이 새 묶음을 덮어쓰지 못하게 한다.
7. 캐시의 저장 항목·당일 보존 및 삭제 정책, API 주소·파라미터·인증키, 문구·색상·스크롤은 유지한다. 원본 응답 전체나 개인정보를 새 진단 로그에 기록하지 않는다.

기존 2026-09-17 계획의 “순차 호출·최소 1초 유지, 병렬 호출 제외”는 당시 구현 범위다. 이번 계획에서는 조회 실행 구조와 요청 제어를 개선 대상으로 확장한다. 기존의 묶음 반영·소유권·세대 보호 기준은 계속 적용한다.

## 3. 제안 처리 흐름

```text
현재 보드 표시 대상 변경 / 수동 이력 새로고침
  → 대상 검증·중복 제거·묶음 세대 결정
  → 메모리·당일 SQLite 캐시 우선 확인
  → 유효 결과를 임시 보관 / 조회가 필요한 번호만 대기열 등록
  → 비동기 요청 제어: 시작 간격 + 최대 동시 요청 수
  → 개별 성공·실패·중단 집계 / 진행 상태 알림
  → 현재 묶음의 모든 대상 처리가 끝남
  → 세대·날짜 재검사 후 UI Dispatcher에서 일괄 반영
```

### 3.1 백그라운드 작업과 캐시

- `async/await` 기반의 수명 관리가 가능한 작업 흐름을 사용한다. 개체마다 Thread 또는 무제한 Task를 만들거나 동기 대기로 UI 스레드를 막지 않는다.
- 캐시 확인 단계가 앞선 HTTP 응답을 기다리지 않도록 분리한다. SQLite 접근은 기존 저장소의 직렬화와 소유권을 유지하며, 병렬 HTTP를 위해 DB 연결까지 무제한 생성하지 않는다.
- 자동 조회는 유효한 당일 캐시를 재사용한다. 전부 캐시 적중이면 HTTP 호출 없이 같은 묶음 반영 절차를 완료한다.
- 수동 새로고침은 캐시를 실패 시 대체값으로 확보한 뒤 요청한다. 캐시가 있다는 이유로 수동 재조회 의도를 무시하지 않는다.
- 이미 확정된 문구는 새 묶음 조회 중 유지한다. 새 캐시 적중분의 개별 선표시는 하지 않는다.

### 3.2 제한된 동시 조회와 호출량 제어

- 최대 동시 HTTP 요청 수와 요청 시작 간격을 별도로 제어한다. 동시 요청을 허용해도 시작 간격을 지키며 요청을 한꺼번에 발송하지 않는다.
- 제공기관의 초당·일일 허용량과 동시 요청 조건은 아직 확인하지 않았다. 구현 전 공식 규격 또는 해당 계정의 허용 조건을 확인한다. 현재의 1초 간격이 제공기관의 필수 규칙이라고 단정하지 않는다.
- 허용 조건 확인 전의 운영 기본값은 현재 동시 1건·최소 1초를 유지한다. 구조를 먼저 분리하고, 확인된 한도 안에서만 운영 값을 조정한다. 설정의 위치·기본값·변경 적용 시점은 구현 시 명시한다.
- 호출 횟수의 확인·증가·저장은 짧은 단일 임계 구역으로 보호한다. HTTP 응답을 기다리는 동안 이 잠금을 유지하지 않으며, 재시도도 실제 API 요청 횟수에 포함한다.
- 인증 오류·허용량 초과를 확인하면 신규 발송을 중단하고 미발송 항목을 중단 상태로 정리한다. 이미 발송된 요청의 결과에도 날짜·세대 검사를 적용한다.
- 재시도 대기는 동시 HTTP 슬롯을 점유하지 않는다. 요청별 제한시간·재시도 상한·재조회 유예는 보존하고, 대기 중인 다른 개체를 먼저 처리할 수 있게 한다.
- 동일 날짜·번호의 중복 요청 병합을 유지한다. 오래된 대상의 구독 취소가 최신 대상도 기다리는 공통 요청을 잘못 취소하지 않도록 구분한다.

### 3.3 표시 대상 우선 처리

- 우선순위는 최신 보드 표시 대상이다. 화면 위치 순으로 안정적인 처리 순서를 정하고, 이력번호 문자열 정렬에만 의존하지 않는다.
- 조회 중 대상이 바뀌면 이전 대상의 미발송 작업을 제거하고 최신 대상의 미조회 번호를 우선 등록한다. 겹치는 번호의 유효 결과·진행 중 요청은 재사용한다.
- 시간에 따라 모든 현재 대상이 처리되도록 한다. 반복 수신으로 같은 앞번호만 재조회하거나 뒤 대상이 계속 밀리지 않게 한다.
- 현재 프로그램의 보드 배치와 페이지 전환 의미를 구분한다. 이번에는 실제로 배치된 대상 집합을 유지하며, 페이지별로 숨겨진 개체를 새로 분류하는 기능까지 추가하지 않는다.
- 일괄 표시를 유지하므로 먼저 조회한 개체가 먼저 보이는 것은 아니다. 우선순위의 주효과는 대상 교체 후 불필요한 요청과 대기를 줄이는 것이다.

### 3.4 진행률과 결과 안내

- MainWindow의 별도 상태 영역에 현재 묶음 상태를 표시한다. 기존 경매·통신 안내를 덮어쓰거나 매 개체 완료마다 긴 로그를 누적하지 않는다.
- 안내 예: `이력 조회 25/143건 처리 · 캐시 20 · 조회 성공 5 · 실패 0`.
- 전체 수는 유효한 중복 제거 대상 수다. 처리 수에는 캐시 적중·조회 성공·실패·중단을 각각 한 번만 포함하며 재시도 횟수는 별도로 다룬다.
- 정상 빈 결과도 조회 성공이다. “조회 완료 건수”와 “문구가 있는 건수”를 구분해 `처리 완료 · 표시 문구 6건`처럼 안내한다.
- 신규 조회 결과가 임시 보관 중이면 `전체 처리 후 일괄 반영` 상태를 알린다. 실제 UI 반영이 완료된 뒤 최종 완료 상태로 전환한다.
- 진행 알림은 짧은 간격으로 합쳐 UI Dispatcher에 전달한다. 완료·오류·중단은 지연 없이 전달하고, 오래된 세대의 알림과 종료 후 콜백은 무시한다.
- 비활성, 대상 없음, 조회 중, 반영 대기, 완료, 일부 실패, 인증·허용량 중단을 구분한다. 서비스 키·개체번호·소유주 이름은 상태 문구에 넣지 않는다.

| 단계 | 작업 | 완료 기준 |

| 1. 기준·계약 확보 | 현재 캐시·중복 병합·수동 갱신·일괄 표시를 합성 데이터로 확인하고 API 허용 조건 조사 | 보존 동작과 호출 제어 기본값 명시 |

| 5. 진행 상태 표시 | 집계 모델과 MainWindow 상태 영역 연결, 알림 합치기 | 조회 중/완료/실패/문구 없음 구분 가능 |
| 6. 회귀·성능 검증 | 오프라인 비교 및 Debug·Release 빌드, 문서·WORKLOG 기록 | 기능·측정 결과와 미확인 운영 범위 구분 |

| `ViewModels/MainWindowViewModel.cs`, `Views/MainWindow.xaml` | 표시 대상 전달, 진행 상태 구독·해제와 UI 안내 |
| `Validation/ReferenceAdoptionChecks`, `Validation/OwnerHistoryChecks` | 호출 제어·캐시·묶음 표시·바인딩 회귀 검사 |
| 관련 계획·검증 README·`WORKLOG.md` | 구현 후 결과 기록. 계획 작성 단계에서는 WORKLOG 미갱신 |

새 패키지·DB 스키마 변경은 우선 필요하지 않은 것으로 본다. 구현 과정에서 직접 필요한 경우에만 목적을 확인해 최소 범위로 진행한다. 운영 XML의 기존 키·주소·색상 등 사용자 설정은 보존한다.

## 6. 검증 계획

- 가짜 HTTP 응답과 제어 가능한 시간·완료 신호로 최대 동시 요청 수, 요청 시작 간격, 재시도 중 슬롯 반환을 확인한다. 실제 운영 API로 부하 시험하지 않는다.
- 동시 완료에서도 호출량 증가가 누락되지 않고, 인증·허용량 중단 후 신규 발송이 멈추는지 검사한다.
- 전부 캐시 적중, 캐시/신규 혼합, 손상·만료 캐시, 정상 빈 응답, 실패 후 기존 문구 유지, 수동 재조회와 연타를 검사한다.
- 대상 A→B→A 전환, 겹치는 번호 재사용, 중복 슬롯, 날짜 변경, 종료, 오래된 Dispatcher 작업과 진행 알림을 검사한다.
- 먼저 끝난 이력이 가격 갱신·SV 수신 중에도 부분 노출되지 않으며, 전체 처리가 끝나면 현재 개체에만 적용되는지 확인한다.
- 진행률의 분모·분자·성공·실패·중단 합계, 문구 없음 안내, 이벤트 구독 해제와 반복 진입을 확인한다.
- 동일한 합성 입력·캐시 비율·응답 지연에서 기존 순차 방식과 개선 방식을 비교한다. 총 수집 시간, UI 반영 시간, 실제 요청 수, 최대 동시 수, UI 알림 수를 기록한다. 빠른 응답에서는 요청 시작 간격이 병목이므로 병렬화만으로 배수 개선을 약속하지 않는다.
- 구현 후 별도 TEMP 출력에 Debug·Release 빌드와 `ReferenceAdoptionChecks history`, `binding`, `updates`, `stage4`, `OwnerHistoryChecks --offline`, 필요 시 `--scroll-offline`을 수행한다. 복원 자산이 유효하면 `--no-restore`를 사용한다.
- 실제 운영 API 허용 조건, 운영 화면의 진행률 가독성 및 실제 전체 수집 시간은 별도 확인 항목으로 남긴다. 오프라인 통과를 운영 검증 완료로 표현하지 않는다.

## 8. 구현 결과

- `AnimalHistoryService.GetCachedNoteAsync`가 HTTP 요청과 독립적으로 캐시를 확인한다. `LookupAsync`는 캐시·성공·실패·중단을 구분하며, 실패 시 사용할 정상 문구와 이번 조회의 결과를 별도로 반환한다.
- API 발송 직전의 동시 수·간격·당일 예약 예산 처리를 직렬화했다. HTTP 응답과 재시도 대기는 이 잠금을 점유하지 않는다. 인증·허용량 오류의 당일 중단 기록과 기존 캐시 형식은 유지한다.
- `AnimalHistoryBatchCoordinator`는 백그라운드에서 캐시를 먼저 준비하고 최대 4개의 비동기 작업으로 대기열을 처리한다. 작업 수 4는 실제 HTTP 동시 4건을 뜻하지 않는다. HTTP는 서비스의 별도 제한을 따른다.
- 새로운 보드 대상은 화면 위치 순으로 등록한다. 제거된 대상은 더 이상 소비자가 없는 요청을 취소하고, 겹치는 대상의 진행 중 요청은 재사용한다. 다른 소비자가 같은 요청을 기다리면 취소하지 않는다.
- 진행 알림은 200ms 단위로 합치고 반영 대기·완료·실패 등 최종 상태는 즉시 전달한다. MainWindow의 기존 하단 70픽셀 영역 안에 상태줄을 추가하여 경매 신호와 로그를 보존했다. 개체별 완료마다 전체 패널을 다시 그리거나 로그를 추가하지 않는다.
- 문구는 여전히 전체 처리 완료 후 일괄 반영한다. 성공 빈 값과 실패를 구분하고, UI 반영 실패를 완료로 보고하지 않는다.
- 호출 제어 값은 `Domain/Settings/AnimalTraceSettings.cs`의 소스 설정이다. XML 파서는 기존 Y/서비스 키만 읽는다. `MaxConcurrentRequests=1`(구현 지원 범위 1~4), `RequestIntervalMs=1000`(최소 1000), `DailyLimit=0`을 유지했다. 공식 자료 검색과 로컬 가이드에서 동시 호출 허용 수치를 확인하지 못했으므로 운영 속도를 임의로 높이지 않았다.

### 검증 결과와 한계

- Debug·Release 빌드: 각각 오류 0개, 기존 경고 78개. 별도 TEMP 출력 사용.
- `ReferenceAdoptionChecks history`: 64개 통과. 캐시 우선 준비, 실제 요청 간격·동시 수·예산, 재시도 중 슬롯 반환, 중복 구독 취소, 대상 교체·겹침 재사용, 단계별 집계, 일괄 반영과 종료 보호를 확인했다.
- `binding`: 3,485개 통과. 실제 MainWindow의 상태 영역 XAML을 분리해 일반 Application에서 로드하고 생성자 없이 ViewModel의 진행 상태 처리·알림을 검사했다. 제품 Window 생성자와 서버는 시작하지 않았다.
- `updates`: 55개, `stage4`: 596개, `OwnerHistoryChecks --offline`: 55+25개, `--scroll-offline`: 18개 통과.
- 합성 비교: 캐시 1건·신규 3건, 가짜 응답 지연 1,500ms, 시작 간격 1,000ms에서 동일한 새 처리 경로의 동시 1건은 약 4,515ms, 동시 2건은 약 3,534ms였다. 양쪽 모두 요청 3회·표시 문구 4건으로 같았다. 이는 기존 실행 파일과의 전후 비교나 실제 API 속도 측정이 아니며 운영 설정은 여전히 동시 1건이다.
- 실제 서버·전광판·전체 앱 운영 실행·배포는 미수행이다. 정상 신규 조회의 최소 요청 간격은 유지되므로 모든 대상이 새 데이터인 경우 대기가 크게 줄었다고 단정하지 않는다. 상세 명령은 [WORKLOG](../../../WORKLOG.md)에 기록했다.
