## 1. 목적

로그인 응답의 `naBzplc`를 현재 인증된 사업장 코드의 기준으로 사용한다. 설정 파일에 적힌 사업장 코드와 실제 로그인 계정의 사업장이 달라 통신과 화면이 서로 다른 사업장을 사용하는 상황을 방지한다.

차수 API 요청, 응찰 서버 인증, 사업장별 화면 분기에 필요한 코드를 로그인 결과에서 얻는다. 현재 애플리케이션의 메모리·API 구조 안에서 완료할 수 있으며 DB를 전제로 하지 않는다.

### 포함 범위

- 로그인 응답의 사업장 코드 검증과 메모리 세션 반영
- 차수 API·응찰 서버 인증·파서·화면 선택에 같은 코드 적용
- 로그인 대기·실패·설정 불일치와 초기화 순서 처리
- 관련 빌드·통신·화면 회귀 검증 및 작업 기록

### 제외 범위

- SQLite 패키지 설치, 테이블·캐시·날짜별 DB 삭제 구현
- API 조회 주기 조정과 호출량 최적화
- 로그인 UI 신설, 계정 전환 UI 신설, 자동 토큰 갱신 기능 추가
- 사업장별 표시 규칙의 일괄 변경, 통신 라이브러리 교체, 폴더 개편

재인증 관련 항목은 이미 존재하거나 이번 초기화 흐름에서 발생 가능한 세션 교체의 안전성 기준이다. 새로운 재로그인 기능을 만드는 요구로 확대하지 않는다.

## 2. 확인된 사실과 근거

- 현재 인증 API에 한 차례 로그인하여 응답에 `naBzplc`, `success`, `accessToken`, `message`가 포함되는 것을 확인했다.
- 반환된 `naBzplc`는 검사 당시 XML의 사업장 코드와 일치했다. 한 계정에서 확인한 결과이며 모든 계정·환경의 응답 형식을 보장하지 않는다.
- `Services/ServerConn.cs`의 `IssueToken()`은 `success`와 `accessToken`만 읽고 `naBzplc`는 무시한다.
- `Models/XMLParser/UserXmlParser.cs`는 XML의 `Auction/AuctionHouseCode`를 읽는다.
- `ServerConn.PostQcn()`은 이 설정 코드를 `naBzplc` 요청 값으로 사용한다.
- `ServerConn.NettyComm()`과 `NetProto/models/ConnectionInfo.cs`는 이 코드를 응찰 서버 인증 패킷에 사용한다.
- `XmlParserCont.XmlPaserResult()`는 호출마다 설정을 새로 파싱한다. 서버 서비스와 MainWindowViewModel이 같은 UserInfo 객체를 공유한다고 가정할 수 없다.
- `Services/DisplaySelect.cs`는 생성 시 `_nhCode`에 사업장 코드를 저장한다. 로그인 이후 다른 UserInfo 객체만 변경하면 기존 화면 선택은 갱신되지 않는다.
- `ServerGetData`는 생성자에서 초기화 작업을 비동기로 시작한다. 화면 구독·준비보다 인증이나 데이터 수신이 빨라지는 순서도 고려해야 한다.

인증 응답 원문, 계정, 토큰, 실제 운영 코드·접속 값은 문서에 기록하지 않는다.

## 3. 사업장 코드 결정 규칙

| 상황 | 처리 |
|---|---|
| 로그인 성공 + 유효한 토큰 + 유효한 naBzplc | 토큰과 사업장 코드를 하나의 인증 결과로 확정 |
| 로그인 실패 또는 토큰 누락 | 인증 완료로 처리하지 않음 |
| naBzplc 누락·null·빈 값·잘못된 형식 | 사업장 미확정으로 처리하고 차수 조회·응찰 인증·사업장 데이터 표시를 시작하지 않음 |
| XML 코드와 로그인 코드 일치 | 로그인 코드 사용 |
| XML 코드와 로그인 코드 불일치 | 로그인 코드 사용, 불일치 사실만 기록. XML 파일은 자동 수정하지 않음 |
| XML 코드가 없거나 비어 있음 | 정상 로그인 응답에서 코드가 확보되면 진행 |
| 재로그인으로 사업장 또는 계정 변경 | 이전 세션의 조회·연결·화면 데이터를 정리한 후 새 세션으로 전환 |

`naBzplc`는 숫자 문자열 식별자로 취급한다. 정수로 변환해 선행 0을 없애거나 특정 사업장 코드로 고정하지 않는다. 앞뒤 공백을 제거한 비어 있지 않은 ASCII 숫자 문자열을 기본 검증하고, 길이를 13자리로 고정하려면 서버 계약을 추가 확인한다. 숫자형 JSON 응답은 계약 확인 없이 문자열 응답과 같다고 가정하지 않는다.

토큰 내부를 임의 디코딩한 값을 별도 대체 출처로 사용하지 않는다. 정상 인증 응답의 명시적 `naBzplc`를 사용하고, 실패 시 XML 코드로 조용히 대체하지 않는다.

## 4. 로그인 결과와 세션 모델

### URL 템플릿과 설정 비교 규칙 (구현 확정)

- XML의 `Auction/AuctionHouseCode`는 예상 사업장 비교용이다. 로그인 응답과 같으면 알림 없이 진행하고, 다르면 한 번 알린 뒤 로그인 응답 코드를 사용한다. XML 값이 없으면 비교를 생략한다.
- `CurrentInfo/Address`와 `AddressEPD`의 고정 사업장 숫자는 `{AuctionHouseCode}`로 변경한다.
- 현황 URL 형식: `/api/v1/auction/{AuctionHouseCode}/entry/board?date=`.
- EPD URL 형식: `/api/v1/epd/info/{AuctionHouseCode}/date/`.
- 실제 요청 주소의 자리 표시자는 검증된 로그인 응답의 `naBzplc`로 치환한다. XML 예상 코드로 URL을 만들지 않는다.
- 기존 숫자가 들어 있는 같은 형식의 URL도 해당 경로 구간만 로그인 코드로 교체해 호환성을 유지한다. URL 안의 숫자를 전역 치환하지 않는다.
- EPD 주소는 현재 실행되는 API 소비처가 없으므로 템플릿 해석만 준비하고 새 EPD 호출을 추가하지 않는다.
- 로그인 코드가 누락되면 URL 생성과 경매 연결·조회를 시작하지 않는다.

### 로그인 결과

`LoginResult` 전용 모델에 최소한 다음을 담는다.

- `AccessToken`: 메모리에서만 사용
- `AuctionHouseCode`: 검증된 로그인 응답 코드

실패는 성공 객체와 구분되는 반환 규칙으로 표현한다. 토큰만 정상이고 사업장 코드 검증이 실패한 경우 부분 성공 상태를 공유하지 않는다. 모델의 자동 문자열 출력이나 직렬화로 토큰을 로그에 남기지 않는다.

### 인증 세션

현재 앱은 초기 로그인 한 번만 수행한다. 첫 구현은 ServerConn이 보유하는 불변 LoginResult를 인증 기준으로 사용하고, 로그인 완료 시 같은 실행용 UserInfo를 서버와 화면에 전달한다. 별도 세션 서비스나 계정 전환 UI는 추가하지 않는다. 초기화는 한 번만 시작되도록 보호하고, 로그인·화면 준비 완료 전에 조회 루프를 시작하지 않는다.

- 토큰과 사업장 코드의 읽기·교체는 동일 세션 스냅샷 기준으로 한다.
- 향후 재로그인·로그아웃 기능을 추가하면 세대 전환과 이전 응답 무효화를 별도 검증한다. 현재 작업에서 새 재로그인 경로를 만들지 않는다.
- 세션은 메모리에만 보관하고 인증 토큰을 파일·로그·WORKLOG에 저장하지 않는다.
- 화면이 준비된 뒤 초기화를 시작하고 로그인 완료 콜백을 기다린다. 구독 전 로그인 알림 유실을 지연 시간에 의존해 해결하지 않는다.

## 5. 초기화 및 화면 반영 흐름

1. XML에서 계정·서버 주소·포트·채널·전광판 배치·색상 설정을 읽는다.
2. 기본 창·패널 자리·인증 상태 안내를 준비한다. 사업장 코드에 의존하는 화면 선택과 경매 데이터 표시는 아직 시작하지 않는다.
3. 화면 메시지 구독과 초기화가 준비된 뒤 로그인 작업을 시작하거나, 이미 완료된 로그인 결과를 현재 상태 조회로 받는다.
4. 인증 API의 토큰과 naBzplc를 모두 검증한 뒤 세션을 확정한다.
5. Dispatcher에서 화면용 UserInfo의 실행 중 사업장 코드를 로그인 코드로 반영하고 DisplaySelect를 초기화한다. XML 원문은 변경하지 않는다.
6. 화면 준비 완료 후 같은 인증 세션으로 응찰 서버 연결과 차수·현황 조회를 시작한다.
7. API·Netty 결과와 화면 갱신에 같은 로그인 결과의 사업장 코드를 적용한다.

색상·해상도 등 사업장 코드와 무관한 설정 로드는 기존 흐름을 유지할 수 있다. 다만 사업장별 화면 구성과 `_nhCode`는 로그인 결과 확정 뒤 사용해야 한다.

향후 재로그인 기능을 추가하여 재인증으로 사업장이 바뀌면 기존 DisplaySelect의 페이지 동기화·타이머·이벤트를 해제하고 새 설정으로 구성한다. UI를 백그라운드에서 직접 갱신하지 않는다. 로그인 이전과 전환 중에는 기존 사업장의 낙찰·진행 화면을 새 사업장의 결과처럼 표시하지 않는다.

기존 생성자에서 시작하는 비동기 초기화와 중복 Start 호출을 점검하고, 화면 준비와 데이터 조회 시작의 순서를 한 번만 확정하도록 구성한다. 단순히 대기 시간을 추가하는 방식으로 경쟁 상태를 해결하지 않는다.

## 6. 사용처별 적용 범위

| 사용처 | 변경 방향 |
|---|---|
| 차수 API | 인증 세션의 코드를 요청 naBzplc로 사용 |
| 응찰 서버 인증 | 토큰과 코드가 같은 인증 응답에서 나온 값인지 보장 |
| AnimalParseData | 현재 세션 코드가 반영된 UserInfo로 사업장 분기 수행 |
| DisplaySelect | 로그인 확정 후 코드 적용, 기존 `_nhCode` 잔존 방지 |
| 기타 사업장 분기 | AuctionHouseCode 및 복사된 필드의 읽기 위치를 전수 검색해 같은 세션인지 확인 |

사업장별 맞춤 화면을 선택하기 위해 코드에 존재하는 사업장 상수는 이번 작업에서 일괄 삭제하지 않는다. 현재 사업장을 정하는 설정값과 특정 사업장의 표시 규칙을 식별하는 상수는 역할이 다르다.

서버 주소·포트·채널·우선순위는 로그인 응답에서 제공 여부가 확인되지 않았다. 이번 작업은 이를 자동 발견하거나 다른 환경으로 전환하는 기능을 포함하지 않는다.

## 7. 예상 변경 파일

| 파일 | 목적 |
|---|---|
| `Models/Structures/LoginResult.cs` 신규 | 검증된 로그인 결과 전달 |
| `Services/AuctionApiAddressResolver.cs` 신규 | 인증된 코드로 현황·EPD URL 템플릿 해석 |
| `Services/ServerConn.cs` | 로그인 응답 파싱, 성공 조건 확장, 세션 기준 차수·응찰 인증 |
| `Services/ServerGetData.cs` | 로그인 결과 적용, 화면 준비 이후 조회 시작, 중복 초기화 차단 |
| `ViewModels/MainWindowViewModel.cs` | 로그인 대기·완료 처리와 화면 초기화 순서 |
| `Config/users.XML` | 현황·EPD URL의 고정 코드를 자리 표시자로 변경 |
| `WORKLOG.md` | 실제 구현·검증 후 결과 기록 |

UserInfo의 기존 AuctionHouseCode 속성과 XML 파서의 읽기 기능은 호환성을 위해 우선 유지한다. XML의 코드는 비교용 기존 설정으로만 취급하며 로그인 코드가 확정된 실행 흐름의 기준으로 사용하지 않는다. 추가 파일 수정이 필요하면 목적과 범위를 보고한다.

기존 사업장별 UI·패키지 버전·폴더 구조·API 조회 주기·SQLite 구현은 이번 작업에서 함께 변경하지 않는다.

DisplaySelect 자체의 사업장 분기 코드는 유지하고, MainWindowViewModel에서 로그인 코드가 반영된 실행용 UserInfo로 처음 생성한다. 별도 내부 메시지나 App 서비스 등록 변경 없이 명시적인 초기화 콜백으로 연결한다.

## 8. 위험과 대응

- 서버용 UserInfo만 바꾸면 화면은 XML의 다른 코드로 동작할 수 있다. 모든 사용처에 세션 반영 여부를 검증한다.
- 로그인보다 화면 준비가 늦으면 첫 데이터 메시지가 유실될 수 있다. 명시적인 준비 상태와 시작 순서를 사용한다.
- 향후 계정 전환 기능 추가 시 이전 API 응답을 세대 검사와 취소·연결 정리로 차단해야 한다. 현재는 초기 로그인만 지원한다.
- 나중에 들어온 로그인 실패 때문에 이전 유효 토큰만 남지 않도록 성공·실패·전환 상태를 구분한다.
- 코드 누락 응답을 허용하면 다른 사업장 조회로 이어질 수 있다. 실패 이유를 사용자에게 알리고 사업장 의존 동작을 시작하지 않는다.
- 사업장별 화면 규칙의 상수를 무작정 제거하면 맞춤 표시가 사라질 수 있다. 상수 제거는 범위에 포함하지 않는다.
- 로그인에 필요한 응답 필드 확인을 위해 토큰·응답 원문을 로그로 출력하지 않는다.

## 9. 검증 계획
