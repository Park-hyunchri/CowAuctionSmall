# 축산물 이력 개체별 즉시 반영 변경 계획

> 문서 상태: **완료·현재 반영 기준** · 정리일: 2026-10-01
> 캐시·API 결과의 단건 적용, 신규 등록 대상 유지와 페이지 보존 구현 결과는 본문 10절에 있다.
> 현재 동작: [기능 문서](../../기능/README.md) · [전체 목차](../../README.md) · [작업 기록](../../../WORKLOG.md)

- 작성일: 2026-09-29
- 상태: 구현·오프라인 검증 완료 / 운영 통신·실제 전광판 확인 미수행
- 실행 승인: 사용자의 “필요한 에이젼트 수 사용 및 수정 진행하자” 요청에 따라 총 3명으로 구현·통합 검증했다.
- 요청: 캐시·API·초기 조회·당일 추가 등록에 서로 다른 일괄/개별 적용 방식을 두지 않고, 개체별로 빠르게 반영하도록 통일한다.
- 범위: 이력 조회 결과의 전달과 화면 반영 방식. 경매 목록 API·SV의 일반 경매 정보 갱신 정책은 유지한다.
- 이전 계획과의 관계: [묶음 표시 계획](../보관/축산물이력_묶음표시_변경계획_2026-09-17.md), [백그라운드 조회 계획](축산물이력_백그라운드조회_개선계획_2026-09-23.md)의 전체 완료 후 일괄 표시 규칙과 현재 500ms 묶음 반영을 이 계획으로 대체한다. 기존 문서는 당시 작업 기록으로 보존한다.

## 1. 결정할 동작

**한 개체의 결과가 준비되면 해당 개체의 현재 화면에 바로 반영한다. 결과의 출처나 전체 대상 수에 따라 반영 방식을 바꾸지 않는다.**

| 상황 | 반영 규칙 |
| --- | --- |
| 메모리 캐시 적중 | 해당 개체 결과를 즉시 UI에 전달 |
| SQLite 당일 캐시 적중 | 읽고 검증한 해당 개체 결과를 즉시 UI에 전달 |
| 캐시가 없어 API 조회 | 정상 결과의 기존 캐시 저장 처리를 거쳐 해당 개체 결과를 즉시 UI에 전달 |
| 초기 실행으로 다수 조회 | 준비된 개체부터 같은 단건 반영 경로 사용 |
| 당일 한두 마리 추가 등록 | 새 대상만 조회 작업에 추가하고 같은 단건 반영 경로 사용 |
| 이력 새로고침 | 기존 표시를 유지하면서 개체별 새 결과를 같은 경로로 반영 |

- 순서는 **결과가 준비된 순서**다. 출품 번호 순서가 맞을 때까지 완료된 결과를 보류하지 않는다.
- 즉시는 별도의 500ms 타이머나 전체 완료 조건 없이 UI Dispatcher에 전달한다는 뜻이다. 네트워크·캐시 접근 시간과 UI 실행 대기는 존재한다.
- 현재 요청 시작 간격 250ms와 동시 HTTP 기본 1개는 유지한다. 화면을 빨리 반영하기 위해 호출 제한을 없애지 않는다.
- 설정 항목이 없을 때의 1000ms 기본값, 허용량 초과·인증 오류 중단, 재시도·중복 요청 억제는 유지한다.

## 2. 현재 구조에서 바꿀 부분

| 현재 코드 | 변경 방향 |
| --- | --- |
| `AnimalHistoryBatchCoordinator`의 전체 `staged` 사전 | 화면 게시를 위해 전체 결과를 복제·축적하는 용도 제거 |
| 캐시 준비 종료 후 묶음 게시 | 캐시 한 건이 준비될 때마다 공통 단건 게시 |
| `FlushUpdatesAsync`의 500ms `PeriodicTimer`와 `dirty` | 제거 |
| `Publication.Results`, `_pendingPublication`의 전체 결과 스냅샷 | 개체번호·조회 결과·유효성 정보 한 건을 전달하는 계약으로 변경 |
| 전체 결과를 바꾸는 `Commit`과 마지막 전체 게시 | 개체별 반영과 조회 완료 통계를 분리. 마지막 개체도 동일한 단건 경로 사용 |
| 인자 없는 `_onApplied` → `ApplyHistoryBatch()` | 어떤 개체가 바뀌었는지 전달하는 콜백으로 변경 |
| `ApplyHistoryBatch()`의 모든 `_visibleCows` 복제·`UpdatePanels` 호출 | 해당 이력번호가 현재 표시된 슬롯만 찾아 갱신 |

이미 화면에서 사용할 수 있는 결과 조회 기능은 필요하다. `TryGetHistory`에 해당하는 개체별 최신 결과 보관은 유지할 수 있으나, 이를 전체 완료를 기다리는 임시 저장소로 사용하지 않는다. 서비스의 메모리 캐시와 화면의 현재 적용 상태도 책임을 구분한다.

일괄/개별 적용을 선택하는 옵션이나 두 가지 구현 경로를 추가하지 않는다. 역할 변경에 맞춰 `AnimalHistoryBatchCoordinator`는 `AnimalHistoryCoordinator`, `ApplyHistoryBatch`는 `ApplyHistoryResult`로 정리하고 직접 참조를 함께 변경한다. 진행률 타입 등의 관련 명칭도 실제 역할에 필요한 범위에서만 정리한다.

## 3. 공통 처리 흐름과 책임

```text
경매 목록 API 또는 SV 수신
  → 현재 보드에 표시되는 유효 개체번호의 증감 확인
  → 새 대상은 캐시 확인 / 제외 대상은 구독 해제

개체별 조회 서비스
  → 메모리 캐시 확인
  → 없으면 SQLite 당일 캐시 확인
  → 없으면 제한된 API 요청 → 기존 정책에 따라 SQLite·메모리 저장
  → 개체번호 + HistoryLookupResult + 유효성 정보 전달

공통 단건 반영
  → UI 실행 시 날짜·대상·요청의 유효성 재확인
  → 현재 같은 개체를 표시하는 슬롯 확인
  → 비고·소유주·주소의 실제 변경 여부 확인
  → 해당 슬롯의 ViewModel만 갱신
```

- `AnimalHistoryService`: 캐시 판독, API 호출 제한, SQLite 저장, 결과 반환을 담당한다. 원본 XML 전체 저장이나 캐시 스키마 변경은 추가하지 않는다.
- 조정자: 대상 증감, 진행 중 요청 공유, 단건 결과 전달, 진행률 집계를 담당한다. 느린 HTTP 응답 때문에 다른 개체의 캐시 확인이 멈추지 않도록 기존 캐시 확인과 HTTP 대기 분리는 유지한다. **결과 반영 경로는 하나**로 통일한다.
- ViewModel: UI 스레드에서 현재 표시 대상과 이력번호를 재확인하고, 관련 개체만 갱신한다. 조회 시작 당시의 경매품 전체를 화면에 다시 대입하지 않는다.
- View/XAML: 기존 바인딩을 사용한다. code-behind에 조회 로직을 추가하거나 화면을 재생성하지 않는다.
- 전체 대상의 조회 종료를 기다리는 작업은 완료 통계·종료 정리에만 사용할 수 있다. 결과 표시의 선행 조건으로 사용하지 않는다.

## 4. 당일 추가 등록과 반복 수신

`/auction/{AuctionHouseCode}/entry/board?date=...`의 다음 정상 응답이나 SV로 신규 경매품이 들어오면 기존 화면 갱신 경로에서 조회 대상 증감을 계산한다.

1. 기존 대상의 정상 표시와 진행 중인 조회는 유지한다.
2. 새로 추가된 유효 개체번호만 캐시 확인·조회 작업에 넣는다.
3. 같은 개체가 여러 슬롯에 있으면 조회는 공유하고, 결과는 그 개체가 현재 표시된 모든 슬롯에 반영한다.
4. 반복된 동일 목록·SV·가격 변경만으로 같은 개체의 이력 API를 다시 호출하지 않는다.
5. 대상에서 제외된 개체는 해당 구독을 취소한다. 다른 사용자가 공유 중인 요청까지 취소하지 않는다.
6. 같은 슬롯에 다른 개체가 들어오면 이전 개체의 늦은 결과를 적용하지 않는다.

신규 대상 하나가 추가되었다는 이유로 남아 있는 모든 대상의 요청과 게시를 무효화하지 않는다. 대상 추가·삭제와 날짜/설정 전환을 구분하고, 개체별 요청 식별자와 현재 대상 여부로 늦은 응답을 검사한다. A→B→A 교체에서도 오래된 A 요청과 새 A 요청을 구분한다.

조회 범위는 현재와 같이 보드에 배정된 소 구분 1·2·3 및 유효한 15자리 이력번호다. 화면 밖의 모든 출품 선조회나 경매 목록 API의 폴링 주기 변경은 포함하지 않는다.

## 5. UI 갱신과 진행률

- 단건 반영 콜백은 `TraceNumber`, `HistoryLookupResult`, 날짜/요청 식별 정보를 받는다. 특정 슬롯 번호만 믿고 반영하지 않는다.
- 현재 슬롯의 최신 경매품을 기준으로 `NoteChangeOwner`, `HistoryOwner`를 반영한다. 가격·진행·낙찰·유찰 상태와 원래 `Note`를 덮어쓰지 않는다.
- 같은 비고·소유주·주소면 불필요한 PropertyChanged·렌더링을 생략한다. 성공했으나 실제 이력이 비어 있는 결과는 이전 이력 표시를 지우는 정상 결과로 구분한다.
- `ShowOwnerChangeNote=N`이면 이력 비고는 계속 숨기되 소유주·주소와 3페이지 정보는 갱신한다.
- 결과 한 건마다 전체 경매품을 복제하거나 전체 패널에 `UpdatePanels`를 호출하지 않는다. 전체 대상 재계산도 이력 표시 콜백의 부수 효과로 반복하지 않는다.
- UI 처리가 느리면 생산자가 비동기로 반영 완료를 기다리는 등 대기량을 제한한다. UI 스레드를 동기 대기시키거나, 타이머에 결과를 다시 모아 일괄 적용하는 방식으로 돌아가지 않는다. 잠금 안에서 UI 완료를 기다리지 않는다.
- 캐시·성공·실패·중단과 소유주 변경 비고 건수는 유지한다. 상태줄의 잦은 문구 알림 제한은 유지할 수 있으나, 이를 개체 결과 반영 지연에 사용하지 않는다.
- 마지막 조회가 끝났다는 이유로 전체 화면을 한 번 더 갱신하지 않는다. 유효한 UI 게시가 처리된 후 완료 상태로 전환한다. UI 반영 실패를 조회 성공과 혼동하지 않는다.

## 6. SQLite와 오류 처리

- SQLite 개체별 당일 캐시와 메모리 캐시를 계속 재사용한다. DB 삭제·초기화·원본 응답 추가 저장·보존 기간 변경은 하지 않는다.
- 이번 단순화는 **일괄 게시용 중간 상태 제거**이며 캐시 저장량 감소를 의미하지 않는다.
- 새 API 결과의 저장 실패를 SQLite 저장 성공으로 보고하지 않는다. 기존 저장 실패·조회 중단 정책을 보존하며, UI 반영 변경이 저장 오류를 숨기지 않도록 검증한다.
- 실패와 정상 빈 결과를 구분한다. 조회 실패 시 기존 정상 결과를 보존하고, 실패한 개체 때문에 다른 완료 결과를 기다리게 하지 않는다.
- 새로고침 중 캐시를 먼저 보여 주더라도 해당 개체의 최신 응답을 오래된 캐시 게시가 덮어쓰지 않도록 순서를 보호한다.
- 날짜 변경, 초기화, 종료, API 사용 비활성화 시 이전 결과의 게시와 상태 알림을 차단한다.
- 정상 빈 이력의 주기적 재조회, 당일 소유주 변경 자동 감지, 신규 대상의 별도 우선순위 정책은 이번 범위에 추가하지 않는다. 기존 수동 새로고침·성공/실패 쿨다운을 유지한다.

## 7. 구현 단계와 대상 파일

| 단계 | 주요 대상 | 작업 및 완료 조건 |
| --- | --- | --- |
| 1. 단건 전달 계약 | `Presentation/Display/AnimalHistoryBatchCoordinator.cs`, `Domain/AnimalHistory/HistoryLookupResult.cs` 및 필요한 단건 전달 타입 | 단건 콜백·개체별 유효성·작업 종료 의미 정의. 기존 결과 모델은 재사용하고 불필요한 DTO 중복은 피함 |
| 2. 개체별 게시 통일 | 조정자, `Presentation/Display/HistoryBatchProgress.cs` | 캐시/API 모두 같은 즉시 게시 경로 사용. staged 전체 복사·500ms 타이머·최종 전체 Commit 제거. 진행률은 별도 집계 |
| 3. 해당 화면만 갱신 | `ViewModels/MainWindowViewModel.cs`, 필요 시 `AuctionItemDisplayViewModel.cs`의 기존 갱신 진입점 | 현재 표시 개체와 슬롯을 확인해 관련 ViewModel만 갱신. 전체 목록 복제·대상 재등록 루프 제거 |
| 4. 검증과 기록 | `Validation/ReferenceAdoptionChecks/HistoryBatchChecks.cs`, `HistoryBackgroundChecks.cs`, `HistoryProgressUiChecks.cs`, `FarmAddressChecks.cs`, `HistoryNoteSettingsChecks.cs` 및 직접 참조 | 묶음 게시 전제를 단건 반영 검증으로 교체하고 회귀 검증. 구현 완료 후 `WORKLOG.md` 기록 |

파일 이동·명칭 변경은 이력 조정자와 그 직접 참조에 한정한다. 기존 사용자 변경을 보존하고 이력과 관계없는 경매 처리·XAML·설정 분기는 수정하지 않는다. 현재 250ms 설정과 SQLite 정책은 재사용하므로 새 패키지나 설정 옵션은 필요하지 않다.

## 8. 검증 시나리오와 완료 기준

| 검증 | 기대 결과 |
| --- | --- |
| 메모리/SQLite 적중과 느린 API 혼합 | 적중 개체가 먼저 표시되고, 느린 응답을 기다리지 않음 |
| API 3건 중 1건만 완료 | 그 개체가 UI에 반영됨. 500ms 경과나 나머지 완료가 필요하지 않음 |
| 여러 응답의 완료 순서가 다름 | 준비된 결과부터 적용. 앞 개체 재시도가 뒤 결과를 막지 않음 |
| 50마리 표시 중 목록 API로 1마리 추가 | 정상 기존 결과 재사용, 새 개체 조회·해당 화면 반영 |
| 조회 도중 신규 등록·중복 SV·동일 목록 반복 | 남은 기존 요청 공유, 불필요한 재호출·전체 화면 재반영 없음 |
| 개체의 여러 슬롯 표시·동일 슬롯 개체 교체 | 모든 현재 해당 슬롯 갱신, 이전 개체 결과 차단 |
| 캐시 게시 대기 중 수동 새로고침·반복 클릭 | 최신 결과가 오래된 게시로 되돌아가지 않으며 중복 요청 없음 |
| 정상 빈 이력·실패·캐시 저장 실패 | 빈 성공은 이전 이력 제거, 실패는 정상 표시 보존, 저장 실패 오인 없음 |
| 날짜 변경·A→B→A·초기화·종료·사용 비활성화 | 유효하지 않은 결과와 지연된 UI 게시 차단 |
| 비고 숨김·3페이지·진행/낙찰/유찰 | 표시 옵션 보존, 이름·주소 반영, 가격·상태 유지 |
| 501개 캐시 적중·UI 지연 | 한 개체당 전체 501개 복제/갱신 없음. UI 대기량 제한·입력 응답성 확인 |
| 진행률·UI 반영 예외 | 처리 건수 중복 집계 없음, UI 적용 대기/실패를 완료로 표시하지 않음 |

타이밍 검증은 가능하면 가짜 응답과 제어 가능한 UI 대기로 수행한다. 캐시 501건의 콜백 개수만 측정하지 않고 복제 대상 수·실제 변경 슬롯 수·할당량·UI 대기량을 함께 비교한다. 계측 없이 성능 개선 비율을 보장하지 않는다.

구현 시에는 Visual Studio와의 생성 파일 경합을 피하도록 임시 `--artifacts-path`에서 복원·빌드하고, 이력 관련 검증 후 전체 `ReferenceAdoptionChecks`를 실행한다. 실제 전광판의 스크롤·페이지 회전·신규 등록 반영은 수동 확인 항목으로 구분한다.

완료 기준은 캐시/API 모두 단건 반영, 500ms 묶음과 마지막 전체 재반영 제거, 관련 슬롯만 변경, 기존 취소·중복 억제·SQLite 정책 보존, 의미 있는 회귀 검증 통과다.

## 9. 계획 작성 당시의 범위

최초 요청에서는 계획 문서만 추가했다. 당시 소스·운영 XML·SQLite·기존 계획 문서·WORKLOG 변경과 빌드·앱 실행·외부 API 호출은 수행하지 않았다. 이후 실행 승인에 따른 구현 결과는 아래와 같다.

## 10. 구현 결과와 검증

- `AnimalHistoryCoordinator`와 `HistoryItemUpdate`로 단건 전달을 통일했다. 캐시 준비와 API 작업은 분리하고, 결과는 같은 UI 게시 경로를 사용한다. 500ms 타이머·전체 staged 복사·마지막 전체 Commit을 제거했다.
- 대상 추가는 기존 조회를 보존한다. 개체별 RequestId·현재 대상·캐시 날짜를 확인하고 제외·초기화·종료 이후의 응답을 거절한다. 수동 새로고침 병합과 기존 요청 공유를 유지했다.
- 게시 생산자가 UI 적용을 비동기로 기다린다. 전역 게시 슬롯은 worker 수+1로 제한하며, 취소된 게시도 실제 UI 콜백이 끝나기 전에는 슬롯을 반환하지 않는다. 상태줄 알림도 최대 1개만 대기한다.
- `MainWindowViewModel.ApplyHistoryResult`는 해당 이력번호의 현재 슬롯만 복제·갱신한다. 전체 `UpdatePanels` 호출과 이력 반영에 따른 대상 재등록을 제거했다. 동일 이력은 복제를 생략한다.
- `DisplaySelect.UpdateHistoryDisplay`를 추가했다. 기존 일반 갱신 경로는 진행 화면을 1페이지로 선택하고 경매 진행 제어를 실행할 수 있어, 이력 전용 경로에서 현재 페이지·스크롤·경매 상태를 보존하도록 했다.
- SQLite 스키마·저장 정책, API 서비스, 운영 XML과 현재 요청 간격은 변경하지 않았다. 진행률 타입의 기존 이름은 직접 기능 변경에 불필요한 참조 변경을 줄이기 위해 유지했다.
- 분리 출력 경로 `%TEMP%/CowAuction-HistoryIndividual-_5sz49ng/artifacts`의 제품·검증 프로젝트 빌드: 경고 0개·오류 0개. 전체 `ReferenceAdoptionChecks all`: **5,547개 통과**.
- 검증에 신규 추가만 조회, 개별 캐시/API 반영, UI 지연·대상 반복 교체의 게시 상한, 저장 실패 정책, 다중 슬롯, 정상 빈 결과/실패, 비고 숨김, 가격·낙찰/유찰 유지, 진행/대기 2·3페이지 및 스크롤 유지가 포함된다.
- 501건 캐시의 합성 테스트에서는 단건 콜백 501회와 추가 1건의 단독 조회·반영을 확인했다. 대기 콜백 최대 2개를 관찰했다. 이 테스트의 소요 시간은 가짜 UI를 1ms 요청 간격으로 폴링하는 운영체제 타이머 대기를 포함하므로 실제 화면 성능 수치로 해석하지 않는다.
