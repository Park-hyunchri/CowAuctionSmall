## 1. 목적과 적용 원칙

현재 WPF와 MVVM 구조를 유지하면서 경매 상태 판단, 통신 메시지 처리, 보드 진단의 명확성을 높인다. 기존 사업장별 화면과 여러 해상도, 캐시, 소유주 이력, 로그인 사업장 적용, PC 간 페이지 동기화를 보존한다.

참고 프로젝트의 개념을 현재 구조에 맞게 적용한다. MAUI·Blazor 전환, 폴더 일괄 재배치, 패키지 일괄 업데이트는 수행하지 않는다. 참고 프로젝트가 현재보다 기능이나 성능이 우수하다고 전제하지 않는다.

**GIF는 절대로 지원하지 않는다.** GIF 자동 탐색, 직접 지정에 따른 로딩, 애니메이션 표시 경로와 전용 의존성을 정리한다. 비고·낙찰자 이름의 텍스트 스크롤은 GIF와 별개이며 유지한다. 기존 사용자 이미지 파일은 삭제하지 않는다.

## 2. 조사 결과와 기준선

| 항목 | 현재 프로젝트에서 확인한 내용 | 적용 방향 |
|---|---|---|
| 상태 판단 | `DisplaySelect.FindPanel`이 상태 문자열을 `int.Parse`하고 11·22·23을 분기하며 나머지는 로고로 표시 | 파싱과 업무 상태 판단을 UI 생성에서 분리 |
| 수신 이벤트 | `NettyAsyncMsgProcess`, `ServerGetData`에 `async void` 처리 존재 | 이벤트 순서·예외·종료를 추적 가능한 Task 기반 처리로 개선 |
| 전달 데이터 | `DataChangedMessage`가 변경 가능한 목록을 보관하고 일부 송신부는 전송 직후 목록을 비움 | 비동기화 전에 메시지 소유권과 복제 범위를 확정 |
| 화면 갱신 | ViewModel에서 Clone, DisplaySelect에서 UpdateSignature와 뷰 재사용 적용 | 기존 최적화를 유지하고 남은 전체 순회·복제를 측정 후 개선 |
| 보드 | 설정된 슬롯에만 표시하고 대응하지 않는 데이터를 건너뜀 | 표시·제외·로고 수와 유효하지 않은 데이터 수를 구분해 진단 |
| 페이지 | master/sub 통신과 고정·해제·fallback 구현 존재 | 상태 관리를 정리하되 PC 간 동기화 유지 |
| 공통 화면 | 비고 호스트·NoteText·낙찰자 이름 스크롤 등 공통 구현 존재 | 새 공통 체계를 중복 도입하지 않고 기존 구현 활용 |
| GIF 잔여 코드 | `LogoManager`의 GIF 우선 탐색, `ImageCacheHelper`의 GIF 로딩, `WpfAnimatedGif` 참조 | 사용자 요구에 따라 제거 대상으로 지정 |

현재 작업 디렉터리에는 다수의 미커밋 변경과 미추적 구현·문서가 있다. 이들을 사용자 변경으로 보존한다. 구현 시작 시 최신 status와 관련 diff를 다시 확인하며 HEAD 버전을 기준으로 덮어쓰지 않는다.

참고 프로젝트의 주의점:

- Channel 포화 시 `WriteAsync(...).GetAwaiter().GetResult()`를 사용하는 부분이 있다. 호출 스레드를 막는 방식을 그대로 이식하지 않는다.
- 메시지의 `ToArray()`는 내부 `gValues`까지 복제하지 않는다. 읽기 전용 컬렉션과 불변 데이터는 구별한다.
- `AuctionStateResolver`는 `IsRunning`을 결과 코드보다 먼저 평가한다. 상충하는 데이터의 우선순위는 현재 경매 처리 규칙을 기준으로 정한다.
- 화면은 128×128 중심이다. 현재 사업장·해상도 지원을 대체하는 완성본으로 취급하지 않는다.
- 현재 프로세스와 같은 환경에서 성능을 비교하지 않았으므로 성능 향상 수치는 미확인이다.

## 3. 적용 순서

각 단계는 해당 단계의 검증을 마친 뒤 다음 단계로 진행한다. 계획 실행을 승인받으면 같은 목적의 통상적인 파일 추가나 단계 진행에 재승인을 요구하지 않는다. 별도 화면 정책 변경이나 운영 배포는 이 계획의 기본 구현 범위에 포함하지 않는다.

### 1단계: GIF 경로 정리와 보드 진단

#### 정적 로고 정책

- 지원 형식은 BMP·PNG·JPG·JPEG로 제한한다.
- 동일 이름의 GIF를 우선 선택하는 코드를 제거한다.
- 확장자 대소문자와 직접 GIF 지정을 포함해 지원하지 않는 형식은 디코딩 전에 제외한다. 실제 GIF를 정적 이미지로 위장한 경우도 디코더 형식 확인으로 거부하며 첫 프레임 표시를 지원으로 남기지 않는다.
- 지정 이미지가 없거나 지원하지 않거나 손상되었으면 `logo.bmp`로 대체한다. 기본 로고도 사용할 수 없으면 예외 없이 검은 배경의 빈 로고 영역을 표시하고 진단 로그를 남긴다.
- `ImageCacheHelper`의 정적 이미지 공유·캐시 기능은 보존한다. GIF 표시 코드 제거 후 사용처가 없는 `WpfAnimatedGif` 패키지 참조를 제거한다.
- 설정 파일과 사용자 이미지 파일을 일괄 수정하거나 삭제하지 않는다.

#### 보드 진단

- API 원본 행 수, 유효한 고유 SpaceIndex 수, 실제 표시 수, Board 밖 제외 수, 로고 슬롯 수를 구분한다.
- 무효 SpaceIndex와 같은 SpaceIndex의 중복 행은 별도 집계한다. 원본 행 수와 고유 계류대 수를 같은 숫자로 취급하지 않는다.
- 전체 조회와 부분 갱신을 구분한다. 부분 메시지를 전체 목록으로 간주해 기존 슬롯을 지우거나 누적 수를 초기화하지 않는다.
- 전체 조회 기준으로 `유효 고유 계류대 수 = Board와 일치하는 수 + Board 밖 제외 수`를 검증한다.
- `실제 사용 슬롯 수 = 개체 표시 슬롯 수 + 로고 슬롯 수`를 검증한다. 중복 Board 설정의 기존 경고·처리 정책은 유지하고 진단 분모를 명시한다.
- 비연속·역순 번호와 XML의 행·열 나열 순서를 유지한다. Board 밖 데이터로 패널을 자동 생성하지 않는다.
- 진단은 기존 상태 표시와 로그 경로에 집계값만 추가한다. 개체·출하자 정보나 원본 응답을 기록하지 않는다.

주요 대상: `Models/LogoManager.cs`, `Utils/ImageCacheHelper.cs`, `CowAuctionSmall.csproj`, `Models/DataChangedMessage.cs`, `ViewModels/MainWindowViewModel.cs`, 필요 시 `Views/MainWindow.xaml` 및 보드 집계 전용 클래스.

완료 기준: GIF 로딩과 전용 참조가 없고 정적 로고 대체 동작이 정상이며, 전체·부분 갱신에서 집계가 일관된다.

### 2단계: 경매 상태 판단 분리

- UI에 의존하지 않는 표시 상태 모델과 해석 함수를 추가한다. 위치는 기존 `Models/Structures`, `Services` 구조를 따른다.
- `FindPanel`은 해석 결과에 따른 기존 화면 연결을 담당한다. 잘못된 상태 문자열로 파싱 예외가 발생하지 않게 한다.
- 초기 적용은 기존 정상 입력에 대한 표시를 보존한다. 대기·진행을 내부적으로 구분하더라도 기존 화면을 그대로 사용할 수 있다.
- 낙찰·유찰 결과와 `IsRunning`이 상충할 때 기존 22·23 표시 우선 동작을 보존한다. 재경매 시작 이벤트에 따른 상태 초기화도 함께 확인한다.
- 취소 24의 기본 표시는 현재와 같은 로고다. 종료 대기·취소 전용 화면 추가는 후속 선택 사항이며 자동으로 도입하지 않는다.
- null, 빈 문자열, 공백, 미등록 코드, 개체 없는 슬롯의 처리를 명시하고 합성 입력으로 검증한다. 정상 데이터의 표시 가능 여부 조건을 참고 코드에서 무조건 복사하지 않는다.

주요 대상: `Services/DisplaySelect.cs`, 신규 표시 상태·상태 해석 클래스, `Models/Structures/AuctionStatus.cs` 및 `Utils/CowDisplaySelector.cs`의 관련 규칙 확인.

완료 기준: 기존 11·22·23·24 화면 대응이 보존되고 비정상 상태 입력에서 예외가 발생하지 않는다. 상태 판단을 앱 실행 없이 검증할 수 있다.

### 3단계: 메시지 스냅샷과 순차 처리

이 단계는 비동기 큐 추가 전에 전달 데이터의 수명을 먼저 정리한다.

1. 모든 관련 송수신 지점을 확인하여 전체 조회, 부분 갱신, 경매 이벤트를 구분한다.
2. 송신 시 컬렉션과 내부 변경 가능한 값까지 안전하게 복제하거나 불변 DTO로 변환한다. 기존 `gValues.Clone()`의 중첩 값 복제 범위를 확인한다.
3. AF22·23·24, AS8006, Refresh 등 핵심 이벤트를 타입이 있는 메시지로 표현한다. 네트워크 프로토콜 필드와 순서는 변경하지 않는다.
4. 상태 변경을 하나의 소비 흐름에서 처리하고 HTTP 폴링 결과도 같은 적용 경계를 통과하게 한다. 오래된 조회 결과가 이후 경매 결과를 덮지 않도록 요청 세대·세션을 구분한다.
5. UI Dispatcher 호출은 확정된 표시 결과 반영 경계에 둔다. Netty 이벤트 스레드에서 HTTP·대량 파싱·화면 갱신을 직접 실행하지 않는다.
6. 플랫폼 이벤트가 아닌 `async void`를 Task 기반 처리로 바꾸고 개별 메시지 실패가 소비 루프 전체를 종료시키지 않게 한다.

큐와 과부하 정책:

- bounded Channel을 기본 후보로 사용하되 참고 코드의 동기 대기를 복사하지 않는다.
- 중요 경매 이벤트는 정상 수용 구간에서 순서를 보존하며 조용히 폐기하지 않는다.
- 최신 값만 필요한 화면 갱신은 같은 세션·계류대 범위에서 병합할 수 있다. 낙찰·유찰·취소·Refresh 경계를 넘어 병합하지 않는다.
- 생산 측의 비동기 backpressure 가능 여부를 먼저 확인한다. 이를 지원하지 못하는 콜백에서 무제한 Task나 무제한 보조 큐를 만들지 않는다.
- 포화 시 이벤트 보존을 보장할 수 없다면 명시적인 동기화 실패 상태와 재동기화 경로를 설계한다. 이벤트 무손실이라고 보고하지 않는다.
- 용량과 제한시간은 합성 부하로 결정한다. queue depth, 처리 지연, 병합·거부 횟수를 개인정보 없이 측정한다.
- 종료 시 수신 중단, 취소, 큐 완료, 작업 종료, 구독 해제 순서를 정한다. UI 스레드와 소비 작업 사이의 상호 대기를 방지한다.

주요 대상: `Models/DataChangedMessage.cs`, `Services/NettyAsyncMsgProcess.cs`, `Services/ServerGetData.cs`, `ViewModels/MainWindowViewModel.cs`, 필요 시 `NetProto`의 전달 경계 및 `App.xaml.cs` 종료 처리.

완료 기준: 송신 후 원본 목록·객체를 바꾸어도 소비 데이터가 변하지 않는다. 중요 이벤트 순서, 오래된 응답 차단, 과부하·종료 시 동작을 재현 가능한 검증으로 확인한다.

### 4단계: 화면용 상태와 공통 표시 정리

- 기존 `UpdateSignature`, 뷰 재사용, 화면용 Clone의 역할을 정리하고 실제 중복 작업을 측정한다.
- 필요할 경우 화면에 필요한 값만 담는 표시 스냅샷을 도입한다. 서버 수신 모델을 전면 교체하지 않는다.
- 변경되지 않은 슬롯은 속성 갱신과 애니메이션 재시작을 피한다. 낙찰자 이름·비고·소유주 이력 등 실제 표시 값의 변경은 누락하지 않는다.
- 전체 목록에서 빠진 개체는 전체 조회 의미에 맞게 초기화하고, 부분 메시지에서 빠진 개체는 유지한다.
- 비고·친자일치·낙찰자 이름은 현재 공통 컨트롤을 우선 활용한다. 128×128 대표 화면에서 확인 후 해당 변경이 필요한 나머지 해상도로 확장한다.
- 페이지 번호·고정 사유·Refresh 해제를 표현하는 상태를 정리하되 `PageTimerSync`의 master/sub 선출, heartbeat, fallback을 보존한다.
- 사업장별 문구·색상·배지 조건을 참고 프로젝트 값으로 일괄 교체하지 않는다.

주요 대상: `Services/DisplaySelect.cs`, `Services/SetCustomDisplay.cs`, `ViewModels/AuctionContPanelViewModel.cs`, `ViewModels/MainWindowViewModel.cs`, `Services/PageTimerSync.cs`, `Views/Common/*`, 관련 비고 호스트·해상도별 XAML.

완료 기준: 주요 화면 상태와 회전 동작이 보존되고 동일 입력 반복 시 불필요한 화면 재생성이 없다. 성능 개선은 같은 조건의 전후 측정으로만 보고한다.

## 4. 검증 계획

### 자동·합성 검증

| 구분 | 확인 시나리오 |
|---|---|
| 로고 | BMP·PNG·JPG·JPEG, GIF 직접 지정·동명 존재·대문자 확장자·위장 파일, 파일 누락·손상, 기본 로고 실패 |

테스트는 상태 전이·동시성·데이터 수명처럼 회귀 위험이 있는 경계에 집중한다. 기존 Validation의 운영 접속 가능 코드를 먼저 확인하고 오프라인 검사만 선별한다. 필요하면 오프라인 전용 검증 프로젝트를 추가하며 기존 라이브 검사를 일괄 실행하지 않는다.

구현 시 기본 명령:

```powershell
dotnet restore CowAuctionSmall.csproj
dotnet build CowAuctionSmall.csproj -c Debug --no-restore
dotnet build CowAuctionSmall.csproj -c Release --no-restore
```

restore는 GIF 패키지 제거 등 프로젝트 구성이 바뀌어 필요한 시점에 수행한다. 이후 소스만 변경한 단계는 필요한 빌드와 해당 검증만 수행한다. 별도 검증 프로젝트를 추가하면 그 프로젝트의 복원·실행 명령과 결과를 기록한다.

### 수동 확인 및 성능

- 합성 데이터와 운영 연결이 차단된 검증 환경에서 화면·회전·스크롤을 먼저 확인한다.
- 실제 전광판과 PC 간 통신 검증은 환경·접속 범위를 확인한 뒤 수행한다. 앱을 단순 실행해 운영 서버에 접속하지 않는다.
- 동일 슬롯 수·해상도·페이지 수·회전 주기·비고 길이로 CPU, 메모리, 이벤트 반영 지연을 비교한다. 준비 구간과 측정 구간을 같게 한다.
- 수백 개 슬롯과 반복 이벤트를 포함하되 실제 개인정보 대신 합성 데이터를 사용한다.
- 최초 계획 작성 시 검증은 미수행이었다. 이후 승인된 구현의 자동 검사와 빌드 결과는 아래 8절에 기록한다. 실제 환경 실측은 미수행이다.

## 8. 구현 및 검증 결과 (2026-09-17)

총 3명의 에이전트가 구현·통신 검토·오프라인 검증을 분담했다. 단계별 검증을 실행하고 통합 검증 후 최종 수정의 영향 범위를 다시 검사했다.

| 단계 | 적용 결과 | 검증 |
|---|---|---|
| 1 | GIF 탐색·표시·패키지 제거, 정적 디코더 허용 목록과 기본 로고 대체, 원본 행·현재 계류대·물리 슬롯 집계 분리 | 직접/위장 GIF 차단, 정적 이미지·대체, 전체/부분/삭제 갱신·중복 보드 합성 검사 통과 |

구현 선택과 한계:

- 실제 상태값 24는 기존처럼 로고로 해석한다. AF24 프로토콜 이벤트의 기존 `updateResultStatus: false` 동작은 유지했다.
- 상태 큐 용량은 256, HTTP 큐 용량은 16이다. 중복 폴링 요청은 병합하며 포화 시 진단과 재동기화 필요 상태를 남기고, 이후 성공한 전체 조회로 복구한다. 모든 입력의 무손실을 보장하지 않는다. 실제 부하에 맞춘 용량 조정은 현장 측정이 필요하다.
- 종료·세대 변경 뒤 오래된 조회 결과의 반영은 차단한다. 기존 HTTP API는 전송 취소를 제공하지 않아 이미 시작된 실제 HTTP 요청은 내부적으로 완료될 수 있다.
- 기존 공통 비고·낙찰자 이름 컨트롤과 사업장 화면을 재사용했다. 공통 화면 전면 전환이나 PageTimerSync 통신 변경은 하지 않았다.
- 실제 제품 App·MainWindow·DisplaySelect를 실행하지 않았다. 직접 컨트롤 생성 검사는 전체 MVVM·페이지 회전·소유주 이력 서비스 연결과 다중 PC 동기화 검증을 대신하지 않는다.
- 합성 반복 검사는 변경 감지·생략 동작 검증이다. 동일 환경의 전후 렌더링 성능 비교는 미수행이며 성능 향상 수치를 주장하지 않는다.
