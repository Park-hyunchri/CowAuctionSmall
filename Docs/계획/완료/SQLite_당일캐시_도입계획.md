# SQLite 당일 캐시 및 소유주 변경 이력 표시 계획

> 문서 상태: **완료·후속 확장 있음** · 정리일: 2026-10-01
> 기본 캐시는 구현됐다. 이후 이력 JSON 버전 2의 사육지 저장, 비고 표시 분리, 요청 간격 설정, 개체별 반영이 추가됐다. 아래 최초 설계의 제한을 현재 기능으로 오해하지 않는다.

- 상태: 사용자 승인 범위 구현 및 검증 완료. 아래 계획과 최하단 구현 대응표·별도 설정 문서를 함께 참조한다.
- 이번 개정은 기존 3개 테이블 설계를 아래의 단일 `daily_cache` 테이블로 대체한다.

## 1. 목적과 확정 사항

1. 오늘 경매 데이터와 개체별 소유주 이력을 SQLite 한 테이블에 저장한다.
2. 같은 날 재시작하면 유효 캐시를 재사용하고 날짜가 다르면 데이터 전체를 초기화한다.
3. 축산물 이력 API는 소 개체번호로 `optionNo=2`를 조회한다.
4. XML 파싱과 표시 문구 생성을 API 호출·DB 저장에서 분리한다.
5. 기존 `Note`를 보존하고 `NoteChangeOwner`에 소유주 변경 문구를 별도로 둔다.
6. 기존 전광판·로고·경매 표시를 먼저 시작하고 이력 조회는 백그라운드에서 수행한다.
7. API 호출량은 캐시 재사용, 동일 요청 공유, 호출 제한으로 관리한다. SQLite 설치만으로 호출량이 감소하는 것은 아니다.

사용자는 화면에 필요한 개인정보를 당일 DB에 보관하고 날짜 변경 시 삭제하는 방식을 선택했다. 이번 계획은 이 범위에서 필요한 데이터만 보관한다.

## 2. 선행 작업 및 적용 범위

- .NET 10 전환과 로그인 응답 사업장 코드 적용은 별도 완료된 작업을 기준으로 한다.
- 경매 캐시는 XML의 비교용 코드가 아닌 인증된 사업장·계정 범위로 구분한다.
- 로그인 전에 만료 데이터 정리는 가능하지만, 경매 캐시 복구는 인증 완료 후 같은 범위의 데이터만 허용한다.
- 인증 실패 상태에서 이전 경매 캐시로 운영을 재개하는 기능은 첫 버전에 포함하지 않는다.
- 기존 경매 API 주기 변경은 이번 개정에서 보류한다. 이전 계획의 대기 주기 3초 → 10초 조정은 적용하지 않는다.
- 먼저 이력 API 중복 호출 감소와 표시를 검증하고, 경매 API 호출 주기 최적화는 별도 측정 후 결정한다.
- 실제 서비스의 일일 허용량·초당 제한·한도 초기화 시각은 아직 미확인이다. 임의의 수치를 공급자 정책으로 단정하지 않는다.

## 3. API 조회와 원본 이력번호

### 조회 방식

- API: `animalTrace/traceNoSearch`
- 요청: `ServiceKey`, `traceNo`, `optionNo=2`
- 필요한 응답: `infoType=2`의 `regYmd`, `regType`, `farmerNm`, `farmAddr` 및 응답에 실제 제공되는 식별 보조 필드.
- 문서의 옵션 표는 2를 출생 등 신고 이력, 9를 묶음 구성 내역으로 설명한다. 일부 소 개체 예제는 옵션 9로 여러 정보를 반환해 설명과 불일치한다.
- 앞선 실제 확인에서는 두 소 개체 모두 옵션 2에 이력이 반환되고 옵션 9에는 0건이 반환됐다. 현재 구현 기준은 옵션 2이며 모든 개체의 동작까지 확인한 것으로 표현하지 않는다.
- 소 이력상의 소유주는 경매 출하주와 동일하다고 보장되지 않는다. 출하주 필드를 덮어쓰지 않는다.

### 번호 처리

- `gValues`에 원본 조회용 `TraceNumber`를 추가할 예정이다. 기존 화면용 `EntityNumber`·축약번호와 분리한다.
- 현재 `AnimalParseData`는 `data[5]`를 잘라 화면 번호를 만든다. `data[19]` 등 다른 식별 필드도 의미를 확인한 뒤 서버 원본과 이력 API 번호의 대응을 검증한다.
- 이미 실제 조회가 확인된 15자리 소 개체번호는 앞자리 0을 포함한 문자열로 유지한다. 지원 형식·길이는 명시적으로 검증하며 잘라낸 화면 번호를 추정 복구하지 않는다.
- 소에만 조회를 적용한다. 염소·말, 누락·잘못된 번호는 호출하지 않는다.

### 인증 설정

- 키는 기존 Git 제외 로컬 파일 `Config/animalTrace.local.json`에서 읽는다. 키나 전체 요청 URL을 DB·로그·문서에 기록하지 않는다.
- 파일 읽기와 설정 누락 시 자동 조회 중단을 구현했다. 개발 빌드에는 로컬 파일이 복사되지만 게시본에는 포함하지 않는다. 게시 환경에는 별도로 제공한다.
- 저장된 `ServiceKeyEncoded`는 이미 URL 인코딩된 값이다. 쿼리 빌더가 자동 인코딩한다면 한 번 디코딩한 값을 전달해 이중 인코딩을 막는다.
- 실제 확인된 주소는 가이드의 HTTP 주소다. HTTPS 요청은 당시 연결에 실패했다. 구현 전 전송 주소 지원 여부를 다시 확인하고 인증서 검증 우회로 해결하지 않는다.

## 4. 단일 테이블 구성

테이블은 `daily_cache` 하나만 만든다. 경매 데이터와 개체 이력은 서로 다른 종류의 행으로 보관한다. 메타데이터·개체별 이력 행을 위해 다른 테이블을 추가하지 않는다.

| 컬럼 | 역할 |
|---|---|
| `cache_type` | `auction`, `animal_history`, `control` 구분 |
| `cache_key` | 종류별 조회 키 |
| `cache_date` | 데이터 보관 기준일, 한국 날짜 `yyyy-MM-dd` |
| `payload_json` | 종류별 허용 필드만 직렬화한 JSON |
| `created_at` | 최초 저장 시각, UTC ISO 8601 |
| `updated_at` | 마지막 정상 갱신 시각, UTC ISO 8601 |

```sql
CREATE TABLE IF NOT EXISTS daily_cache (
    cache_type TEXT NOT NULL
        CHECK (cache_type IN ('auction', 'animal_history', 'control')),
    cache_key TEXT NOT NULL,
    cache_date TEXT NOT NULL CHECK (length(cache_date) = 10),
    payload_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    PRIMARY KEY (cache_type, cache_key)
);
```

- `cache_date`는 경매일·신고일과 다르다. 과거 경매 또는 내일 경매를 오늘 조회해도 보관 기준일은 오늘이다.
- 날짜 문자열의 실제 유효성과 JSON 구조·버전은 애플리케이션에서 검증한다. 컬럼 길이 검사만으로 날짜 유효성을 보장하지 않는다.
- 스키마 버전은 SQLite `PRAGMA user_version`으로 관리한다. 별도 버전 테이블은 만들지 않는다.
- 모든 SQL은 매개변수를 사용한다.
- `control`은 호출 횟수·호출 중단 상태를 같은 날 재시작 후에도 유지하기 위한 소량의 제어 행이다. 개인정보와 실제 인증키를 넣지 않는다.

### 종류별 키와 JSON

| 종류 | 키 범위 | JSON 내용 |
|---|---|---|
| `auction` | 실행 환경·인증 계정 범위 + 인증 사업장 + 조회 경매일 | 마지막 정상 현황 스냅샷, 항목 수, 허용 출품 정보 배열 |
| `animal_history` | 원본 소 이력번호 | 데이터 형식 버전, 결과 건수, 필요한 전체 신고 이력 배열 |
| `control` | API 종류 + 비밀값이 아닌 로컬 인증 프로필 식별자 | 당일 예약·사용 호출 수, 일시 중단 사유, 다음 허용 시각 |

- 키는 충돌하지 않는 구조화 형식으로 만든다. 운영 URL·비밀번호·토큰·서비스키를 키에 넣지 않는다.
- 경매 출품 배열 안에서는 실제 항목별 차수·경매대상 종류·출품번호로 구분한다. 차수 API 첫 값으로 모두 덮어쓰지 않는다.
- 전체 현황은 스냅샷 한 행을 트랜잭션으로 교체한다. 정상 빈 목록도 `items: []`로 저장해 이전 출품이 남지 않게 한다.
- 개체는 경매 출품 여러 행에서 사용하더라도 이력 캐시 한 행을 공유한다.
- 이력 0건도 정상 결과로 저장한다. 통신·인증·XML 오류는 빈 이력으로 저장하지 않는다.
- 표시 문구는 이력 JSON에서 다시 만든다. 같은 개인정보를 경매 JSON의 `NoteChangeOwner`에 중복 저장하지 않는다.
- 제어 행 갱신은 경매·개체 데이터의 저장 날짜나 정상 조회 시각을 연장하지 않는다.

## 5. 개인정보와 DB 위치

- NuGet: `Microsoft.Data.Sqlite` 예정. 정확한 버전과 네이티브 의존성은 구현 시 .NET 10 호환성을 확인한다.
- 설치형 DB 서버는 필요하지 않으며 SQLite 라이브러리는 앱과 함께 배포한다.
- DB 위치: `%LocalAppData%/CowAuctionSmall/Cache/<설치경로 식별자>/auction-cache.db`.
- 실행 폴더와 DB 위치를 분리해 현재 저장소의 OneDrive 동기화 경로에 DB를 만들지 않는다.
- 경매 데이터는 기존 화면·파서에 필요한 필드만 명시적으로 저장한다. 출하자·낙찰자·참가번호·번호·지역·비고 등 당일 보관 허용 범위를 적용한다.
- 개체 이력은 신고일·신고 구분·소유주와 필요한 지역, 식별 보조 필드만 저장한다. `farmAddr`는 첫 버전 비고에 사용하지 않으므로 원문 상세 주소를 기본 저장하지 않고, 향후 지역 표시가 필요하면 최소 단위로 선별한다.
- 원본 HTTP 응답 전체, 인증 정보, 운영 접속 정보, 불필요한 내부 관리 필드는 저장하지 않는다.
- 기존 `gValues.toString()` 등 덤프·로그에 `NoteChangeOwner`와 원본 이력번호를 무조건 추가하지 않는다. 신규 로그는 API 종류·상태·건수·소요 시간 등으로 제한한다.

## 6. 프로그램 시작과 초기화 판단

날짜 기준은 PC 시간에서 산출한 한국 날짜로 통일한다. 시스템 시계가 앞으로 또는 뒤로 변경되어 현재 기준일이 달라져도 재검사한다.

| 시작 상태 | 처리 |
|---|---|
| DB 없음 | DB와 테이블 생성 |
| 테이블 없음 | 테이블 생성 |
| 빈 테이블 | 초기화 없이 오늘 캐시 사용 시작 |
| 모든 행이 오늘 | 같은 인증 범위의 정상 캐시 재사용 |
| 다른 날짜 행이 하나라도 있음 | 전체 행 삭제 후 오늘 기준으로 시작 |
| 스키마·JSON 형식 불일치 | 해당 캐시를 복구 데이터로 사용하지 않고 재생성 또는 재조회 |
| DB 잠금·손상·권한·삭제 실패 | 이전 데이터를 사용하지 않고 캐시 사용 중단 및 상태 안내 |

```text
앱 시작
  → 기존 패널·로고 즉시 표시
  → 백그라운드에서 DB 소유권·스키마·날짜 검사
  → 필요하면 전체 데이터 초기화
  → 경매 로그인 완료 후 해당 범위의 캐시 복구
  → 서버 최신 상태 확인
  → 필요한 소 개체의 이력 캐시 확인 및 누락분 조회
```

- 날짜 판단은 `created_at`·`updated_at` 대신 `cache_date`를 사용한다. 비정상 날짜도 유효 캐시로 취급하지 않는다.
- 정상적인 날짜 초기화는 테이블 구조를 유지하고 `DELETE FROM daily_cache`를 트랜잭션 안에서 수행한다.
- 빈 DB에서도 실행 중 날짜 변경을 판단하도록 메모리에 현재 보관일과 세대 번호를 유지한다.
- 이전 날짜 행을 삭제하기 전에는 개인정보 JSON을 화면용으로 복원하지 않는다.
- 날짜 검사와 캐시 읽기·쓰기의 경합을 막아 검사 직후 오래된 행이 들어오는 상황을 차단한다.

## 7. 자정·종료·삭제 처리

### 화면 전환 시 당일 보관 정책 (2026-09-15 확정)

- 조회 등록은 화면 표시 대상으로 선정된 개체를 기준으로 한다.
- 화면에서 사라져도 저장된 개체 이력은 삭제하지 않는다. 이미 등록한 요청도 화면 이탈만을 이유로 취소하지 않으며, 기존 호출 예산·오류 정책에 따라 한 건씩 조회 후 저장한다.
- 응답 시 현재 표시 개체의 원본 번호가 일치하는 경우에만 화면에 반영한다. 같은 날 다시 표시되면 저장된 이력을 재사용한다.
- 날짜 변경 시 기존 초기화 규칙을 적용한다. 앱 종료·시간 제한·날짜 변경에 따른 응답 무효화는 계속 유지한다.
- 앞선 안내에서 화면 이탈 개체의 대기 요청 취소를 필수 잔여 작업으로 분류한 것은 정정한다. 현재 구현은 위 당일 보관 정책과 일치하며 별도의 삭제·취소 기능을 추가하지 않는다.

### 날짜 변경 및 종료

1. 경매가 없는 상태에서도 날짜를 주기적으로 확인하고, 모든 캐시 접근 전에도 확인한다.
2. 날짜 변경 시 조회·저장 큐를 잠시 막고 캐시 세대를 증가시킨다.
3. 이전 요청을 취소하고 DB를 초기화한 뒤, 메모리 캐시와 화면의 이전 `NoteChangeOwner`도 비운다.
4. 진행 중인 경매의 종료·유찰을 임의로 선언하지 않는다. 이전 경매 스냅샷은 더 이상 현재 데이터로 재사용하지 않고 서버 결과로 갱신한다.
5. API 요청이 시작될 때 날짜·세대·화면 대상 식별값을 캡처하고, 응답·저장·UI 반영 전에 현재 값과 비교한다. 전날 응답은 버린다.
6. 정상 종료는 요청 취소·작업 큐 정리·DB 연결 해제를 수행한다.

DB는 `journal_mode=DELETE`, `secure_delete=ON`, 연결 풀 비활성화로 시작한다. DB 작업은 UI 스레드 밖의 직렬 작업 큐에서 수행한다. 일반 삭제만으로 남는 데이터 문제를 줄이기 위해 모든 쓰기 연결에 보안 삭제 설정을 적용하고 실제 적용값을 확인한다. SQLite의 보안 삭제·저널 동작은 [공식 PRAGMA 문서](https://www.sqlite.org/pragma.html#pragma_secure_delete)를 기준으로 검증한다.

- 스키마 재생성이나 손상 복구 시 앱 소유 경로와 파일을 확인하고, 연결·소유권을 확보한 상태에서만 DB 및 저널 부속 파일을 처리한다. 사용 중인 저널 파일을 임의 삭제하지 않는다.
- WAL은 첫 버전에서 사용하지 않는다. 다른 버전이 만든 WAL DB가 있으면 정상 복구·정리 절차를 따르며 단순 부속 파일 삭제로 처리하지 않는다.
- 삭제 시 가상 개인정보를 넣어 DB·저널 파일의 잔존 여부를 확인한다. SSD·파일시스템 스냅샷·외부 백업까지 복구 불가능한 물리적 삭제를 보장하는 정책은 아니다.
- 앱이나 PC가 꺼져 있으면 자정 삭제는 실행되지 않는다. 다음 실행 시 초기화한다. 종료 중에도 시각에 맞춘 삭제가 필요하면 별도 작업이 필요하다.
- 동일 DB의 복수 프로세스 접근은 경로별 배타적 파일 잠금(`auction-cache.db.lock`, FileShare.None)으로 제한한다. 두 번째 프로세스는 해당 DB를 초기화하지 않는다.
- 설치별 DB 중 오래된 앱 소유 캐시는 시작 시 정리 대상으로 확인하되, 다른 실행본이 소유한 DB를 강제로 삭제하지 않는다.

## 8. API 트래픽 및 오류 정책

| 상황 | 동작 |
|---|---|
| 당일 정상 캐시 있음 | API 호출 없이 재사용 |
| 당일 정상 0건 캐시 있음 | 빈 결과 재사용 |
| 캐시 없음 | 조회 큐 등록 |
| 같은 개체 조회가 이미 진행 중 | 같은 Task 공유 |
| 동일 개체가 여러 패널에 표시됨 | 한 번 조회한 결과를 여러 표시 대상에 적용 |
| 정상 캐시 수동 새로고침 | 개체 한 건만 재조회, 진행 중 요청 공유·쿨다운 적용 |
| 일시적인 통신 오류 | 제한된 재시도와 지연, 정상 당일 캐시는 유지 |
| 인증 실패·한도 초과 | 해당 API 자동 재시도 중단, 상태창 안내 |
| DB 사용 불가 | 기존 경매 기능 유지, 메모리 캐시 사용. 영속 호출 예산을 확인할 수 없으면 신규 자동 이력 조회 중단 |

- 우선 화면에 필요한 개체부터 조회한다. 전체 출품 선조회는 호출 예산을 확인한 후 별도 선택 사항으로 둔다.
- 첫 제안값은 동시 요청 1개, 시작 간격 최소 1초, 일시 오류 자동 재시도 최대 2회다. 이는 앱의 보수적 초기값이며 공급자의 허용량을 의미하지 않는다.
- 일일 예산 값은 실제 발급 계정 한도를 확인해 설정한다. 미설정 상태에서 전체 개체 자동 선조회를 시작하지 않는다.
- 호출 직전 `control` 행에 예산을 예약하고 실제 HTTP 전송 시도마다 집계한다. 요청 직후 종료되어도 횟수를 적게 계산하지 않도록 한다.
- 인증 오류·한도 초과 중단 상태는 당일 재시작 후에도 유지한다. 공급자 한도 초기화 시각을 확인하기 전에는 로컬 자정만으로 한도 복구를 보장하지 않는다.
- 여러 PC가 같은 키를 쓰면 로컬 집계로 전체 한도를 관리할 수 없다. PC별 할당량 또는 중앙 중계가 필요한지 배포 환경에서 결정한다.
- 수동 새로고침도 예산을 사용한다. 실패해도 저장된 정상 이력을 빈 값으로 덮어쓰지 않는다.

## 9. 함수와 책임 분리

| 역할 | 함수 예시 | 책임 |
|---|---|---|
| HTTP 클라이언트 | `FetchAnimalHistoryAsync` | 옵션 2 요청·시간 제한·취소·HTTP 결과 |
| XML 파서 | `ParseAnimalHistory` | XML과 업무 결과코드 검증, 이력 DTO 변환 |
| 표시 변환기 | `FormatAnimalHistoryNote` | 검증된 이력을 문구로 변환 |
| SQLite 저장소 | `GetCacheAsync` / `SaveCacheAsync` | 날짜 확인·JSON 버전 검사·조회·저장 |
| 캐시 수명 관리 | `EnsureTodayAsync` | 시작·자정 초기화와 세대 관리 |
| 이력 서비스 | `GetAnimalHistoryAsync` | 캐시 우선·요청 공유·호출 예산·오류 정책 |

- 파서는 네트워크·DB·Dispatcher에 의존하지 않는 순수 함수로 작성한다.
- HTTP 성공과 API `resultCode` 성공을 별도로 확인한다.
- 결과는 정상 이력, 정상 0건, 인증 오류, 한도 초과, 일시 오류, 파싱 오류로 구분한다.
- XML DTD·외부 엔터티를 허용하지 않고 응답 크기를 제한한다.
- 누락값·빈 태그·잘못된 날짜·예상하지 못한 infoType·중복 item을 테스트한다. 항목 오류를 조용히 삭제해 정상 0건으로 만들지 않는다.
- 날짜가 같은 이력의 선후를 확정할 수 없으면 임의의 소유주 이동을 만들어내지 않는다.

## 10. NoteChangeOwner 표시

```text
Note            : 기존 비고
NoteChangeOwner : 이전 소유주 → 현재 소유주(양수 2026-08-05)
```

예제는 형식 설명용이며 실제 조회한 사람 이름·개체번호를 문서나 테스트에 복제하지 않는다.

- `gValues.Note`는 기존 경매 API의 값 그대로 보존한다.
- `gValues.NoteChangeOwner`는 기본 빈 문자열로 추가하고 매번 계산 결과로 교체한다. `Note += ...` 방식은 사용하지 않는다.
- ViewModel 또는 표시 전용 변환기에서 두 값을 조합한 `DisplayNote`를 제공한다. `NoteChangeOwner`만 존재해도 비고 영역이 표시되어야 한다.
- `Note`의 빈 값·공백·기존 무값 표기 `-`를 처리한다. 연결 구분자는 기존 흐르는 비고 영역에 맞춰 ` / `를 기본 제안으로 한다.
- `TraceNumber`, `NoteChangeOwner`를 복사·동등성 비교·UpdateSignature 등 실제 변경 감지 경로에 반영한다. 로그용 문자열 덤프에는 추가하지 않는다.
- `AuctionContPanelViewModel` 갱신 시 표시 문구 변경을 알리고 비고 스크롤 위치·텍스트 스냅샷을 갱신한다.
- 경매 API에서 새 gValues가 만들어져도 개체번호로 이력 캐시를 다시 병합한다.
- 비동기 응답은 캡처한 출품번호만으로 반영하지 않는다. 현재 개체번호·인증 범위·화면 세대가 동일한지 확인 후 UI Dispatcher에서 적용한다.
- 실제 바인딩과 공통 NoteHost, 진행·낙찰·유찰·사업장별 예외·해상도별 페이지를 조사한 뒤 필요한 범위에만 적용한다.

### 변경 문구 결정 기준

- 정상 전산등록 1건만 있으면 변경 문구는 빈 값이다.
- 날짜순 정렬 후 완전히 동일한 기록은 중복 제거한다.
- 첫 버전 표시안은 최근에 확인 가능한 변경 한 건이다. 필요한 전체 이력은 당일 JSON 캐시에 보관한다.
- 직전 소유주 기록과 양수 기록이 있고 순서가 명확하면 `이전 → 이후(양수 날짜)` 형태로 표시한다.
- 이름만 같다고 동일인으로 단정하지 않는다. 동일 이름·정보 누락·동일일 순서 불명 등 변경 여부를 확정할 수 없는 경우 이름을 연결해 사실을 만들어내지 않고 문구를 생략하거나 신고 사실만 표시하는 규칙을 테스트로 확정한다.
- 전산등록·양수·도축출하 등을 모두 소유주 변경으로 집계하지 않는다. 신고 구분의 실제 응답 범위를 확인한다.
- 조회 중·실패·이력 없음 상태는 내부적으로 구분한다. 기존 당일 정상 문구가 있으면 일시 오류에 유지하고, 날짜 변경 시에는 제거한다.

## 11. 경매 캐시의 최신성

- 당일 캐시 복구 후 서버에서 최신 현황을 확인한다. 캐시만으로 경매 진행·종료·낙찰 상태를 확정하거나 타이머를 재개하지 않는다.
- 정상 빈 응답은 빈 스냅샷으로 저장하고, 서버 오류는 기존 정상 스냅샷을 보존한다.
- AF·일괄 종료·SZ·날짜 전환·디코더 새로고침 등 기존 진입점을 확인해 파생 이력이 유실되지 않게 한다.
- 실시간 결과보다 먼저 시작한 조회 응답이 낙찰·유찰 상태를 되돌리지 않도록 기존 이벤트 세대와 응답 최신성을 확인한다.
- 서버 반영 이후의 재조회가 필요한 경우 과거 정기 요청에 무조건 합류하지 않는다.

## 18. 인증 설정 간소화 (2026-09-15, 최신 변경)

사용자 요청에 따라 XML은 `AnimalTrace/ServiceKey`만 사용한다. 이전 절의 Enabled·Address·KeyFile·DailyLimit·RequestIntervalMs 및 로컬 JSON 배포 설명은 이번 변경으로 대체한다. API 주소·일일 로컬 예산 100회·간격 1000ms는 AnimalTraceSettings의 소스 기본값이며, 옵션 2·재시도도 소스에서 관리한다. 빈 인증키는 조회를 사용하지 않는다. users.XML과 대체 XML 7개에 기존 키를 이전했고, 실제 키는 문서에 기록하지 않는다. XML의 기존 배포 정책에 따라 키도 함께 전달된다. 기존 JSON 파일은 보존하지만 읽거나 복사하지 않는다. 당일 예약 집계와 중단 상태는 이어받는다.


## 19. 임의 일일 제한 해제 (2026-09-15, 최신 변경)

사용자 요청에 따라 앞 절의 하루 100회 기본 예산은 폐기한다. AnimalTraceSettings.DailyLimit=0은 로컬 일일 제한 없음이며, 기존 Count가 100 이상이어도 조회·집계를 계속한다. 날짜 초기화나 DB 삭제 없이 적용한다. 실제 API 한도 초과·인증 오류 중단, 최소 1초 간격, 캐시 및 중복 요청 공유는 유지한다. 설정 XML에는 인증키만 둔다.


## 20. 이력 사용 여부 선택 (2026-09-15, 최신 변경)

사용자가 추가한 AnimalTrace/IsAnimalProductsTraceability를 사용한다. Y이고 인증키가 있을 때만 이력 API 조회와 합성 비고 표시를 사용한다. 기본값은 N이며 누락·빈 값·잘못된 값도 N으로 처리한다. N이면 자동·수동 이력 요청과 신규 이력 저장을 하지 않고 기존 Note만 표시한다. 기존 당일 캐시는 보존하며 Y로 변경 후 재시작하면 재사용한다. 현재 users.XML의 Y는 보존하고 대체 XML 7개에는 N을 추가했다. 경매 현황 조회와 날짜별 삭제 정책은 유지한다.
