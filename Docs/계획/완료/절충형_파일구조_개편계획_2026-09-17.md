## 1. 목표와 선택

현재의 WPF·MVVM 및 해상도·사업장별 화면을 유지하면서 참고 프로젝트의 업무 규칙·처리 흐름·외부 입출력 분리를 적용한다. 수정할 파일의 위치와 의존 관계를 쉽게 파악하는 것이 목적이다. 폴더 이동 자체를 실행 성능 개선으로 보고하지 않는다.

현재 구조의 주요 문제:

- Services에 HTTP·Netty 처리, 저장소, 경매 규칙, WPF 화면 선택과 애니메이션이 함께 있다.
- Models에 데이터 모델뿐 아니라 XML 파서·로고 로딩·WPF Converter와 실제 화면 컨트롤이 포함되어 있다.
- 조사 시점 DisplaySelect는 약 1,496줄, ServerGetData는 약 1,461줄이다. 위치 정리 이후 책임 분리도 별도 단계로 검토해야 한다. 줄 수 자체를 분리 기준으로 삼지는 않는다.
- 참고 프로젝트는 Domain·Application·Infrastructure·Presentation 분류가 명확하지만 일부 파일의 네임스페이스는 이전 Models·Services 이름을 유지한다. 폴더와 의존성 정리를 함께 완료하는 기준이 필요하다.

**GIF는 절대로 지원하지 않는다.** 정적 로고 형식 제한, 위장 GIF 차단과 기본 로고 대체를 유지한다. 텍스트 스크롤은 유지한다.

## 4. 의존성·네임스페이스 원칙

- Domain은 외부 통신·저장·WPF·앱 전역 설정 읽기를 참조하지 않는다. 단순 데이터와 순수 규칙을 둔다.
- Application은 Domain과 필요한 계약을 사용한다. 외부 구현 연결은 App의 서비스 등록에서 조립하는 방향으로 정리한다.
- Infrastructure는 Application의 계약을 구현하고 Domain 데이터를 사용한다. View·ViewModel을 참조하지 않는다.
- Presentation·ViewModels·Views는 Application의 결과와 Domain 데이터를 화면에 반영한다. Converter·Dispatcher·애니메이션은 이 영역에 둔다.
- 계층 간 현재 직접 참조는 이동 단계에서 목록화하고 책임 분리 단계에서 해소한다. 폴더 이동만으로 계층 분리가 끝났다고 보고하지 않는다.
- 계약은 실제 경계를 분리하거나 가짜 구현으로 검증하는 데 필요한 경우에만 추가한다. 모든 클래스에 인터페이스를 만들지 않는다.
- 목표 네임스페이스는 폴더에 맞춘다. CowAuctionSmall.Application을 도입하면서 WPF Application과 충돌하는 곳은 System.Windows.Application 또는 명시적 별칭으로 해결한다. 불필요한 전역 치환은 하지 않는다.
- 기존 타입 이름·메서드 계약은 우선 유지한다. using, 별칭, 완전 수식 이름, XAML xmlns, x:Class, 리소스 키·URI, DI 등록, reflection 및 검증 코드의 타입 참조를 함께 점검한다.
- 네임스페이스가 저장 데이터·직렬화 타입 식별자 등에 포함되는지 확인한다. 영향이 있으면 기존 저장 계약을 보존하는 호환 처리를 먼저 정한다.

## 5. 단계별 실행과 완료 기준

### 0단계 — 현재 작업 기준선 확정

1. git status·관련 diff·미추적 파일과 하위 AGENTS.md를 확인한다. 현재 사용자 내용을 기준으로 이동 전 파일 목록과 내용 식별값을 보관한다. 민감정보 원문은 문서에 남기지 않는다.
2. 각 파일의 현재 경로·목표 경로·타입·참조 위치를 이동 목록으로 만든다. 추적 여부를 구분한다.
3. 현 상태 Debug·Release 빌드와 기존 오프라인 전체 검증으로 기준선을 확보한다. 이미 같은 내용으로 확보된 결과는 재사용할 수 있다.
4. 기존 공백 오류·경고와 새 오류를 구분한다. 기존 미커밋 변경을 되돌리거나 별도 commit을 전제하지 않는다.

완료 기준: 누락·중복 없는 이동 목록, 사용자 변경 보존 기준, 실행 가능한 오프라인 검사 확보.

### 1단계 — 데이터·규칙·메시지 위치 정리

- Domain 및 Application/Messaging·Abstractions에 해당하는 파일부터 이동한다.
- IAuctionDataSource처럼 계약과 구현이 한 파일에 있는 경우 동작을 바꾸지 않고 파일만 분리한다.
- 소비자의 using·완전 수식 이름을 함께 수정하고 클래스 로직은 유지한다.
- 상태 판단, 메시지 복제, 보드 원본 집계 및 데이터 필드 보존 검사를 실행한다.

완료 기준: Debug 빌드와 해당 검사 통과, Domain의 금지 의존성 없음, 이동 전후 선언·로직 차이 설명 가능.

### 2단계 — 외부 통신·설정·저장 위치 정리

- Api·Netty·Synchronization·Persistence·Configuration·Logging을 이동하고 호출자·서비스 등록을 수정한다.
- Application/Auction·AnimalHistory의 처리 흐름 파일을 옮긴다. 이 단계에서는 기존 호출 순서와 상태 변경 위치를 보존한다.
- 설정·DB·로그 경로, API 요청·응답 형식, 네트워크 프로토콜, 큐 용량과 재동기화 정책을 유지한다.
- 순서·중복·포화·지연 응답·날짜 경합·종료 및 가짜 API 통합 검사를 실행한다.

완료 기준: Debug 빌드와 관련 오프라인 검사 통과, 운영 접속 없음, Config·저장 계약·통신 동작 변경 없음.

### 3단계 — WPF 표시 지원 코드 위치 정리

- Display·Converters·Assets·Animation 및 OutlinedTextBlock을 이동한다.
- 기존 Views 경로는 유지하며 관련 XAML·App 리소스·ViewModel 참조를 갱신한다. Views 폴더명 대소문자·철자 통일은 함께 하지 않는다.
- 정적 로고·위장 GIF 차단, 보드 갱신, 페이지 상태, 해상도별 직접 생성, 비고·낙찰자 스크롤 수명 검사를 실행한다.
- reflection으로 문자열 타입명을 조회하거나 명시적 csproj Include/Update가 있는지 점검한다. Validation 컴파일 제외 규칙을 유지한다.

완료 기준: Debug·Release 및 오프라인 전체 검사 통과, 누락된 XAML 타입·리소스 없음. 여기까지를 파일 이동과 참조 정리의 완료 지점으로 기록한다.

### 4단계 — 구조·참조 정합성 확인

- 이동 목록과 최종 트리를 대조하여 누락·중복 컴파일·이전 타입 사본 여부를 확인한다.
- 예전 네임스페이스·파일 경로를 검색해 실행 참조의 잔여를 정리한다. 과거 WORKLOG 기록은 당시 사실로 보존하고 현재 사용 안내의 링크만 갱신한다.
- Application에서 Infrastructure·Presentation을 직접 사용하는 지점과 전역 설정·메시지 의존성을 목록화한다. 다음 단계의 실제 분리 대상을 이 목록으로 결정한다.

완료 기준: 파일 위치와 네임스페이스 일치, 현재 문서 링크 유효, 남은 의존성마다 후속 처리가 명시됨.

### 5단계 — 큰 클래스의 책임 분리

파일 이동이 검증된 뒤 별도 변경 묶음으로 수행한다. 아래는 후보 책임이며 클래스 이름과 개수는 실제 호출 관계를 기준으로 정한다.

- ServerGetData: 조회 작업 조정, 응답 파싱·검증, 경매 상태 반영, polling·종료 수명을 분리할 수 있는 경계부터 추출한다. 상태 변경의 단일 소비 흐름과 세대 검사는 유지한다.
- DisplaySelect: 화면 생성·재사용, 페이지 회전·고정, 패널/비고 호스트 수명 중 독립적으로 검증 가능한 책임을 추출한다. PC 동기화 통신 구현은 기존 계약을 통해 연결한다.
- MainWindowViewModel: 새 서비스로 옮긴 책임이 중복되지 않게 정리하되 바인딩·Command와 화면 상태 반영을 유지한다. 관련 없는 UI 개편은 하지 않는다.
- 전역 설정이나 외부 구현 직접 참조는 필요한 작은 계약·설정 전달로 치환한다. 데이터 모델 전면 교체나 새 범용 프레임워크 도입은 하지 않는다.
- 각 추출 후 해당 회귀 검사와 빌드를 실행한다. 단순 줄 수 감소를 위한 partial 파일 분할을 책임 분리 완료로 간주하지 않는다.

완료 기준: 추출한 클래스의 책임과 의존성 설명 가능, 상태 전이·조회·페이지·수명 계약 보존, 영향 범위 검증 통과. 여전히 큰 클래스가 있더라도 분리 근거가 없는 부분은 이유를 기록한다.

## 6. 검증 명령과 보고 기준

구현 승인 후 실행할 기본 명령:

```powershell
dotnet build CowAuctionSmall.csproj -c Debug --no-restore
dotnet build CowAuctionSmall.csproj -c Release --no-restore
dotnet run --project Validation/ReferenceAdoptionChecks/ReferenceAdoptionChecks.csproj --no-restore -- all
```

각 단계에서는 영향에 따라 같은 검증 프로젝트의 stage1·stage2·stage3·stage4를 선택한다. 최종 통합 검증은 전체를 실행한다. 소스 참조가 바뀌므로 이전 바이너리만 실행하는 --no-build로 대체하지 않는다. WPF obj 충돌을 피하도록 빌드·검증 실행은 한 담당자가 순차 수행한다.

- 파일 이동만으로 복원이 필요하지 않으면 --no-restore를 사용한다. 복원 자산이 없거나 실제 프로젝트 구성이 바뀐 경우에만 필요한 restore를 수행한다.
- 선행 구현 기록은 전체 879개 통과 후 QCN 보완 관련 stage3 219개 통과이며, 최종 검사 정의는 882개다. 구조 개편에서는 실행 당시 실제 개수와 결과를 새로 기록한다.
- 현재 기록의 Debug·Release 경고는 각각 90개다. 실제 기준선과 비교하여 새 경고·오류를 해결한다. 기존 경고 일괄 정리는 포함하지 않는다.
- Validation/OwnerHistoryChecks는 라이브 동작 가능성을 먼저 확인한다. 변경된 참조의 컴파일과 fake 기반 이력·SQLite 회귀를 필요한 범위에서 검사하며 라이브 검사를 일괄 실행하지 않는다.
- 순수 파일 이동을 검증하기 위해 구현을 그대로 따라 하는 테스트를 추가하지 않는다. 기존 검사로 포착되지 않는 추출 경계·의존성·수명 변화에만 의미 있는 검사를 보강한다.
- WPF 숨겨진 HWND·컨트롤 직접 생성 검사는 전체 앱·사업장·운영 통신 검증과 구별한다. 실제 서버·전광판, 전체 페이지 회전과 master/sub·fallback은 환경 확인 후 별도 수동 검증 대상으로 기록한다.
- 빌드·테스트 실패 시 같은 단계에서 원인을 해결하고 다음 단계로 넘어간다. 이미 성공한 검사는 새로운 변경·실패 근거가 없으면 반복하지 않는다.

## 7. 담당 분배와 변경 보호

실행 인원은 총 3명이다. 계획 작성 단계에는 추가 에이전트를 실행하지 않았으며, 후속 구현 승인에 따라 아래 역할을 분담했다.

| 담당 | 역할 |
|---|---|
| 주 담당 | 이동 목록·공통 네임스페이스·App/DI·csproj·XAML 참조 통합, 문서·최종 확인 |
| 구조·통신 담당 | 할당된 Domain/Application/Infrastructure 이동 및 책임 분리, 의존성 검토 |
| 검증 담당 | Validation 참조 수정, 단계별 검사·빌드 단독 실행, 회귀·미검증 범위 보고 |

동시에 같은 파일을 수정하지 않는다. 네임스페이스·XAML·DI처럼 광범위한 참조 변경은 주 담당이 순서대로 통합하고, 다른 담당은 독립된 파일 검토·검증 준비를 병행한다. 단순 이동 단계는 병렬 수정량보다 일관성을 우선한다.

이동 전 절대 경로가 저장소 안인지 확인하고 목적지 파일 충돌을 검사한다. 기존 파일을 덮어쓰지 않는다. 파일 내용·인코딩·줄바꿈을 보존하고, 파일별 이동 기록으로 추적한다. 실패 복구가 필요하면 이번 작업으로 이동·수정한 범위만 최신 사용자 내용과 대조하여 되돌린다. git reset·clean·restore로 사용자 변경을 폐기하지 않는다.

## 9. 구현 결과 (2026-09-17)

- 기존 소스 80개를 이동하고 namespace·using·XAML 참조를 갱신했다. [현재 구조 안내와 전체 이동표](../../파일구조_안내.md)에 이전·현재 경로를 대응시켰다.
- Domain의 이력 설정을 AnimalTraceSettings로 분리했다. CowDisplaySelector는 UI를 사용하지 않는 계류대별 개체 선택 규칙이므로 계획의 Presentation 후보에서 Domain/Auction으로 확정했다. LoginResult는 JSON 응답 파싱을 포함하므로 Infrastructure/Api에 유지하고 Application에는 순수 인증 결과와 경매일 DTO를 전달한다.
- 기존 IAuctionDataSource의 구현을 분리하고, 접속·파싱·로그·이력 조회·당일 저장에 필요한 계약 5개를 추가했다. App에서 실제 구현을 조립한다. Application의 Infrastructure·WPF 직접 참조와 Infrastructure의 WPF·View·ViewModel 참조를 제거했다.
- ServerGetData에서 AuctionSnapshotParser와 AuctionPollingLifetime을 추출했다. 상태 변경은 기존 단일 소비자와 세대 검사 안에 유지했다. 나머지 상태 적용·재동기화 처리는 같은 데이터와 순서에 결합되어 있으므로 억지로 나누지 않았다.
- DisplaySelect에서 DisplayPanelStore와 RunningPageSchedule을 추출했다. ViewModel·두 비고 호스트의 해제 순서와 UTC 페이지 계산식을 보존했다. 페이지 고정·전환 제어는 기존 조정자에 유지한다.
- MainWindowViewModel은 이전 작업에서 보드·변경 감지 처리가 이미 분리되어 있어 이번에는 참조만 갱신했다. 바인딩·Command와 화면 반영 책임은 유지했다.
- Netty 접속 결과는 외부 DTO 대신 결과 문자열을 내부 메시지로 전달한다. 재시작은 메시지로 App에 요청한다. PageTimerSync는 UI dispatch 함수를 받아 기존 비동기 전달을 유지한다.
- Views 경로·화면 내용, Config·프로젝트·패키지·DB 정책·프로토콜 및 GIF 미지원 정책을 보존했다. 이동 후 비어 있는 기존 소스 디렉터리 12개만 제거했다.
