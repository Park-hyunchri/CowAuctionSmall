# Debug 출력·파일 로그 비동기 처리 개선 계획

> 문서 상태: **완료** · 정리일: 2026-10-01
> Debug 출력 작업자·파일 로그 비동기 처리 결과는 본문 11절에 있다. 실제 Visual Studio·전광판 성능 비교는 별도 확인 대상이다.
> 현재 동작: [기능 문서](../../기능/README.md) · [전체 목차](../../README.md) · [작업 기록](../../../WORKLOG.md)

- 요청: 수신 원문을 포함한 다른 Debug 출력과 파일 로그가 경매 처리를 지연시키지 않도록 변경 계획을 작성한다.

- 기준: 현재 작업 폴더의 기존 사용자 변경과 앞서 완료한 [SV/API 공통 갱신 개선](SV_API_공통변경감지_갱신개선계획_2026-09-22.md)을 유지한다.

## 1. 확인한 사실과 아직 확인하지 못한 원인

첨부 로그에 포함된 첫 SV 기록은 13:30:13.484, 마지막 SV 기록은 13:30:19.745로 약 6.261초 차이가 난다. 첨부에 포함된 SV는 500건이고 마지막 API 안내는 501건이다. 발췌 범위가 다를 수 있으므로 이 차이를 패킷 유실로 판단하지 않는다. 반복되는 약 20~22ms 간격은 관찰 사실이며, 그것만으로 디버거가 지연 원인이라고 확정하지 않는다.

| 확인 위치 | 현재 동작 | 의미 |
|---|---|---|
| [AuctionClientInboundDecoder.cs](../../../Infra/Netty/netty/handlers/AuctionClientInboundDecoder.cs) | 분기·전달 전에 원문을 `Debug.WriteLine`으로 출력 | 출력 호출 지연이 다음 메시지 처리에 영향을 줄 수 있음 |
| [DisplaySelect.cs](../../../Presentation/Display/DisplaySelect.cs), [AuctionContPanelViewModel.cs](../../../ViewModels/AuctionContPanelViewModel.cs) | 페이지 타이머·진행 화면에서도 직접 Debug 출력 | 수신 경로 외에 UI 작업의 출력 비용도 확인 필요 |

기록 시각은 소켓에 바이트가 도착한 시각이 아니라 디코더가 해당 문자열을 처리한 시각이다. API 수신 안내 역시 화면 적용 완료를 의미하지 않는다. 앞선 수십 ms의 합성 검증은 원문 Debug 출력·디버거·실제 전광판 렌더링을 제외했다. 이번에는 이 비용을 분리해서 측정한다.

## 2. 목표와 변경 범위

1. Netty·경매 상태 처리·UI 스레드는 출력 완료나 디스크 쓰기를 기다리지 않고 로그 등록 후 업무를 계속한다.
2. 수신 원문의 필드·빈 값·순서·발생 시각을 확인할 수 있게 한다.
3. 제품 코드의 직접 Debug 출력을 공통 경로로 옮긴다. 고빈도 반복 진단은 별도 옵션으로 제어한다.
4. Debug와 파일 기록의 큐를 분리해 한쪽의 밀림이 다른 쪽 소비를 직접 막지 않게 한다.
5. 큐와 메모리 사용에 상한을 두고, 로그 누락·기록 실패·종료 미기록 건수를 확인할 수 있게 한다.
6. 현재 NLog 6.2.0과 기존 파일 경로·업무 로그 내용을 우선 재사용한다. 패키지 업데이트는 기본 범위에 포함하지 않는다.

경매 신호 해석, API 조회 주기, SV/API 병합, 화면 알림 묶음 간격과 디자인은 변경하지 않는다. 기존 Netty 원문을 새로 파일에 저장하지 않는다. Visual Studio 자체의 모듈 로드 메시지와 외부 라이브러리 내부 출력은 제품의 공통 출력 함수로 제어할 수 있는 범위와 구분한다.

## 3. 처리 구조

```mermaid
flowchart LR
    A[Netty · 경매 처리 · UI] --> B[Debug 이벤트 등록]
    B --> C[용량 제한 Debug 큐]
    C --> D[단일 출력 작업 · 묶음 출력]
    D --> E[Visual Studio 출력]
    A --> F[기존 NLog 호출]
    F --> G[NLog AsyncWrapper 큐]
    G --> H[기존 로그 파일]
```

- 로그 한 건마다 `Task.Run` 또는 새 스레드를 만들지 않는다.
- Debug는 하나의 장기 실행 소비 작업으로 직렬 출력한다. 디버거 출력이 오래 막혀도 일반 ThreadPool 작업에 영향을 덜 주도록 전용 백그라운드 스레드를 초기 구현 후보로 삼는다.
- 파일은 NLog의 비동기 소비 기능을 사용한다. Debug 작업과 큐를 공유하지 않으며 파일 기록용 스레드·추가 중간 큐를 직접 중복 구현하지 않는다. NLog가 사용하는 작업 스케줄링을 전용 스레드 두 개라는 보장으로 표현하지 않는다.
- 비동기 전환도 문자열 생성·큐 등록·문맥 캡처 비용은 남는다. 경매 처리가 어떤 경우에도 지연되지 않는다고 보장하지 않는다.

## 4. Debug 출력 설계

### 4.1 이벤트와 순서

- 이벤트에는 발생 시각, 경과 시간 측정용 단조 증가 시계 값, 순번, 분류, 출력할 문자열을 담는다. 필요하면 호출 스레드 번호도 호출 시점에 캡처한다.
- Netty 원문은 디코더 진입 시점의 시각을 기록한다. 뒤늦게 출력하더라도 출력 시각으로 바꾸지 않는다. 이름도 실제 네트워크 도착 시각으로 오해하지 않게 설명한다.
- 순번 부여와 큐 등록을 같은 짧은 동기화 구간에서 수행한다. 이 구간에는 출력·파일 I/O·UI 호출이 없다. 여러 생산자의 전역 순서는 등록 순서로 정의하며, 단일 수신 흐름의 순서는 그대로 보존한다.
- 원문은 문자열 그대로 보관하고, 여러 원문을 묶어 출력해도 각 메시지 경계를 유지한다. 필드를 다시 조립하거나 빈 필드를 제거하지 않는다.
- UI 객체·변경 가능한 경매 객체·전체 응답 객체를 소비 작업까지 붙잡아 두지 않는다. 필요한 문자열과 값만 캡처한다.
- Debug와 파일 사이에는 출력 완료 순서를 보장하지 않는다. 비교가 필요한 공통 업무 이벤트는 발생 시각과 식별 가능한 진단 순번으로 연결한다.

### 4.2 큐와 묶음 출력

다음 값은 초기 후보이며 측정 후 조정한다.

| 항목 | 초기 후보 | 목적 |
|---|---:|---|
| Debug 대기 건수 | 2,048건 | 501건 새로고침과 후속 신호를 수용 |
| Debug 대기 문자열 총량 | 400만 문자 | 긴 메시지로 건수 제한만 우회하는 메모리 증가 방지 |
| 출력 묶음 간격 | 최대 약 50ms | 호출 횟수 축소와 확인 지연 절충 |
| 한 번의 출력 묶음 | 최대 128건, 약 64K 문자 목표 | 과도하게 큰 출력 호출 방지 |

- 첫 입력이 들어오면 소비를 깨우고, 현재 모인 메시지를 묶어 출력한다. 계속 수신된다는 이유로 출력 기한을 무한히 뒤로 미루지 않는다.
- 단일 메시지가 묶음 목표보다 크면 큐 총량 제한 안에서 해당 메시지 하나를 출력한다. 원문을 조용히 잘라내지 않는다.
- 큐 포화 또는 단일 메시지가 큐 총량 상한보다 큰 경우에는 새 로그 등록을 거절하고 누락 건수·순번 범위를 집계한다. 업무 호출자는 공간이 날 때까지 기다리지 않는다.
- 출력이 다시 가능해지면 누락 사실을 요약해서 알린다. 누락 요약 자체를 동일한 가득 찬 큐에 반복 등록하지 않는다.
- Debug 출력을 끈 상태는 의도적인 비활성화로 구분하고 과부하 누락 수와 섞지 않는다. 비활성화 시 불필요한 문자열 조합도 피한다.
- 기존 `Debug.WriteLine`의 Release 빌드 제외 성격을 보존한다. 공통 함수로 바꾼 뒤 Release에서 원문 수집·문자열 생성이 새로 활성화되지 않도록 검사한다.

### 4.3 출력 분류와 호출부 전환

| 분류 | 기본 방향 |
|---|---|
| Netty 원문 | 사용자가 요청한 Debug 원문 확인 유지, 비교 측정용 켜짐/꺼짐 지원 |
| 상태 변화·연결·오류 | 기존 의미와 메시지 유지, 공통 비동기 경로 사용 |
| 매 타이머 tick·반복 진행 화면 | 기존 `COWAUCTION_DIAGNOSTICS` 등 선택적 진단으로 제어 |
| 제품의 Console 출력 | 용도와 Release 동작을 확인해 전환 여부 결정, 중요한 오류를 Debug 전용으로 바꾸지 않음 |
| 검증 프로그램의 Console 결과 | 테스트 결과 출력이므로 그대로 유지 |

운영체제 전체 Debug 리스너를 가로채기보다 제품 코드의 호출부를 명시적으로 전환한다. 기존 주석·도달하지 않는 코드·무관한 파일 정리는 함께 수행하지 않는다.

## 5. 파일 로그 설계

### 5.1 NLog 비동기 래퍼

- 기존 `File` 대상을 명시적인 `AsyncWrapper`로 감싸고 로깅 규칙이 래퍼를 가리키게 한다. `NLogger`를 거치지 않는 `App`의 NLog 직접 호출도 같은 설정을 적용받도록 한다.
- 초기 후보는 `queueLimit=10000`, `batchSize=200`, `overflowAction=Discard`다. 세부 속성·누락 감지 이벤트는 설치된 NLog 6.2.0에서 확인한다.
- `Block`으로 큐가 빌 때까지 업무 스레드를 기다리게 하거나 `Grow`로 무제한 증가시키는 방식은 기본값으로 사용하지 않는다.
- `async="true"`만 추가하고 기본 누락 정책을 방치하지 않는다. 상한과 포화 처리를 명시하고 운영 중 확인할 수 있게 한다.
- 경로와 레이아웃은 기존 설정을 유지한다. Debug 큐의 원문을 파일 대상으로 자동 전달하지 않는다. 파일 보관·삭제 정책 확대도 이번 범위에 포함하지 않는다.

NLog의 비동기 처리, 묶음 기록, 포화 정책과 종료 Flush 필요성은 [공식 AsyncWrapper 문서](https://github.com/NLog/NLog/wiki/AsyncWrapper-target)를 기준으로 한다.

### 5.2 누락과 기록 실패

- 큐가 가득 찬 경우의 누락과 파일 쓰기 실패를 각각 집계한다. 이벤트 핸들러는 카운터만 갱신하며 같은 NLog 경로를 재귀 호출하지 않는다.
- 큐 누락/파일 오류 요약은 속도를 제한해 Debug 또는 기존 상태 안내 경로로 전달한다. 개별 실패마다 새로운 실패 로그를 만들어 폭주시키지 않는다.
- Warn/Error도 유한 큐와 디스크 장애 상황에서 무조건 보존된다고 약속하지 않는다. 정상 부하에서는 모두 기록되고, 과부하에서는 누락 여부가 드러나는 것을 초기 기준으로 한다. 중요 로그 무손실 보장이 별도로 필요하면 우선순위 큐·별도 저장 정책을 후속 범위로 설계한다.
- 파일 로그는 큐 건수뿐 아니라 실제 대기 메모리도 측정한다. 대형 원문을 추가하지 않는 현행 범위를 지켜 문자열 크기 급증을 방지한다.
- `autoReload`에 따른 설정 재적용 시 누락 감지 구독 중복과 이전 큐 수명을 검사한다.

## 6. 시작·종료 수명

1. 시작 시 첫 제품 로그보다 먼저 공통 Debug 출력과 NLog 설정을 준비한다. 초기화 실패가 다시 같은 로거를 호출하는 순환을 만들지 않는다.
2. 정상 종료 시 Netty·업무 서비스·UI 타이머 등 로그 생산자를 먼저 정리한다. 기존 제한 시간을 둔 서비스 종료 방식을 유지한다.
3. 정리 중 생긴 로그와 마지막 종료 메시지를 등록한 뒤 로그 큐의 새 등록을 닫는다.
4. Debug 대기 출력과 NLog Flush를 제한 시간 안에서 마무리한다. 로그 정리의 전체 추가 예산은 초기 2초 후보이며 단계별 대기가 무제한 누적되지 않게 한다.
5. Flush 후 NLog Shutdown을 수행하고 소비 작업·이벤트 구독을 해제한다. 파일 대상 정리까지 포함한 종료 시간을 검증한다.
6. 종료·재시작 중 중복 호출은 안전하게 처리한다. 종료 후 새 타이머나 작업을 만들지 않는다.

Debug 출력 호출 자체가 디버거 안에서 막히면 취소 토큰만으로 강제 중단할 수 있다고 가정하지 않는다. 해당 작업을 무기한 Join하지 않고, 종료 예산 초과 시 남은 건수를 미기록으로 집계한다. 소비 작업은 Dispatcher를 호출하지 않아 UI 종료와 교착하지 않게 한다. 강제 종료·프로세스 충돌·디스크 장애에서 모든 로그 보존은 보장할 수 없다.

## 7. 예상 변경 파일

신규 이름은 구현 책임을 나타내는 제안이다. 기존 구조에 맞춰 최소한으로 확정한다.

### 9.2 성능 비교

- 같은 입력·설정·빌드에서 Debug 출력만, 파일 기록만, 둘 다 켬, 둘 다 끔을 비교한다. 진단용 파일 기록 끄기는 별도 검증 설정에만 적용한다.
- Visual Studio 디버거 연결/미연결을 나누고 각 조건을 반복 측정한다. 출력 창 화면 표시를 숨기는 것과 로그 생성 자체를 끄는 것을 같은 조건으로 취급하지 않는다.
- 최초 실행과 준비 후 반복 실행을 분리해 초기 로드·JIT 비용을 기록한다.
- 측정 항목: 로그 등록 시간, 큐 최대 건수/문자량·최장 대기, 출력 호출 수/시간, 파일 기록 완료 시간, 누락 수, 경매 입력 큐 대기, SV 상태 반영, 첫/마지막 UI 적용, CPU·할당량이다.
- 경과 시간은 `Stopwatch` 계열로 측정하고 벽시계는 사람이 보는 발생 시각에 사용한다. 측정 결과는 주기적 요약으로 출력하며 매 이벤트 측정 로그를 추가해 부하를 키우지 않는다.
- 디코더 시각만으로 서버 전송 완료를 판단하지 않는다. 실제 소켓 도착까지 구분하려면 별도 검증 환경의 송신 측 시각·수신 계층 계측이 필요하다.
- 통과 기준은 정상 501건 입력에서 로그 누락 없이 원문을 보존하고, 의도적으로 느리게 만든 출력 때문에 업무가 같은 시간만큼 대기하지 않는 것이다. 실제 화면 지연 개선은 별도 실측 결과로 판단한다.
- 6.261초를 특정 수치 이하로 줄인다고 선약하지 않는다. Visual Studio 자체 부담·디스크 자원 경쟁·UI 렌더링·서버 전송 지연은 비동기 로그만으로 제거되지 않을 수 있다.

### 9.3 구현 후 실행할 명령

아래 명령은 향후 구현 검증용이며 이번 문서 작성에서는 실행하지 않는다. 실행 중인 앱의 출력 파일을 덮지 않도록 TEMP 경로를 사용한다.

```powershell
$debugOutput = Join-Path $env:TEMP 'CowAuction-LoggingValidation-Debug'
$releaseOutput = Join-Path $env:TEMP 'CowAuction-LoggingValidation-Release'
$historyOutput = Join-Path $env:TEMP 'CowAuction-LoggingValidation-History'
dotnet build Validation/ReferenceAdoptionChecks/ReferenceAdoptionChecks.csproj --no-restore "-p:OutputPath=$debugOutput" -v:q
dotnet "$debugOutput\ReferenceAdoptionChecks.dll" all
dotnet build CowAuctionSmall.csproj -c Release --no-restore "-p:OutputPath=$releaseOutput" -v:q
dotnet build Validation/OwnerHistoryChecks/OwnerHistoryChecks.csproj --no-restore "-p:OutputPath=$historyOutput" -v:q
dotnet "$historyOutput\OwnerHistoryChecks.dll" --offline
```

새 로그 검사를 `all`에 연결한다. 실제 Visual Studio 출력과 전광판의 체감 지연 비교는 오프라인 회귀 통과와 별도로 기록한다.

## 11. 구현·검증 결과 — 2026-09-22

### 실제 구현

- [AsyncDebugOutput.cs](../../../Infra/Logging/AsyncDebugOutput.cs): 전용 백그라운드 스레드 하나가 Debug 큐를 소비한다. 최대 2,048건·400만 문자 대기 큐, 최대 128건·약 64K 문자 묶음, 최초 입력 기준 최대 약 50ms 대기를 적용했다. 실제 출력이 막히면 이보다 늦어질 수 있다.
- 원문은 재조립하지 않고 시각·등록 순번과 함께 출력한다. 예시는 `[시각] [#순번] [Netty 수신] SV|...` 형식이다. 시각은 디코더 처리 시각이며 실제 소켓 도착 시각을 뜻하지 않는다.
- 제품의 활성 Debug 호출은 공통 경로로 전환했다. 타이머 tick·진행 화면·페이지 회전·반복 Ping·조회 주기 진단은 선택적으로 출력한다. 저빈도 Console 설정 안내와 연결/시작 오류는 기존 Release 가시성을 유지했다.
- 환경 변수 `COWAUCTION_DEBUG_OUTPUT=0`은 제품 Debug 출력을 끈다. 기본값은 켜짐이며, `COWAUCTION_DIAGNOSTICS=1`로 반복 진단을 켠다. 환경 변수는 시작 시 읽는다. 보간식은 비활성화 시 평가를 건너뛰고 Release에서는 조건부 Debug 호출이 제거된다.
- [LoggingLifetime.cs](../../../Infra/Logging/LoggingLifetime.cs)의 `ObservedAsyncTarget`은 NLog `AsyncTargetWrapper`를 상속한다. 자체 파일 큐를 추가하지 않고 NLog의 큐·묶음 기록을 사용하며 등록·쓰기 완료·실패·포화 누락·미완료를 집계한다.
- `NLog.config`는 `ObservedAsyncWrapper`에 10,000건·200건 묶음·Discard를 명시했다. 기존 File 대상의 경로·레이아웃은 유지했다. 새 별칭은 앱에서 설정을 읽기 전에 등록하고, 설정 재적용도 같은 집계 값을 사용한다.
- 파일 실패·누락 요약은 최대 5초 간격으로 Debug와 기존 상태 안내에 전달한다. 실패 콜백은 카운터만 갱신하고 NLog를 재귀 호출하지 않는다. 종료 직전에 이미 시작된 안내 콜백은 끝날 수 있으나 UI 수신부가 종료 상태를 확인한다.
- 앱은 서비스 정리·마지막 로그 이후 파일 Flush/Shutdown과 Debug 종료에 총 2초의 추가 대기 예산을 적용한다. NLog 정리는 백그라운드에서 진행하고 자동 ProcessExit Shutdown의 중복 대기를 해제했다.
- Debug의 메모리 상한은 대기 큐 기준이며 소비 중인 묶음 하나와 문자열 조합 공간은 별도다. 파일 `Pending`은 큐 대기와 기록 중인 건수를 포함한다. 종료 제한을 넘긴 건수는 미완료이며 실제 유실 확정으로 표현하지 않는다.
- Debug 원문을 파일에 추가 저장하지 않았다. 기존 패키지·경매 처리·화면 갱신 정책은 유지했다.

### 검증 결과

- 별도 TEMP 출력에서 Debug·Release 빌드 성공: 각각 오류 0개·경고 84개. 시작 전 기준 Debug도 경고 84개였다.
- Debug `ReferenceAdoptionChecks all`: **1,312개 통과**. 기준 1,253개에 로그 검사 59개를 추가했다.
- Release `ReferenceAdoptionChecks logging`: **59개 통과**. Release의 Debug 호출 제거·문자열 평가 생략을 포함한다.
- 느린 Debug/파일 대상을 막은 상태에서 생산자 완료, 독립 Debug 소비, 정확한 포화 집계, 쓰기 실패, XML 재적용, 종료 시간 제한을 검사했다. 실제 TEMP 파일로 501건·최종 Warn/Error·재적용 후 로그의 순서와 기록도 확인했다.
- 상세 명령·파일 목록·이력 회귀 결과는 [WORKLOG](../../../WORKLOG.md), 검사 설명은 [검증 README](../../../Validation/ReferenceAdoptionChecks/README.md)에 기록한다.

### 측정과 확인 한계

Debug 최종 검사에서 501건을 출력할 때 호출마다 지연을 주는 동기 가짜 대상은 등록 완료까지 약 7,586ms·501회 출력이었고, 비동기 방식은 등록 약 0.64ms·전체 배출 약 59.44ms·4회 출력·누락 0건이었다. 가짜 대상의 1ms sleep 요청이 해당 Windows 환경에서 약 15ms로 실행된 결과다. **실제 Visual Studio의 6.261초 지연이 이 수치로 줄었다는 검증은 아니다.**

| 합성 출력 조건 | 501건 등록 시간 | 생산자 스레드 할당량 |
|---|---:|---:|
| 모두 끔 | 0.01ms | 0바이트 |
| Debug만 | 0.70ms | 40,416바이트 |
| 파일만 | 0.74ms | 144,304바이트 |
| 둘 다 | 1.62ms | 184,720바이트 |

위 파일 비교도 묶음당 지연을 주는 가짜 대상이며, 실제 파일 성공 검사는 별도로 수행했다. 수치는 전체 프로세스 CPU·메모리 사용량이나 전광판 표시 지연을 뜻하지 않는다. 정상 종료 시 배출, 과부하 시 누락 표시를 확인했으며 무제한 부하에서 Warn/Error까지 무손실을 보장하지 않는다.

앱 재빌드·재실행 후 실제 Visual Studio에서 원문 확인·새로고침 체감 시간·파일 기록을 비교해야 한다. 운영 서버 연결·실제 전광판·배포·commit·push는 수행하지 않았다.
