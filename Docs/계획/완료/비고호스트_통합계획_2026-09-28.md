# 128×128 비고 호스트 통합 계획

> 문서 상태: **완료** · 정리일: 2026-10-01
> 공통 호스트·스크롤 구현 결과는 본문 9절에 있다. 당시 CowHistorySearchRun의 별도 리소스 오류는 2026-09-28 후속 작업에서 수정됐으며, 당시 실패 기록은 보존한다.
> 현재 동작: [기능 문서](../../기능/README.md) · [전체 목차](../../README.md) · [작업 기록](../../../WORKLOG.md)

- 작성일: 2026-09-28
- 상태: 구현 완료. 공통 호스트·스크롤 검증 통과. 아래 별도 화면 오류는 당시 검사 결과이며 후속 처리 사항은 상단 안내 참조.
- 요청: `RunningNoteHost128`과 `RunningNoteHost128_Running`의 중복을 정리하기 전에 변경 계획을 작성한다.
- 승인 범위: 계획 작성 후 사용자의 “좋아 진행하자”로 아래 소스 변경·검증 실행 승인.

## 1. 조사 결과와 목표

두 호스트는 본문 페이지를 담고 하단의 친자 배지·원본 비고·소유주 이력과 스크롤을 표시한다. 낙찰자 `Bidder` 자체를 표시하는 컨트롤은 아니다.

| 항목 | RunningNoteHost128 | RunningNoteHost128_Running |
|---|---|---|
| 현재 사용 | 낙찰·유찰 | 대기·진행 |
| 호스트 DataContext | gValues 스냅샷 | AuctionContPanelViewModel |
| 배지 입력 | 개체 속성 직접 바인딩 | Canvas에서 CowInfo로 DataContext 변경 |
| 비고 입력 | Note·NoteChangeOwner 직접 바인딩 | 루트 ViewModel의 Note·NoteChangeOwner 참조 |
| 공통 기능 | PageContent, 배지, NoteText, FlowTextAnimation, Loaded/Unloaded 정리 | 동일 |
| 개체 교체 | 개체 식별값 비교 후 애니메이션 해제 | 동일 처리에 진행 ViewModel의 위치 초기화 추가 |

레이아웃과 애니메이션 관리가 거의 같고, 주된 차이는 데이터 진입 경로와 스크롤 상태 연결이다. 결과 화면은 이미 `AuctionItemDisplayViewModel`을 받지만 결과용 비고 호스트는 그 안의 스냅샷을 따로 받는다.

**목표:** 호스트를 하나로 통합하고 표시 입력을 명시한다. 대기·진행·낙찰·유찰에서 비고·배지의 표시 및 갱신 규칙을 공유하며 기존 화면과 스크롤 동작을 보존한다.

## 2. 변경 범위

### 포함

- 기존 `RunningNoteHost128`을 공통 호스트로 사용한다.
- 공통 호스트의 표시 입력, 개체 변경 감지, 애니메이션 수명 주기를 통일한다.
- 진행·결과 화면의 연결과 패널 상태 저장·해제 코드를 변경한다.
- 연결 및 검증 코드 이관 후 `_Running` 호스트의 XAML·코드 파일을 제거한다.
- 기존 오프라인 검증을 단일 호스트와 두 입력 방식에 맞춰 갱신한다.

### 유지

- 이번에는 남는 호스트의 이름·폴더를 바꾸지 않는다.
- 본문 페이지의 DataContext와 개별 화면의 바인딩·레이아웃을 유지한다.
- 비고 원문·이력 문구 생성 및 NoteText의 색상 구분을 유지한다. 비고 내용으로 이력 여부를 추측하거나 중복 문구를 제거하지 않는다.
- 배지 위치·색상·크기, 비고 영역 크기·폰트·속도·기존 스크롤 시작 조건을 유지한다.
- 낙찰자 이름, 성별, 가격, 통신·파싱·API·캐시·설정 XML은 변경하지 않는다.
- 다른 화면도 사용하는 `FlowTextAnimation`과 ViewModel의 위치 저장 기능을 일괄 개편하거나 삭제하지 않는다.

## 3. 공통 호스트의 입력 설계

호스트가 DataContext의 구체 타입을 검사해 표시 경로를 선택하지 않도록 명시적인 의존성 속성을 사용한다.

| 속성 | 형식 | 역할 |
|---|---|---|
| PageContent | object | 기존 본문 화면. 현재 속성 유지 |
| ItemDisplay | AuctionItemDisplayViewModel, null 허용 | 모든 상태에서 동일하게 받는 표시 데이터 |
| ScrollOwner | AuctionContPanelViewModel, null 허용 | 진행 화면에서 기존 비고 위치 저장 기능을 연결하는 선택 입력 |

- 비고·배지 영역만 `ItemDisplay.Snapshot`에 바인딩한다. 친자 배지, `Note`, `NoteChangeOwner` 모두 동일한 스냅샷을 사용한다.
- `PageContent` 영역은 비고 영역의 DataContext 변경에 영향을 받지 않도록 분리한다.
- 진행 본문은 기존 `AuctionContPanelViewModel`, 결과 본문은 기존 `AuctionItemDisplayViewModel`을 계속 받는다.
- 호스트는 별도의 표시 ViewModel을 생성하거나 스냅샷을 다시 복제하지 않는다. 호출 측이 이미 생성한 `ItemDisplay`를 공유한다.
- `ScrollOwner`가 있으면 기존 ViewModel 연동형 FlowTextAnimation을 사용하고, 없으면 기존 독립형을 사용한다. 상태별 차이는 이 입력으로 한정한다.
- `ScrollOwner`의 변경은 이전 위치 저장 대상과 이벤트가 남지 않도록 애니메이션을 정리한 뒤 적용한다. 진행 ViewModel의 Dispose 책임은 기존 패널 관리자가 유지한다.
- 비고·배지 표시는 호스트 DataContext에 의존하지 않는다. DataContextChanged로 개체 교체를 판단하던 코드는 ItemDisplay 변경 처리로 대체한다.

새로운 업무 로직이나 별도의 광범위한 ViewModel 계층은 추가하지 않는다. 스크롤 상태 추상화까지 확장하는 작업은 이번 범위에 포함하지 않는다.

## 4. DisplaySelect 연결 방식

### 대기·진행

- 진행 ViewModel을 만든 시점에 공통 호스트의 `ScrollOwner`를 해당 ViewModel로 연결한다.
- `ItemDisplay`는 해당 ViewModel의 `ItemDisplay` 속성에 단방향 바인딩한다. `UpdateCowInfo()`의 기존 PropertyChanged를 이용한다.
- 진행 ViewModel이 교체되면 이전 바인딩 원본을 해제하고 새 원본으로 연결한다.
- 페이지 전환 시 PageContent만 바꾼다. 같은 호스트의 ItemDisplay·애니메이션을 불필요하게 초기화하지 않는다.
- 기존의 호스트 적용 조건을 유지한다. 128×128이고 염소·말이 아닌 경우에 적용하며 `AuctionRunning2_3`·`AuctionRunning4`의 제외 규칙도 유지한다.

### 낙찰·유찰

- 본문에 전달하는 `soldDisplay`·`unSoldDisplay`를 호스트 ItemDisplay에도 동일하게 전달한다.
- 최초 생성뿐 아니라 같은 결과 상태에서 데이터만 갱신되는 빠른 경로도 함께 수정한다.
- 진행용 ItemDisplay 바인딩이 남아 있다면 먼저 해제한다. ScrollOwner는 null로 설정한다.
- 기존 해상도·축종 조건과 결과 화면 선택 분기는 유지한다.

### 패널 상태

- `PanelDisplayState.RunningNoteHost` 필드 하나로 관리한다.
- `RunningNoteHost_Running` 필드를 제거한다.
- `ClearRunning`, 로고 전환, 패널 해제 및 Dispose에서 PageContent·ItemDisplay 바인딩·ItemDisplay 값·ScrollOwner·남은 DataContext 참조를 해제한다.
- 상태 전환 시 호스트 재생성 여부는 기존 수명 주기 정책을 따른다. 통합을 이유로 상태 간 스크롤 위치까지 새롭게 공유하지 않는다.

## 5. 갱신과 스크롤 동작

개체 동일성은 현재 구현처럼 `TraceNumber + SipNumber + SpaceIndex`의 각 값을 비교한다. 객체 참조만 달라졌다는 이유로 스크롤을 재시작하지 않는다.

| 상황 | 처리 기준 |
|---|---|
| 같은 개체·같은 비고를 새 객체로 수신 | 표시 입력을 갱신하되 기존 애니메이션과 위치 유지 |
| 같은 개체의 가격·다른 정보만 변경 | 비고 스크롤 유지 |
| 같은 개체에서 PageContent 변경 | 비고 애니메이션 유지 |
| 비고 호스트 제외 페이지를 거쳐 복귀 | 기존 진행 ViewModel에 저장한 위치 복원 |
| 다른 개체로 교체, 비고 문구는 동일 | 기존 위치를 초기화하고 새 개체 기준으로 시작 |
| Note 또는 NoteChangeOwner 변경 | 두 값 적용 후 최종 표시 텍스트를 기준으로 재평가. 표시 문구 변경 시 재시작 |
| 문구는 같고 원본·이력의 구성이 변경 | NoteText 색상·출처 표시 갱신. 텍스트가 같으면 불필요한 위치 초기화 방지 |
| 친자 배지 표시·해제·색상 변경 | 동일 스냅샷으로 배지와 비고 배치 갱신, 이전 개체의 배지 잔재 제거 |
| 빈 비고·이력만 존재·모두 삭제 | 기존 NoteText 규칙 유지, 이전 텍스트 잔재 제거 |
| ItemDisplay가 null | 배지·문구와 애니메이션 정리. 이후 유효 입력으로 복구 가능 |
| Unloaded·패널 해제 | 예약 Dispatcher 작업 취소, 클록·이벤트 해제 |
| 동일 데이터로 다시 Loaded | 기존 진행 위치 저장 정책을 유지하며 필요한 애니메이션만 생성 |

- ItemDisplay 교체 시 이전·새 스냅샷을 비교하고 바인딩이 적용된 후 애니메이션을 초기화한다.
- 예약된 초기화 작업은 하나로 합치고 실행 시 현재 입력·로드 상태를 확인한다. 이미 교체된 입력으로 애니메이션이 시작되지 않게 한다.
- 기존 NoteText 및 FlowTextAnimation의 텍스트 변경 감지를 활용한다. 중복 초기화나 Note/History 중간 상태를 최종값으로 저장하는 문제는 실제 WPF 검증으로 확인한다.

## 7. 단계별 구현 순서

1. **기준 확보**: git status·diff와 현재 호스트·호출부를 확인하고 기존 사용자 변경을 보존한다. 기존 바인딩·스크롤 검사의 실행 가능 상태를 확인한다.
2. **공통 호스트 구현**: ItemDisplay·ScrollOwner 입력과 개체 변경 처리를 추가하고 합성 데이터로 진행/결과 두 입력 방식을 확인한다.
3. **호출부 이관**: 대기·진행과 낙찰·유찰, 동일 상태 데이터 갱신, 패널 상태·정리 경로를 하나의 호스트로 연결한다.
4. **중복 제거**: `_Running` 생성·타입·필드 참조가 없어졌는지 확인한 뒤 중복 XAML·코드 파일을 제거하고 검증 코드를 갱신한다.
5. **검증 및 기록**: 아래 검증을 실행하고 사용자 변경과 이번 변경을 구분하여 최종 diff 및 WORKLOG를 정리한다.

## 8. 검증 계획과 완료 조건

### 필수 검증

- Debug 빌드 및 기존 `binding`, `stage4`, OwnerHistoryChecks의 `--scroll-offline` 실행.
- 실제 WPF 클록으로 위 갱신 표의 위치 유지·재시작·중지·복귀를 검사한다. 단순 속성 존재 검사로 대체하지 않는다.
- 진행 본문의 IsRunning·ItemDisplay·CowInfo 바인딩과 낙찰·유찰 본문의 기존 바인딩 유지 확인.
- 같은 상태에서 새로고침·이력 비동기 반영·비고 삭제·개체 교체 시 갱신 확인.
- 진행 → 낙찰 → 유찰 → 대기, 로고 전환, 반복 진입, 초기화 예약 직후 Unloaded를 확인한다.
- 호스트 적용 대상·제외 페이지·염소·말과 다른 해상도의 기존 표시 경로가 유지되는지 검사한다.
- 제거된 `_Running` 타입·필드가 실행 코드와 검증 코드에 남지 않았는지 검색한다. 과거 작업 기록의 언급은 보존한다.

### 검증 환경의 기존 이슈

- 앞선 폴더 이동 검증 당시 사용자 추가 화면으로 진행 화면이 33개가 되어, `binding`의 고정 32개 조건에서 중단된 이력이 있다. 구현 시작 시 최신 화면 수와 검증 의도를 확인하고, 단순히 검사를 생략하거나 무조건 통과하도록 완화하지 않는다.
- 당시 별도 작업 중인 CowHistorySearchRun의 옛 네임스페이스 참조로 일반 빌드가 실패한 이력도 있다. 최신 상태를 다시 확인하고 이번 통합으로 인한 오류와 구분한다. 사용자 작업을 임의로 되돌리지 않는다.
- 기존 WPF 중간 산출물 문제로 검증이 어려우면 별도 임시 중간·출력 경로를 사용한다. 기존 bin·obj를 수동 삭제하지 않는다.
- 계획 작성 단계에서는 빌드·테스트·운영 앱 실행을 수행하지 않는다. 후속 구현의 기본 검증은 합성 데이터와 오프라인 WPF로 수행한다.

### 완료 조건

- 실행 코드의 호스트 클래스와 패널 저장 필드가 각각 하나다.
- 두 상태 계열이 동일한 ItemDisplay 입력을 사용하며 비고·배지에 DataContext 타입별 분기가 없다.
- 표시 문구·색상·배지·본문 바인딩과 개체별 스크롤 유지/초기화 동작을 보존한다.
- 이벤트·클록·예약 작업·이전 ViewModel 참조가 해제된다.
- 빌드·검증 결과와 외부 요인으로 미확인된 범위를 구분해 보고한다.
- 중복 코드 감소가 주된 효과다. 두 호스트가 항상 동시에 동작한 것은 아니므로 메모리·CPU 절감률을 사전에 단정하지 않는다.
