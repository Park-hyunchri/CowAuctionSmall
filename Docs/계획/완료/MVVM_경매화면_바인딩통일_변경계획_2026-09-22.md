- 목적: 대기·진행·낙찰·유찰 화면에서 경매품 표시 경로를 통일하고, 데이터 갱신과 화면 동작의 책임을 분명하게 한다.

## 2. 목표 구조와 바인딩 규칙

### 2.1 역할 구분

- Model (`gValues`): 경매품 데이터와 기존 파생 데이터 제공.
- ViewModel (`AuctionContPanelViewModel`): 현재 경매품 참조, 진행 상태, 표시용 상태, 갱신 알림과 기존 페이지·비고 상태 관리.
- View (XAML): 데이터 표시, 스타일, 애니메이션 연결.
- 표시 조정 코드 (`DisplaySelect`, `DisplayPanelStore`): 화면 선택·재사용·데이터 연결·수명 관리. 기존 역할을 유지한다.

이번 범위에서 전체 MVVM 구조를 새로 만들거나 기존 표시 조정 코드를 모두 ViewModel로 옮기지 않는다.

### 2.2 영역별 DataContext

| 영역 | DataContext | 경로 예시 |
| --- | --- | --- |
| 대기·진행 UserControl 루트 | 기존 ViewModel | `IsRunning`, 화면 동작 관련 속성 |
| 대기·진행 경매품 표시 영역 | 루트 ViewModel의 `CowInfo` | `EntityNumberShort`, `LowestPrice`, `Weight` |
| 낙찰·유찰 경매품 표시 영역 | 기존 `gValues` | `EntityNumberShort`, `BidPrice`, `Bidder` |
| 공통 경매품 배지 | 호출자가 제공한 `gValues` | `Is_Nh_QQuri` |
| 사용자 컨트롤 자체 속성 | 명시적인 컨트롤 참조 | 기존 `PageContent` 등 |

진행 화면 전환 예시:

```xml
<UserControl x:Name="Root">
    <Grid>
        <!-- 기존 진행 상태 바인딩은 ViewModel 영역에 유지 -->

        <Grid DataContext="{Binding CowInfo}">
            <TextBlock Text="{Binding EntityNumberShort}" />
            <TextBlock Text="{Binding LowestPrice}" />
        </Grid>
    </Grid>
</UserControl>
```

위 코드는 구조 설명용이다. 실제 적용 시 기존 Grid·Canvas를 활용하고 좌표·크기·겹침 순서를 보존한다. 추가 컨테이너가 필요한 경우 렌더링 결과를 비교한다.

### 2.3 예외 처리 규칙

1. `CowInfo.XXX`는 경매품 영역에서 `XXX`로 변경한다.
2. 경매품 객체 전체를 받는 `{Binding CowInfo, Converter=...}`는 해당 영역에서 `{Binding Converter=...}`로 바꾼다. Converter에 계속 `gValues`가 전달되는지 확인한다.
3. `DataTrigger`, `MultiBinding`, Style, 첨부 속성, 공통 컨트롤도 검사한다. 단순 문자열 일괄 치환으로 완료하지 않는다.
4. `IsRunning`처럼 Model과 ViewModel에 같은 이름이 있는 속성도 의미와 알림 주체를 구분한다. 기존 진행 테두리 동작은 ViewModel의 알림을 유지한다.
5. 경매품 영역 안에서 ViewModel 속성이 필요하면 루트 ViewModel을 명시적으로 참조한다. 중첩 UserControl에서 가장 가까운 `UserControl`이 원하는 루트라는 가정을 하지 않는다. 각 이름 범위에서 유효한 `ElementName` 또는 구체적인 상위 타입을 사용한다.
6. 루트 `DataContext`를 자기 자신으로 덮어쓰거나, `CowInfo`가 있으면 쓰고 없으면 직접 객체를 쓰는 임시 호환 분기를 남기지 않는다.
7. 공통 컨트롤 변경은 호출부와 함께 전환한다. 특히 `NhQquriBadge`는 직접 경매품 객체를 받는 규칙으로 맞춘다.

## 3. 갱신 계약: 바인딩 경로보다 먼저 보장할 사항

`gValues`는 개별 속성 변경을 통지하지 않는다. 기존 `CowInfo.XXX` 경로를 경매품 영역의 직접 바인딩으로 바꾸면, `PropertyChanged(nameof(CowInfo))`만 발생시키고 같은 참조를 다시 제공하는 방식으로는 내부 표시 갱신을 보장할 수 없다.

기본 구현 방향은 다음과 같다.

1. SV/API 공통 변경 감지 결과에서 변경이 없는 경매품은 기존처럼 UI 갱신을 생략한다.
2. 표시할 내용이 바뀌면 기존 전달 경로에서 새 경매품 객체가 제공되는지 확인한다.
3. 이미 새 객체가 제공되면 그대로 사용한다. 같은 참조를 수정하는 경로가 있으면 **화면에 전달하는 경계에서 변경된 경매품의 스냅샷을 교체**하여 새 참조를 보장한다.
4. 진행 ViewModel의 `CowInfo` 변경 알림으로 경매품 표시 영역의 `DataContext`가 교체되도록 한다. 낙찰·유찰도 변경된 표시 객체로 교체한다.
5. `Note`, `NoteChangeOwner`, `DisplayNote`, 친자 표시 등은 이전 표시 스냅샷을 기준으로 변경을 판단한다. 원본이 먼저 변해 비교 기준까지 달라지는 경우를 검증한다.
6. UI 객체와 바인딩 소스 연결은 UI 스레드에서 처리한다. Netty/API 수신 경로에서 직접 화면을 조작하지 않는다.

화면에 공개한 `CowInfo`와 결과 화면의 `DataContext`는 읽기 전용 스냅샷으로 취급한다. 같은 참조 갱신 검증은 원본 수신 객체를 수정한 뒤 갱신 진입점에 다시 전달하는 경우를 뜻한다. 공개한 표시 객체를 직접 수정하는 방식은 사용하지 않는다. `gValues`의 값 비교 때문에 이미 수정된 표시 객체와 복제본이 같다고 판단되어 WPF의 자식 바인딩 갱신이 생략될 수 있다. 비고 편집은 ViewModel의 `Note` setter를 사용한다.

모든 속성을 ViewModel에 복제하거나 `gValues` 전체를 알림 모델로 전환하는 작업은 기본안에 포함하지 않는다. 변경 없는 501개 품목까지 매번 복제하는 방식도 사용하지 않는다. 기존 변경 감지·표시 묶음 처리를 유지하고 필요한 경계에서만 교체한다.

## 5. 단계별 실행 계획

각 단계는 해당 단계의 검증을 통과한 뒤 다음으로 진행한다. 구현 승인 후 이 순서로 이어서 수행하며 단계마다 같은 승인을 반복해서 요청하지 않는다.

### 1단계 — 기준 상태와 검사 범위 확정

- 기존 미커밋·미추적 변경을 보존하고 구현 시작 시점의 관련 diff를 확인한다.
- 화면별로 루트 컨텍스트, 경매품 영역, ViewModel 전용 참조, Converter 입력, 코드 비하인드 의존성을 기록한다.
- 실제 화면 선택 분기와 각 해상도·페이지·품종 조합을 검사 목록에 반영한다.
- 기존 오프라인 UI 검사의 컨텍스트를 실제 제품과 맞춘다. 현재 `UiChecks`에는 진행 화면에 `gValues`를 직접 넣고 비고만 검사하는 경우가 있어 전체 바인딩 정상 여부를 보장하지 못한다.
- 완료 기준: 변경 대상과 기존 오류가 구분되고, 잘못된 경로를 검출할 수 있는 검증 방법이 준비됨.

### 2단계 — 갱신 경계와 대표 화면 전환

- `CowInfo` 교체와 표시 스냅샷 갱신 계약을 먼저 적용·검증한다.
- 공통 배지 의존성이 없는 대표 진행 페이지 1개를 골라 내부 표시 영역을 전환한다.
- `HoengseongUnSold`의 잘못된 경로도 수정하고 유찰 화면과 동일한 속성 경로가 동작하는지 확인한다.
- 가격만 변경, 같은 출품의 개체 교체, 비고 변경, 변경 없는 재수신을 검사한다.
- 완료 기준: 표시 값이 실제로 바뀌고, 진행 테두리와 비고 동작이 유지됨.

### 3단계 — 128×128 화면과 공통 컨트롤 전환

- 기본·사업장별 진행 페이지의 경매품 영역을 전환한다.
- `NhQquriBadge`와 호출부를 함께 변경한다.
- 진행 비고 호스트의 표시 영역을 정리하고 친자·비고·이력·스크롤 갱신을 확인한다.
- 진행용/결과용 호스트를 하나의 클래스로 합치는 구조 변경은 이번 필수 범위에서 제외한다.
- 완료 기준: 대상 페이지의 직접 속성 바인딩과 공통 배지가 정상이며, ViewModel 전용 바인딩이 정확한 원본을 참조함.

### 4단계 — 나머지 해상도 전환

- 128×64 → 160×64 → 320×64 순으로 적용한다.
- 페이지별 루트 ViewModel, 코드 비하인드의 비고 위치 저장, 애니메이션 연결을 보존한다.
- 페이지 수·순서 및 염소·말 등 분기별 화면을 확인한다.
- 완료 기준: 해상도별 데이터 표시·테두리·비고·페이지 전환 회귀가 없음.

### 5단계 — 결과 화면 및 상태 전환 통합 검증

- Sold·UnSold 전체의 직접 바인딩을 점검하고 남은 잘못된 경로만 수정한다.
- 대기 → 진행 → 낙찰/유찰 → 재경매 → 로고 → 재진입을 검사한다.
- 캐시 재사용 시 데이터 교체, 이전 비고 제거, 반복 Loaded/Unloaded, 이벤트·타이머·애니메이션 해제를 확인한다.
- 완료 기준: 이전 경매품의 값·강조·친자 배지·스크롤 상태가 잘못 남지 않음.

### 6단계 — 최종 검증과 작업 기록

- Debug·Release 빌드 및 관련 오프라인 회귀 검사를 실행한다.
- `CowInfo` 잔여 검색은 허용된 컨텍스트 연결 경계와 C# 내부 사용인지 검토한다. 단순히 검색 결과가 0개인 것을 목표로 삼지 않는다.
- 최종 diff에서 기존 사용자 변경과 이번 구현을 구분한다.
- 구현·검증이 완료되면 `WORKLOG.md`에 실제 변경과 결과, 수동 확인 항목을 기록한다.

## 6. 검증 기준

| 항목 | 합격 기준 |
| --- | --- |
| 바인딩 오류 | 실제 계약으로 생성한 대상 화면에서 경로·Converter 오류가 없고 기존 유찰 오류가 재현되지 않음 |
| 표시 값 | 합성 개체번호·예정가·낙찰가·비고가 예상 Text/Visibility/Style에 반영됨 |
| 객체 교체 | 새 객체 전달 후 표시 영역이 새 값을 표시함 |
| 같은 참조 변경 | 지원되는 갱신 진입점을 통과하면 표시 스냅샷 교체 등으로 값이 반영됨 |
| 무변경 | 동일 데이터 반복 수신 시 불필요한 화면 재생성·비고 재시작이 없음 |
| 상태 알림 | 데이터 변경 없이 진행 상태만 바뀌어도 테두리 등 상태 표시가 반영됨 |
| 비고·친자 | 일반 비고/이력 각각 변경·삭제, 친자 있음/없음 전환이 정상 |
| 상태·해상도 | 대기·진행·낙찰·유찰 및 4가지 해상도와 사업장별 고유 화면을 검사 |
| 수명 | 반복 진입·해제 시 이벤트 중복, 잔여 타이머·애니메이션이 없음 |
| 성능 | 합성 501품목 무변경/가격 변경/전체 변경에서 갱신 횟수·할당량을 비교하여 전량 재생성 회귀를 확인 |

WPF 바인딩 오류는 빌드 성공만으로 검출되지 않는다. 오프라인 STA/Dispatcher 환경에서 일반 `System.Windows.Application`과 합성 데이터로 컨트롤을 생성하고, 바인딩 진단과 실제 표시 값을 함께 검사한다. 진단 Listener는 검사 종료 시 해제하고 합성 데이터만 사용한다.

제품 `App` 시작이나 운영 서버 접속 없이 검증한다. 기존 검사 프로젝트를 우선 확장하며, 실행 중인 제품과 분리된 임시 출력 경로를 사용한다. 현재 동작과 비교할 때 디버그 원문 출력 조건을 동일하게 맞춘다. 처리 시간은 실제 전광판 렌더링 완료 시간으로 표현하지 않는다.

구현 후 실행할 명령의 예시:

```powershell
$bindingDebugOutput = Join-Path $env:TEMP 'CowAuction-BindingValidation-Debug'
dotnet build Validation/ReferenceAdoptionChecks/ReferenceAdoptionChecks.csproj --no-restore -p:OutputPath=$bindingDebugOutput -v:q
dotnet "$bindingDebugOutput\ReferenceAdoptionChecks.dll" all

$bindingReleaseOutput = Join-Path $env:TEMP 'CowAuction-BindingValidation-Release'
dotnet build Validation/ReferenceAdoptionChecks/ReferenceAdoptionChecks.csproj -c Release --no-restore -p:OutputPath=$bindingReleaseOutput -v:q

$bindingHistoryOutput = Join-Path $env:TEMP 'CowAuction-BindingValidation-History'
dotnet build Validation/OwnerHistoryChecks/OwnerHistoryChecks.csproj --no-restore -p:OutputPath=$bindingHistoryOutput -v:q
dotnet "$bindingHistoryOutput\OwnerHistoryChecks.dll" --offline
```

추가한 바인딩 검사는 `all`에 포함되도록 한다. 복원 자산이 필요한 경우에만 구현 단계에서 필요한 복원을 먼저 수행한다. 실제 전광판의 글자 위치·겹침·색상·스크롤 속도는 별도의 수동 확인 항목으로 남긴다.

## 7. 범위와 완료 조건

- 경매품 표시 영역에서 직접 속성 경로를 사용하는 규칙이 대기·진행·낙찰·유찰에 일관되게 적용된다.
- 진행 화면 루트의 ViewModel과 기존 화면 제어 동작을 보존한다.
- `CowInfo`를 경매품 표시 영역에 연결하는 경계는 허용하며, 내부 경매품 표시에서 불필요한 `CowInfo.XXX` 참조를 제거한다.
- 데이터 변경 시 화면 갱신과 무변경 시 갱신 생략이 모두 검증된다.
- 화면 디자인 변경, 프로토콜/API 파서 수정, 경매 판정 변경, 전체 모델 알림화, 폴더·클래스 이름 정리, 패키지 교체는 포함하지 않는다.
- 별도 승인 없이 commit·push·운영 배포를 수행하지 않는다.

최초 계획 작성에서는 문서만 추가했다. 이후 사용자가 총 3명의 에이전트로 진행하도록 승인하여 소스 구현과 오프라인 검증을 진행한다. 실제 결과는 아래 실행 결과와 `WORKLOG.md`에 기록한다.

## 8. 실행 결과 — 2026-09-22

- 총 3명이 공통 데이터 전달·화면 XAML·검증을 분담했다.
- 진행 페이지 32개의 기존 Grid·Canvas에 경매품 컨텍스트를 연결하고 517개의 `CowInfo.` 속성 경로를 직접 경로로 전환했다. 진행 상태와 비고 알림은 구체적인 상위 화면 ViewModel을 참조한다. 컨테이너·좌표·크기와 루트 ViewModel은 유지했다.
- 공통 배지, 진행 비고 호스트, 잘못된 유찰 개체번호 경로까지 XAML 35개를 변경했다. 화순 화면의 성별 스타일 Converter 2곳도 경매품 객체를 입력받도록 수정했다.
- ViewModel이 표시용 스냅샷을 소유하고, 변경된 입력에만 새 스냅샷과 알림을 제공한다. `Note` setter도 스냅샷을 교체하며 기존 진행 상태를 유지한다. 낙찰·유찰 진입점도 원본과 표시 객체를 분리하고 컨트롤 재사용을 유지한다.
- 마지막 스크롤 검사에서 같은 비고를 가진 다른 개체로 바뀔 때 진행 비고 호스트의 스크롤이 재시작하지 않는 현상을 수정 전 DLL로 재현했다. 내부 경매품 영역의 컨텍스트 변경에도 기존 애니메이션 수명 처리를 연결하고, 개체가 바뀌면 저장한 위치를 초기화했다. 수정 후 18개 스크롤 검사가 통과했다.

추가한 스크롤 전용 실행 명령:

```powershell

```

사업장별 실제 글자 배치·겹침·색상·스크롤 속도, 실제 운영 통신과 전광판 출력은 미수행이다. 기존 소유주 이력 전체 UI 경로는 UDP 동기화를 시작하므로 실행하지 않고 오프라인 두 모드로 검증했다. commit·push·배포는 수행하지 않았다.
