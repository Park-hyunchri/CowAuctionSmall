# SV·API 공통 변경 감지 및 갱신 개선 계획

> 문서 상태: **완료** · 정리일: 2026-10-01
> 공통 변경 감지·부분 갱신과 오프라인 검증 결과는 본문 11절에 있다. 실제 장비 성능과 운영 검증 범위는 별도로 본다.
> 현재 동작: [기능 문서](../../기능/README.md) · [전체 목차](../../README.md) · [작업 기록](../../../WORKLOG.md)

- 작성일: 2026-09-22
- 상태: 소스 구현·오프라인 검증 완료 / 실제 운영 통신·전광판 확인 미수행
- 요청 범위: 계획 문서 작성 후 사용자의 “좋아 진행하자”에 따라 구현·검증까지 진행. 아래 1~10절은 작성 당시 계획이며, 실제 결과는 11절에 기록한다.
- 목적: Netty SV와 API 조회 결과를 공통 변경 감지·반영 경로에서 처리하고, 실제로 달라진 정보만 화면에 전달한다.
- 기준: 현재 작업 폴더의 미커밋·미추적 변경을 포함한 구현. 앞서 완료한 SV 예정가 반영과 Netty 원문 Debug 출력은 유지한다.

## 1. 목표와 범위

1. `------------ 1`처럼 의미가 불분명한 건수 출력은 제거한다.
2. 단건 변경과 새로고침에 사용되는 SV를 같은 방식으로 해석한다. 가격뿐 아니라 SV에 실제로 포함된 비고·중량·개체정보 등의 변경도 반영한다.
3. SV와 API의 필드 위치 차이를 입력 단계에서 정리하고, 출품 식별·병합·비교·화면 통지는 공통으로 사용한다.
4. 출품별 사전을 유지해 SV 한 건을 받을 때마다 전체 목록을 검색하지 않는다.
5. 변경이 없는 수신은 화면 알림을 발생시키지 않는다. 연속 수신에서는 변경된 출품과 영향받는 계류대만 묶어 전달한다.
6. SV에 없는 API 전용 정보와 이력 정보, 최신 경매 진행·낙찰 상태를 보존한다.

이번 계획은 API 주소·호출 간격·인증·캐시 저장 정책, WPF 화면 디자인, 사업장별 표시 규칙을 바꾸지 않는다. 패키지 추가나 폴더 개편은 목표에 포함하지 않는다. 실제 속도 개선 수치는 구현 전후 측정 후에만 보고한다.

## 3. 입력 형식과 공통 데이터

### 3.1 형식별 필드 해석

아래 인덱스는 `|` 분리 후 0부터 시작한다. 표는 현재 코드 및 제공된 SV 형태를 기준으로 하며, 구현 첫 단계에서 실제 파싱 코드와 합성 예제로 확정한다.

| 항목 | Netty SV | 현재 API 파서 기준 |
|---|---:|---:|
| 출품번호 | 2 | 2 |
| 경매 회차 | 3 | 3 |
| 개체관리번호 | 5 | 5 |
| 중량 | 25 | 25 |
| 최초 최저가 | 26 | 26 |
| 현재 최저가 | 27 | 27 |
| 비고 | 28 | 28 |
| 낙유찰 결과 | 29 | 29 |
| 낙찰금액 | 31 | 31 |
| 계류대 번호 | 34 | 34 |
| 낙찰자 표시 정보 | 36 | 38 |
| 월령 | 37 | 39 |
| 등록구분명 | 38 | 40 |

- 입력 경로와 실제 형식을 명시적으로 전달한다. 메시지 접두어 하나나 배열 길이만으로 모든 필드 위치를 추측하지 않는다.
- 공통 앞부분을 재사용하되 뒤쪽 필드와 API 추가 정보는 각각의 형식으로 해석한다.
- AS[4]를 SV의 현재 예정가 대신 사용하지 않는다. 현재 예정가는 SV[27]과 API의 대응 필드에서 해석한다.
- 원문 전체를 새로운 영구 저장소나 파일 로그에 보관하지 않는다. 기존 사용자 요청에 따른 Netty 원문 Debug 출력은 유지한다.

### 3.2 필드 존재 여부를 갖는 입력 모델

형식별 파서의 결과는 업무 필드 값과 함께 다음 정보를 가져야 한다.

- 입력 출처: SV 또는 API.
- 경매 사업장·날짜·회차와 출품 식별 정보.
- 입력에 실제로 존재하는 필드 집합.
- 필드별 유효성 및 수신 순서/요청 기준 정보.

`없음`, `명시적인 빈 값`, `잘못된 값`을 구분한다.

| 상태 | 반영 원칙 |
|---|---|
| SV에 해당 필드가 없음 | 기존 값을 유지 |
| 필드가 있고 빈 값이 정상 의미임 | 해당 값 제거/초기화. 예: 비고 삭제 |
| 가격·날짜·식별자 등 필수 형식이 잘못됨 | 해당 값으로 기존 정상 데이터를 덮어쓰지 않음 |
| 식별 불가 또는 구조가 잘린 메시지 | 적용하지 않고 기존 복구 경로 사용 |
| 가격 0 등 기존 파서에 특별한 의미가 있음 | 기존 결장 등 표시 규칙 유지 |

부분 데이터에서 만든 기본 `gValues`를 기존 개체 전체에 덮어쓰지 않는다. 입력에 있는 값을 기존 상태에 병합한 후 기존 사업장별 표시 변환을 적용한다. 표시 옵션·관련 필드가 바뀌면 성별 표시, 월령, 파생 문구 등도 함께 다시 계산한다.

## 4. 공통 변경 감지와 출품 저장

### 4.1 처리 흐름

```text
Netty SV → SV 형식 해석 ─┐
                        ├→ 공통 병합·비교 → 변경 출품/계류대 → 화면 알림
API 응답 → API 형식 해석 ┘
                            ↑
                  현재 출품 사전·진행/결과 보호 규칙
```

- 새 업무 처리기는 기존 `AuctionIngress`의 단일 상태 처리 흐름 안에서 사용한다. 별도의 상태 변경 스레드를 추가하지 않는다.
- 출품별 사전을 초기 API/캐시 목록에서 구성하고 이후 추가·수정·삭제 시 함께 유지한다.
- 경매 세션은 사업장·날짜·회차를 기준으로 구분하고 세션 내부에서는 출품번호로 조회한다. 개체관리번호도 확인하여 동일 출품번호에 다른 개체가 들어온 경우를 일반 수정과 구분한다.
- 날짜·회차를 아직 모르는 초기 신호는 임의의 날짜/회차를 만들어 기존 출품에 붙이지 않는다. 기존 초기 목록 대기·회차 확인 경로와 연결해 일치하는 세션에만 적용한다.
- 계류대는 변경 가능한 표시 위치이므로 출품의 식별 키로 사용하지 않는다. 같은 계류대 후보를 찾기 위한 보조 색인을 유지한다.

### 4.2 변경 여부 판단

1. 키로 기존 출품을 찾는다.
2. 입력에 포함된 유효 필드를 비교한다. 동일하면 기존 상태와 화면 알림을 그대로 둔다.
3. 변경 필드를 병합하고 파생 표시 값을 계산한다.
4. 업무 데이터가 바뀌었는지와 현재 표시 내용이 바뀌었는지를 구분한다. 화면에 나타나지 않는 변경도 상태 저장에는 반영한다.
5. 화면에 영향이 있으면 해당 출품과 기존/새 계류대를 변경 집합에 추가한다.

기존 `gValues.Equals`, `DisplayUpdateTracker` 및 관련 검사 항목을 검토해 비교 기준을 재사용한다. 비교 대상 누락이나 중복 정의가 있으면 이번 갱신 범위에 필요한 만큼 정리한다. 해시가 같다는 이유만으로 변경이 없다고 확정하지 않는다. 성능 병목이 확인되기 전에는 새로운 해시 계층을 추가하지 않는다.

### 4.3 부분 갱신과 전체 목록 구분

- SV 한 건은 해당 출품에 대한 부분 갱신이다. 이번 SV 묶음에 나오지 않았다는 이유로 다른 출품을 삭제하지 않는다.
- API 전체 목록은 현재 세션의 정상적이고 유효한 전체 응답임을 확인한 뒤 추가·수정·삭제를 판단한다. 실패·잘린 응답을 빈 목록으로 취급하지 않는다.
- 초기 전체 표시와 세션/보드 초기화에는 전체 목록 알림을 사용할 수 있다. 이후 같은 세션의 반복 조회는 변경 목록과 삭제/계류대 해제 정보만 전달한다.
- 전체 응답의 통계는 데이터 변경이 없어도 필요하면 갱신한다. 통계 전달 때문에 전체 화면 데이터를 다시 보내지 않도록 한다.
- 계류대 이동·삭제·개체 교체는 이전 위치와 새 위치의 후보를 모두 다시 선택한다. 기존 `CowDisplaySelector`의 우선순위와 다중 물리 슬롯 표시를 유지한다.

## 5. SV와 API가 경합할 때의 규칙

공통 처리는 두 입력이 항상 같은 시점의 데이터라는 뜻이 아니다. 현재 `AuctionIngress`의 요청 세대·날짜 검사와 경매 상태 보호를 유지하면서 필드 단위 병합을 보완한다.

1. API 요청을 시작할 때 세션과 당시의 SV 반영 순서를 기록한다.
2. 응답이 도착하면 세션·요청 유효성을 먼저 확인한다.
3. 요청 시작 이후 SV로 변경된 필드는 오래된 API 응답으로 되돌리지 않는다. 영향을 받지 않은 API 전용 정보는 유효한 경우 반영한다.
4. SV로 변경된 필드는 API가 같은 값을 반환하면 동기화가 확인된 것으로 처리한다. 확인 과정에서도 더 늦은 SV가 있었는지 검사한다.
5. AS/AF로 확정한 진행·종료·낙찰 결과와 낙찰자 확인 규칙은 일반 SV/API 병합보다 우선한다. SV의 낙유찰 필드를 단순 덮어써 진행 상태나 확정 결과를 되돌리지 않는다.
6. 세션 변경·재접속·재동기화에서는 사전, 보호된 변경, 표시 대기 데이터의 수명을 함께 정리한다. 종료된 세션의 콜백은 반영하지 않는다.

서버가 공통 버전/수정 시각을 제공하지 않으면, 뒤늦게 조회한 API 값이 오래된 복제본인지 새로운 수정인지 완전히 구분할 수 없다. 따라서 타임아웃만으로 SV 우선권을 해제하지 않는다. 우선 기존 가격 보호처럼 API 일치 확인과 세션 수명을 사용하고, API에서만 다른 값으로 수정되는 운영 사례는 수동 확인 항목으로 남긴다. 최초 구현에서 서버에 없는 정렬 규칙을 가정하지 않는다.

## 6. 화면 알림 묶음과 로그

### 6.1 상태는 즉시 반영하고 화면 알림만 합치기

- SV마다 검증·변경 감지·업무 상태 반영은 즉시 수행한다.
- 같은 출품에 여러 변경이 이어지면 대기 중인 화면 데이터는 최신 상태 하나로 합친다.
- 첫 변경은 가능한 한 즉시 전달하고, 이미 화면 작업이 대기 중이면 후속 변경을 합친다. 첫 구현의 묶음 간격 후보는 약 30ms이며 고정된 초기 마감 시점을 사용한다. 입력이 계속된다는 이유로 마감 시간을 계속 뒤로 미루지 않는다.
- AS 시작·종료, AF 결과, 날짜/방식 전환이 오면 이전 화면 대기 데이터가 새 상태를 나중에 덮지 않도록 먼저 정리하거나 무효화한다. 이 신호를 SV 전체 수신 종료까지 대기시키지 않는다.
- 가격 단건 변경도 501건 전체 수신 완료를 기다리지 않는다. 묶음 간격의 적절성은 상태 처리 시각과 UI 적용 시각을 따로 측정해 결정한다.
- UI에 보낼 데이터는 독립된 복사본으로 전달한다. 예약된 UI 작업은 실행 직전에 세션·표시 순서·Dispose 상태를 확인한다.
- 타이머/예약 작업은 최대 하나의 활성 일정으로 관리하고 화면 종료·서비스 해제 시 구독과 함께 정리한다.

### 6.2 로그 정리
