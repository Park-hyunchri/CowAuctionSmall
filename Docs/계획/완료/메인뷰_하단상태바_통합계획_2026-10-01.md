# 메인뷰 하단 상태바 통합 계획

- 작성일: 2026-10-01
- 상태: **구현·오프라인 검증 완료 · 운영 전광판 검증 미수행**
- 요청: AMS_Server의 구획형 상태바와 현재 프로젝트의 흰색 경매·이력 안내를 하나의 영역으로 통합한다.
- 승인 이력: 최초 계획 작성 후 사용자가 에이전트를 사용한 구현 진행을 승인했다. 총 3명이 경매 상태·페이지 상태·UI 통합을 분담했다.

## 1. 목적

응찰서버 연결, 마스터·서브 역할, 경매 상태, 페이지 상태와 최근 수신 정보를 한곳에서 확인하도록 배치한다. 현재 흰색 안내의 정보와 초록색 로그의 가독성을 유지한다.

참고 대상은 로컬 `AMS_Server/CowAuctionSmall/Views/MainWindow.xaml`과 `ViewModels/MainWindowViewModel.cs`다. 구획과 색상 표현을 참고하고, 현재 프로젝트의 상태 전달 흐름에 맞게 구현한다.

## 3. 최초 계획의 표시 구성

아래는 최초 계획 예시다. 후속 사용자 요청으로 변경한 현재 배치는 10절을 기준으로 한다.

```text
응찰서버 ● 연결 │ 마스터 모드 │ 일괄경매 · 대기 │ 뿌리농가 Y │ 페이지 1/3 · 전환 중 │ 버전 …
최근 수신 11:25:10 · 경매 대기 신호 │ 구분 0(전체) · 1구간 · 출품 1~999번
이력 처리 115/115건 · 소유주 변경 비고 87건 · 캐시 115 · 실패 0
──────────────────────────────────────────────────────────────────────────────
기존 초록색 로그
```

- 첫 줄은 어두운 배경, 흰색 글자, 얇은 세로 구분선으로 항목을 구분한다.
- 최근 신호·구간과 이력 안내는 같은 상태 영역의 두 번째·세 번째 줄에 둔다.
- 기존 하단의 별도 모드·페이지 바를 통합하여 동일 정보를 중복 표시하지 않는다.
- 페이지 점은 현재/전체 표기와 함께 공간이 허용되는 범위에서 유지한다. 점을 생략해도 현재 위치와 고정·복구 상태는 텍스트로 확인 가능해야 한다.
- 정상 연결은 녹색, 대기·미확인은 회색, 고정·주의는 황색, 연결 종료·오류는 적색을 기본으로 한다. 로컬 복구는 기존 하늘색 의미를 유지한다. 색만으로 상태를 구분하지 않고 문구와 툴팁을 제공한다.
- 기본 글자 크기 12와 초록색 로그의 기존 가용 높이를 유지한다. 로그의 새로고침 메뉴·스크롤 이벤트는 보존한다.
- 고정 열 너비를 그대로 복사하지 않는다. 좁은 창에서는 항목 묶음 단위로 줄바꿈하고, 상세 안내의 긴 문구는 말줄임과 전체 툴팁을 제공한다. 필요한 상태 영역 높이는 창 높이 계산에도 반영한다.
- 버전은 실행 어셈블리에서 가져와 페이지 상태 바로 옆에 표시한다. 문자열을 하드코딩하지 않는다.

## 4. 표시 상태와 데이터 기준

### 4.1 응찰서버

- 기존 `NettyConnectionResultMessage`의 성공·실패·중복 접속 결과와 연결 종료 전달 경로를 사용한다.
- 초기 상태는 `확인 중`으로 표시한다. 응답이 없다는 이유로 성공 상태를 가정하지 않는다.
- 연결 종료 시 녹색 성공 표시를 해제하고 재접속 성공 시 복원한다.
- 마스터·서브 역할과 응찰서버 연결은 독립 항목으로 유지한다.

### 4.2 경매 방식·진행 상태

- 경매 방식은 현재 수신 처리의 단일·일괄 구분을 사용한다.
- 대기·진행·종료·미확인을 실제 상태 처리 결과로 표시한다. 단일 경매의 대상 번호는 현재 처리에서 확인된 경우에만 덧붙인다.
- 사용자용 로그나 `AuctionSignalDisplayText`의 한국어 문자열을 다시 파싱하지 않는다. 기존 수신 처리에서 확정된 값을 담는 작은 표시용 메시지 또는 상태 객체를 전달한다.
- 아직 진행 여부를 받지 못한 상태를 `종료`로 단정하지 않는다. 연결 종료나 방식 전환 시 이전 상태가 현재 값처럼 남지 않도록 초기화 기준을 정한다.
- 최근 수신 시각·신호 문구와 구간 정보는 기존 상세 안내를 유지한다. 업무 처리·원문 로그 방식은 변경하지 않는다.

### 4.3 페이지·동기화 상태

페이지는 `현재/전체`로 표시한다. 1페이지뿐이어도 상태 영역을 숨기지 않는다.

| 조건 | 표시 기준 |
| --- | --- |
| 고정 사유 있음 | `고정`과 실제 사유를 표시하고 현재 페이지 값 사용 |
| 전체 1페이지 | `1/1 · 단일 페이지`로 표시하며 회전 중이라고 하지 않음 |
| MASTER, 여러 페이지, 타이머 실행 | `전환 중` |
| MASTER, 여러 페이지, 타이머 정지 | `정지` |
| SUB, 정상 동기화 | `동기화 수신 모드`로 표시. 로컬 타이머가 없다는 이유로 정지 판정하지 않음 |
| SUB, 로컬 복구 | `로컬 복구`와 로컬 타이머 실행·정지를 구분 |
| 초기 상태 또는 유효한 정보 없음 | `확인 중` |

- `DisplaySelect`가 소유한 실제 타이머 실행 여부를 스냅샷·메시지에 추가 전달한다. UI가 타이머를 직접 조회하거나 별도 폴링하지 않는다.
- 시작·정지·역할 전환·복구 전환·페이지 변경 시 상태 발행 누락 여부를 확인한다.
- SUB의 수신 모드 표기를 원격 MASTER의 타이머 실행이 확인되었다는 의미로 사용하지 않는다.
- 새로고침 후 회전 재개 누락은 [기존 후속 과제](../../기능/화면표시_페이지전환.md#남은-확인)다. 이번 계획에서는 실제 정지를 정확히 표시하며 회전 정책이나 재개 로직 수정은 별도로 다룬다.

### 4.4 설정·이력·버전

- 뿌리농가 값은 현재 로드된 `IsShowQQuri`의 Y/N/X를 표시한다. 누락·알 수 없는 값은 `미확인`으로 두고 설정값을 변경하지 않는다.
- `HistoryProgressText`와 `AuctionSectionText`의 기존 의미·갱신 경로를 유지한다.
- 버전은 기존 `VersionShow()`의 어셈블리 버전 읽기를 재사용한다.

| 이력 조회 꺼짐·진행·완료·실패 | 기존 이력 문구·카운트·갱신 흐름 보존 |
| 좁은 창·일반 창·긴 안내·DPI 배율 | 상태 항목과 로그가 겹치거나 잘리지 않고 툴팁 확인 가능 |

- 상태 조합·전이 검사는 기존 검증 도구를 우선 활용하고 운영 서버에 연결하지 않는 방식으로 수행한다.
- 구현 후 별도 임시 artifacts 경로로 `dotnet build CowAuctionSmall.csproj --artifacts-path <임시경로> -v:minimal`을 실행한다. 후속 빌드는 복원 자산이 동일하면 `--no-restore`를 사용한다.
- 실제 다중 PC 동기화·운영 수신·전광판 검증은 오프라인 결과와 구분하여 기록한다. 미수행 항목을 완료로 표시하지 않는다.
- 현재 경매품 화면·설정값·API·캐시·회전 정책을 보존하고 하단 상태의 통합·정확성·가독성을 확인하면 구현 완료로 판단한다.

- 구획형 상태바, 최근 수신·구간, 이력 안내를 로그 위로 통합했다. 후속 사용자 요청에 따라 버전은 모든 폭에서 페이지 상태 다음에 붙이며, 공간이 부족하면 줄바꿈한다. 상태 영역 실측 높이로 창 높이를 갱신하며 로그 행은 70을 유지한다.
- 경매 표시 전이는 `AuctionDisplayState`와 별도 메시지 파일로 구현했다. 8001은 미확인, 8002는 대기, 8003은 가격 변경으로 기존 진행 유지 또는 대기, 8004는 진행, 일치하는 종료 신호는 종료다. 의미가 확정되지 않은 8005·SD F는 진행 상태를 임의로 바꾸지 않는다.
- 연결 종료를 전달하고 실패 중의 늦은 경매 표시 갱신을 무시한다. 중복 접속 후 채널이 닫혀도 중복 사유를 유지한다. 수신 예외를 실제 종료와 혼동하지 않도록 `AuctionClientInboundDecoder.ExceptionCaught`는 기존 연결 예외 콜백을 호출한다.
- 페이지 상태에는 실제 타이머 실행 값을 추가했다. 단발 타이머의 페이지 전환 후 재시작 상태도 발행한다. 정상 SUB는 `동기화 수신 모드`, fallback은 `로컬 복구`로 구분한다.
- `Views/MainWindow.xaml.cs`에는 레이아웃 높이 전달만 추가했다. 새 업무 로직·통신·타이머를 넣지 않았다.
- 기존 `HistoryProgressUiChecks`의 옛 높이 기반 탐색을 이름 기반으로 변경했다. `DisplayLifetimeChecks`의 오래된 3페이지 사업장 기대값을 기존 HEAD의 정책과 일치시켰으며 실제 사업장 선택 코드는 수정하지 않았다.
